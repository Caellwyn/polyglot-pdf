**Model:** claude-opus-4-8 via the local `claude` CLI (free in-env). All runs use

## TL;DR (for the maintainer)

7a9.10 showed the LLM-native architecture nails the SMALL form (I-90: F1 ~97).
This bead is the stress test on the BIG form: **I-589, 460 widgets, 12 pages, 9
tables.** The result is a clear two-part answer:

- **Q6 (does the single-shot call complete?) -- YES.** Opus produced a full schema
  from the 460-widget form in one call (~28 min, 168K output tokens), no timeout,
  no truncation. The file-delivery fix from 7a9.10 carries it. gemini-3.1-pro timed
  out on the SMALLER hybrid prompt in the bake-off; the Opus-via-CLI path does not.
  **No chunking is required for the call to complete.**

- **Q5 (does the enriched bundle help table / consolidation?) -- NO, decisively.**
  Every arm badly UNDER-CONSOLIDATES and detects **0 of 9 tables.**

| I-589 arm | fields (gold 156) | F1 | type | pfn | tables (gold 9) | show_if (53) | sections (gold 9) |
|---|---:|---:|---:|---:|---:|---:|---:|
| single-shot, no few-shot | 433 | 28.9 | 82.4 | 98.8 | **0** | 0 | 12 |
| single-shot, + few-shot | 349 | 31.3 | 86.1 | 100.0 | **0** | 1 | 10 |
| **chunked (per-page)** | 402 | 31.9 | 85.4 | 94.4 | **0** | 2 | 40 |
| *(I-90 single-shot, 7a9.10)* | *132 (=gold)* | *~97* | *97* | *100* | *0 in gold* | *74%* | *match* |

F1 collapses from ~97 (I-90) to ~29-32 (I-589). The cause is NOT the call failing
and NOT context overload -- it is **table/multi-entry consolidation**, a genuine
semantic gap the enriched bundle does not close.

## Why it fails: the gold's tables are a structural abstraction the bundle can't see

I-589's gold collapses 460 raw widgets into 156 logical fields. The hardest part:
**9 `type: table` fields** that each describe a repeating table by STRUCTURE
(`columns` + `multi_entry`), not by enumerating widgets. Example: the gold's
`part_a_i_us_entries` is ONE field with `columns: 4, multi_entry: true` -- but the
AcroForm exposes that table as ~16-20 flat text widgets (4 columns x N rows). 7 of
the 9 tables sit in Part A (pages 0-3), the densest region.

The model has no generic way to know those 20 flat widgets ARE a 4-column
repeating table from names + geometry alone -- it sees 20 separate text boxes and
emits ~20 separate fields. That is the bulk of the 348 spurious fields. **This is
a real semantic gap, not a prompt-size or chunking artifact:** I-90 has ZERO tables
and the same architecture scored ~97; I-589 has 9 and it scored ~29. The
table-consolidation difference explains essentially the entire quality gap.

Two corollaries, both confirmed in the data:

- **The (b) relationship 0% is DOWNSTREAM of the consolidation failure, not an
  independent gap.** The model DID synthesize 37 show_if + 23 controls_fields in
  the no-shot draft -- it is not ignoring conditionals. They score ~0 because the
  scorer credits a gold field's show_if only if the gold field's MATCHED draft
  field also carries one (`schema_score.score_relationships`); with only 85/156
  gold fields matched and the granularity diverged, the model's conditionals hang
  off field ids that do not line up with the gold. Fix consolidation and (b)
  becomes scoreable; until then (b) recall on the big form is uncreditable.
- **`pdf_field_name` fidelity stays high (94-100%) even at 460 widgets** -- the
  anti-hallucination anchor holds at scale (answers the bead's Q4-at-scale sub-
  question). The model copies exact widget names faithfully; it just groups them
  wrong.

## The chunking test: per-page chunking does NOT fix it (hypothesis falsified)

The obvious hypothesis was context overload: the model consolidates well on
I-90's small pages (<=99 widgets) but loses the thread across 460 widgets in one
shot. So I built `arm_llm_native_chunked.py` -- a minimal per-page chunked pass
(each page extracted independently where the model is at I-90 scale, then field
lists merged). I-589's tables each sit within a single page and no page exceeds 99
widgets, so page-chunking keeps every call I-90-sized.

**It did not help.** Chunked produced 402 fields (vs single-shot's 433) and **still
0/9 tables** -- the model under-consolidates a 59-widget page just as it does the
460-widget form. So context size is NOT the cause; the cause is that recognizing
"these flat widgets are a repeating table" is a semantic judgment the model does
not make from the enriched bundle, at any chunk size. Chunking also INTRODUCED a
regression: 40 sections vs the gold's 9 (each page invents its own sections,
because no chunk sees the global part/section structure) -- a merge problem a naive
per-page split creates.

**Conclusion on chunking:** page-chunking is the wrong lever for I-589. It does not
fix consolidation (the real problem) and it breaks global structure. If chunking is
used at all, the unit should be a PART (which bounds a coherent section block), not
a page -- but even part-chunking will not detect tables without an explicit table
pass. The recommendation is NOT to chunk, but to add a table-aware step (below).

## Recommendation (feeds 7a9.12)

1. **The LLM-native architecture is validated for COMPLETION at 460 widgets but is
   NOT sufficient for big, table-heavy forms as-is.** It is the right engine for
   small/flat forms (I-90) and for the per-field (a) layer; it does not solve table
   consolidation on I-589.
2. **Table detection needs an explicit, dedicated pass -- it is the dominant
   residual cost on big forms.** Options, in rough order of generality: (a) a
   table-region detector (the printed page has visible grid lines / column headers
   the model CAN see in the image -- the 7a9.10 annotated-page approach is a
   natural fit: ask the model "which marker groups form a repeating table?"); (b)
   feed the gold's `columns`/`multi_entry` table schema as an explicit few-shot so
   the model knows the target shape. Neither was tested here; both are 7a9.12 work.
3. **Do NOT page-chunk.** It does not help and breaks global structure. If the
   single-shot ever does fail to complete on a bigger form, part-chunk (not page-
   chunk) and add a global merge/dedup pass for parts+sections.
4. **(b) relationships are blocked behind consolidation on big forms.** Measuring
   (b) on I-589 is not meaningful until consolidation is fixed; revisit after the
   table pass lands.

The headline for the epic: on big forms the residual human-labor hours are in
**table/multi-entry consolidation**, exactly the (a)/(b)-spanning structural work
the original epic framing predicted would be the hard part -- now localized to a
specific, addressable pass.

## Reproducibility

```
VENV=backend/.venv/Scripts/python.exe
PYTHONPATH=. $VENV scripts/bakeoff/acroform_dump.py \
    example_pdfs/i-589/i-589-asylum-application.pdf \
    --json scripts/bakeoff/outputs/i589_acroform.json   # 460 widgets, 12 pages

# single-shot (completes; default trim + light order framing):
PYTHONPATH=. $VENV scripts/bakeoff/arm_llm_native.py \
    --pdf example_pdfs/i-589/i-589-asylum-application.pdf \
    --acroform scripts/bakeoff/outputs/i589_acroform.json --out OUT.json
#   + few-shot: --fewshot-truth form-kits/i-90/schema.json
# chunked (per-page; does NOT fix consolidation):
PYTHONPATH=. $VENV scripts/bakeoff/arm_llm_native_chunked.py \
    --pdf example_pdfs/i-589/i-589-asylum-application.pdf \
    --acroform scripts/bakeoff/outputs/i589_acroform.json --out OUT.json
PYTHONPATH=. $VENV scripts/schema_score.py --draft OUT.json \
    --truth example_pdfs/i-589/i589_schema.json
```

Single-shot is ~28 min / ~150-170K output tokens; chunked is ~16 min over 12
sequential per-page calls. Outputs gitignored. n=1 per arm (the result -- 0/9
tables, F1 ~30 across all three arms -- is unambiguous enough that repeats would
not change the conclusion; `pdf_field_name` fidelity and field-count divergence
are deterministic-ish at temperature 0).

## Decisions made autonomously (and why they were mine)

- **Built `arm_llm_native_chunked.py` to test the chunking hypothesis** rather than
  just reporting the single-shot failure -- the bead explicitly asks for "a
  chunking design IF the single-shot fails"; the single-shot completed but failed
  on QUALITY, so testing whether chunking fixes quality is the same deliverable in
  spirit. A reversible research script. Implementation call.
- **Diagnosed the failure as table-consolidation (not context size)** by checking
  the gold's table schema + running the chunk control, rather than assuming. The
  data falsified the obvious context-overload hypothesis.
- **n=1 per arm.** The 0/9-tables result is categorical, not marginal; spending 3x
  the Opus time for repeats of an unambiguous failure is not warranted. Noted.
- **Recommended a table-aware pass over chunking** as the 7a9.12 direction, and
  pointed at the 7a9.10 annotated-page approach as the natural detector -- a
  technical recommendation within the research remit (the actual build is 7a9.12).
