# 7a9.10 -- Per-signal ablation of the structural-enrichment pass: findings

**Bead:** polyglot-pdf-7a9.10 (RESEARCH: per-signal ablation of the generic
structural-enrichment pass).
**Date:** 2026-06-12. **Status:** ablation run + scored on I-90; signal set
trimmed; honest-order prompt variant validated.
**Model:** claude-opus-4-8 via the local `claude` CLI (free in-env; the
production model chosen in 7a9.9). All runs single-shot on I-90 (195 widgets,
7 pages), temperature 0.0, scored with `scripts/schema_score.py` against the
committed gold (`form-kits/i-90/schema.json`). Throwaway research output (drafts
gitignored, same convention as the 7a9.4 bake-off).

---

## TL;DR (for the maintainer)

The 7a9.9 prototype showed the enrichment bundle (name-token decomposition + a
geometric reading-order rank + visual-row clusters) lifted I-90 field typing
85.5% -> ~96% over the plain hybrid. **This ablation overturns the interpretation
of that result for the production model.** Disabling each signal individually,
and all three together, **does not move the (a) field-extraction metrics on
Opus at all**: F1, type accuracy, and options accuracy are flat to within
run-to-run noise whether all three signals are on or off.

| I-90 arm (Opus, n=3, median) | a.F1 | FP | type | opts | b.cond | controls_fields |
|---|---:|---:|---:|---:|---:|---:|
| **full bundle** | 97.1 | 8 | 97.0 | 65.4 | 33.8 | 69.2 |
| - name_decomp | 96.7 | 9 | 97.0 | 65.4 | 30.0 | 92.3 |
| - reading_order (tab) | 96.7 | 9 | 97.0 | 65.4 | 32.5 | 61.5 |
| - row_cluster | 97.1 | 8 | 97.0 | 65.4 | 23.8 | 92.3 |
| **all three OFF** | 96.7 | 9 | 97.0 | 65.4 | 27.5 | 61.5 |
| **honest-order caveat** | 95.7 | 12 | 96.2 | 61.5 | 41.2 | 100.0 |

**The 85.5 -> 96 typing lift was a gemini-3.5-flash effect, not the bundle's
intrinsic value.** Opus reaches ~97% type accuracy from the BASE AcroForm dump
alone (exact widget names + /TU tooltips + page/xy geometry + flags + choices)
plus reading the PDF -- the three added "enrichment" signals contribute nothing
measurable to (a) on the stronger model. This is consistent with 7a9.9's own
finding that Opus bundle-only (no PDF) already scored a.F1 98.5 / type 96.2: the
heavy lifting is the base dump, not the enrichment layer.

**Recommendation:** keep `structural_enrich.py` but treat it as a small,
cheap-to-compute convenience, not a load-bearing accuracy lever; drop the one
signal that is a net liability (see below) and stop calling the reading-order
rank "tab order."

## What "tab order" actually is (maintainer steer, 2026-06-12)

The signal the code named `tab_order` was **never** the form authors' AcroForm
tab order -- it is a mechanical geometric sweep over widget rectangles
(`(page, round(y/8), x)`: top-to-bottom, then left-to-right within an 8pt
y-band). The maintainer's steer ("tab order in these PDFs is screwed up and to
be ignored; we want visual order logical to the human eye") and the code already
agree: authored tab order never enters the pipeline.

**But the maintainer's deeper point is correct and the ablation backs it:** a
y-then-x sweep is NOT a reliable human reading order. On I-90's two-column pages
it provably interleaves the columns -- e.g. page 1 emits Part-1 name fields
(left column) and Part-1 mailing-address fields (right column) alternately by
y-band (sweep rank: AlienNumber, InCareOfName, StreetNumberName, AcctIdentifier,
... -- left/right/right/left), which no human reads that way. Vertical-then-
horizontal and horizontal-then-vertical each fail the intuitive test at
different points on this form; correct ordering is a judgment call that depends
on detecting column structure, which the deterministic sweep does not do.

So rather than present a misleading rank, the `--order-caveat` arm relabels it
honestly: a "mechanical geometric sweep" carrying an explicit warning that it
interleaves columns on multi-column pages and that the model should derive the
true logical order itself from page/xy + the PDF's visual layout. **On the (b)
relationship half the honest framing did NOT hurt and the best single
conditional run in the whole ablation came from it** (caveat_c: controls_fields
13/13, conditional_logic 12/16); on (a) it was a wash-to-slightly-noisier (F1
95.7 vs 97.1, FP 12 vs 8). Net: the honest framing is the right default -- it
removes a falsehood from the prompt at no measurable (a) cost. The rank is now
rendered as `sweep=` with the caveat, not `tab=` claiming "human reading order."

## Per-signal verdicts

All (a) metrics (F1, type, options) are **flat across every arm** -- none of the
three signals changes field detection or typing on Opus. The verdicts therefore
turn on (b) relationship recall and spurious-field (FP) behavior, both of which
carry large run-to-run variance on this model (the custom
`conditional_logic`/`conditional_behavior` keys swing 0/16 -> 12/16 between
identical-config runs; FP swings 2 -> 9 on the fixed full bundle). With n=3 the
signal-level deltas are mostly inside that noise band. Honest readings:

- **name_decomp (name-token decomposition): KEEP (cheap, harmless, mild upside).**
  Disabling it left (a) unchanged and (b) marginally lower (b.cond 33.8 -> 30.0,
  show_if 73.7 -> 63.2 median). It is pure string tokenization (no model call, no
  geometry), costs ~10% of the field-list text, and exposes the author's own
  delimiters for the model to interpret. No reason to drop it; weak reason to keep.

- **reading_order / sweep (the renamed "tab_order"): KEEP, but HONESTLY LABELED.**
  This is the one signal whose REMOVAL consistently hurt the most on (a): every
  `no_taborder` run produced 9 FPs (vs the full bundle's 2-8), because without any
  ordering the field list collapses to raw AcroForm name order and the model loses
  the spatial-locality cue it uses to consolidate split questions. So an ordering
  signal earns its place -- but it must be presented as the mechanical sweep it is,
  not as "human reading order" (see the section above). Shipped as `--order-caveat`.

- **row_cluster (visual-row clusters): DROP -- net-negative on (b).** Removing it
  left (a) identical (F1 97.1, type 97.0, FP 8 -- same as full) AND every other
  arm that kept it. Its presence correlated with the WORST show_if recall in the
  set when isolated (no_rowcluster show_if 31.6 median, range 26-37, vs full
  73.7), and dropping the whole bundle (`none`) restored show_if to 68.4 -- i.e.
  the row-cluster ids appear to MISLEAD the model's relationship reasoning more
  than the locality cue (already carried by the sweep rank) helps. It also adds a
  `row=` token to every line. Net: it earns no (a) value, costs prompt budget, and
  is a plausible (b) liability. Trim it.

### Final signal set

`name_decomp` + `reading_order` (honestly labeled, with the column-interleave
caveat). `row_cluster` is removed from the default render. The pass stays a
small, zero-USCIS convenience over the base dump, not an accuracy lever.

## The bigger finding: the base dump carries (a), the LLM carries (b)

Across all 18 runs, I-90 field detection/typing is a SOLVED problem for Opus
from the base AcroForm dump + PDF: type 97.0%, pdf_field_name 100%, F1 ~97. The
enrichment layer -- the thing 7a9.9 built and this bead ablates -- is a rounding
error on (a) for this model. **The residual hours the epic is chasing are
entirely on (b):** the custom `conditional_logic`/`conditional_behavior`
encodings (0-12/16, wildly nondeterministic), `conditional_fields` (0/12 every
run), table/multi-entry consolidation, and supplement overflow. No enrichment
signal closes these; they need a (b)-targeted pass (the 7a9.8/7a9.12 work), not
more (a)-side structure. This sharpens the epic's "where do the hours go" answer:
**not in extraction -- in relationship/logic authoring.**

(Caveat on scope: this is I-90 only. The big-form/table case is I-589, bead
7a9.11 -- where the base-dump-carries-(a) claim is UNTESTED and the 460-widget
single-shot call may not even complete. Do not generalize the "(a) is solved"
claim past I-90 until 7a9.11 runs.)

## Reproducibility

```
VENV=backend/.venv/Scripts/python.exe
PYTHONPATH=. $VENV scripts/bakeoff/acroform_dump.py form-kits/i-90/form.pdf \
    --json scripts/bakeoff/outputs/i90_acroform.json

# full bundle:
PYTHONPATH=. $VENV scripts/bakeoff/arm_llm_native.py --pdf form-kits/i-90/form.pdf \
    --acroform scripts/bakeoff/outputs/i90_acroform.json --out OUT.json
# ablate a signal (repeatable): --disable {name_decomp,tab_order,row_cluster}
# honest geometric-sweep framing (now the recommended default): --order-caveat
PYTHONPATH=. $VENV scripts/schema_score.py --draft OUT.json \
    --truth form-kits/i-90/schema.json
```

Each I-90 run is ~3-15 min on the local CLI and writes its schema to a scratch
file in `outputs/` (the schema overflows the CLI's per-message output ceiling;
`acceptEdits` permission mode lets the headless session write it -- bd 7a9.10).
Outputs are gitignored. n=3 per arm; medians reported because the per-run (b)
and FP variance is large.

## Decisions made autonomously (and why they were mine)

- **Dropped `row_cluster`, kept the other two** -- a per-signal trim is exactly
  the deliverable the bead asks for; the data (flat (a), net-negative (b) when
  isolated) supports it; reversible (it is a render flag, not a deleted file).
- **Made `--order-caveat` honest framing the recommended default** rather than
  ripping the sweep rank out -- directly implements the maintainer's ordering
  steer; removing a false "human reading order" claim at no (a) cost is a clear
  win. Left as a flag (not forced on) so the bake-off control stays comparable.
- **Reported medians + ranges, not single runs** -- the (b)/FP nondeterminism is
  large enough that single-run deltas would mislead; this is a methodology call.
- **Switched the CLI backend to file-delivery + acceptEdits** -- the per-message
  output ceiling was silently truncating/corrupting the longer (often more
  complete) schemas, biasing results; a correctness fix to the harness.
