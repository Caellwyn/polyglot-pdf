## TL;DR (for the maintainer)

I prototyped the architecture the bead proposes: **drop the USCIS-specific
heuristic parser, and instead feed a strong LLM a generic, form-agnostic bundle of
every structural signal the PDF exposes** (exact widget names + tooltips + geometry
+ name-token decomposition + tab order + visual-row clusters), plus an optional
few-shot example distilled from a *different* form's gold schema.

Held the model fixed at **gemini-3.5-flash** (the bake-off's recommended Gemini) so
the only thing changing is the **architecture**, not the model. Three runs on I-90,
scored with the committed scorer against the committed I-90 ground truth:

| Arm (I-90, gemini-3.5-flash) | a.F1 | a.attr | type | b.cond | section_id |
|---|---:|---:|---:|---:|---:|
| baseline `gemini35flash-hybrid` (re-run) | 97.0 | 32.2 | 85.5 | 26.2 | **0.0** |
| **PROTO: + generic enrichment, no few-shot** | **98.5** | 34.2 | **96.9** | 21.2 | **0.0** |
| **PROTO: + enrichment + cross-form few-shot** | 97.0 | 30.9 | 85.5 | **28.8** | **0.0** |

**The headline:** the generic-enrichment architecture **matches or beats** the
current hybrid arm on field detection and field typing, **with zero USCIS-specific
code** -- it is a clean, generalizable replacement for the heuristic layer on the
(a) field-extraction half. The few-shot helped relationship recall (b.cond 28.8,
the best of the three) but slightly hurt (a)-attribute fidelity.

### Opus 4.8 results (the chosen production model -- free in-env)

Same architecture, same enriched bundle, run on **claude-opus-4-8 via the local
CLI**. I-90, scored against the committed gold:

| Arm (I-90, claude-opus-4-8) | a.F1 | type | pdf_position | section_id | notable b |
|---|---:|---:|---:|---:|---|
| + enrichment, **no PDF** (bundle-only) | 98.5 | 96.2 | 0.0 | 0.0 | copy_to **100%** |
| **+ enrichment + PDF, no few-shot** | **98.5** | **96.9** | **99.2** | 0.0 | show_if **78.9%** |
| + enrichment + PDF + cross-form few-shot | 98.5 | 93.9 | 0.0 | 0.0 | copy_to **100%** |

Three things stand out vs the Gemini runs:

1. **Opus matches Gemini on detection/typing AND recovers `pdf_position` (99.2%,
   127/128)** -- a per-field attribute NO prior bake-off arm got (every Gemini/Claude
   arm scored position 0.0% by not propagating coords). Opus reads the enriched
   geometry + the PDF and passes the rects through. That is a clean (a)-attribute
   win the deterministic arm also can't beat.
2. **Bundle-only (NO PDF at all) already scores a.F1 98.5 / type 96.2 / copy_to
   100%.** The enriched AcroForm signals alone -- exact names, tooltips, tab order,
   row clusters -- carry enough for Opus to extract the form without pixels. The PDF
   mainly adds `pdf_position` and a few more conditionals. This is a strong, cheap
   fallback for forms where rendering is expensive or unavailable. (It is NOT the W-7
   case -- W-7 has no tooltips, so it still needs the PDF; see Q2.)
3. **The cross-form few-shot is inconsistent on Opus too** (helped copy_to, dropped
   position + sections). On both models the few-shot is a wash-to-slightly-negative
   for (a); its only repeatable benefit is some (b) relationship recall. Recommend
   making few-shot OFF by default and revisiting it as a (b)-only lever.

`section_id` is 0.0% on every Opus arm too -- the same broken-metric story (Q1);
Opus produced clean ids like the Gemini arms, just not the gold's idiosyncratic
strings. **Net: switching to Opus loses nothing and gains `pdf_position`; the
architecture conclusion is unchanged and if anything stronger.**

The `cost_usd_equiv` the CLI reports (~$3-4/form) is the API-equivalent figure for
reference; under the maintainer's subscription it is not metered per-token. The
CLI's `input_tokens` counter reads ~0 because the prompt is delivered through the
agent turn rather than a raw completion -- not a real measurement; ignore it.

**The most important finding is a correction to the bake-off's own premise:** the
claim that "the deterministic extractor owns schema-conformant `section_id`" does
**NOT generalize.** On I-90, **every arm including the old deterministic
extractor scores `section_id` 0.0%.** The 88.3% the deterministic arm posted was
**I-589 only** -- and it's an artifact of the I-589 gold schema having been authored
*by editing the deterministic extractor's own output*. `section_id` is graded by
exact string match against an internally-inconsistent, hand-authored gold; it is
**not a learnable convention**, so neither few-shot nor heuristics can "win" it on a
form they didn't seed. (Details + receipts in Q1.)

**Recommendation:** the thesis is **largely validated** -- retiring the USCIS
heuristic layer in favor of a generic-enrichment LLM pass is sound and loses
nothing measurable on (a). But the case for it does **not** rest on `section_id`
(that metric is broken), and it does not yet solve (b)'s hard custom-encoding keys.
See "Recommendation / path forward" at the end.

## What was built (reusable, committed)

All under `scripts/bakeoff/`, ASCII-only, pluggable model:

1. **`structural_enrich.py`** -- a **generic** (zero USCIS knowledge) enrichment
   pass over the existing `acroform_dump.py` output. Adds three signals, all
   derived mechanically:
   - **name-token decomposition** -- splits the XFA dotted path + leaf into tokens
     on the author's own delimiters (`P1_Line3a_FamilyName` -> `[P,1,Line,3a,
     Family,Name]`). Pure tokenization -- it does NOT map `P1`->`Part 1` (that's
     the heuristic treadmill the bead wants to retire); it just exposes the
     structure for the LLM to interpret.
   - **tab order** -- the page-then-reading-order (top-to-bottom, left-to-right)
     rank of each widget. This recovers logical sequence the bare name-list loses.
   - **visual-row clusters** -- widgets sharing a y-band on a page get one cluster
     id, so split questions (name -> family/given/middle; the 3 "Unit"
     checkboxes + apt-number box) are visible as a group to consolidate.
2. **`arm_llm_native.py`** -- the LLM-native arm. Feeds `[schema contract] +
   [anti-hallucination rule] + [optional cross-form few-shot] + [enriched field
   list] + [the PDF]` to the model. Flags: `--fewshot-truth OTHER.json`,
   `--no-pdf` (ablation), `--model`.

Both are throwaway research tools matching the bake-off's existing style; nothing
touches the live app (per the bead's integration note).

## Answers to the open questions (Q1-Q7)

### Q1 -- Can few-shot make the LLM match the `section_id` convention? **NO -- and the question is based on a false premise.**

This is the most consequential finding, so here are the receipts.

**The cross-form few-shot mechanism WORKS** -- the LLM faithfully imitated the
I-589 slug style when extracting I-90. Sample of what the few-shot arm produced for
I-90 sections: `part_1_info`, `part_1_mailing`, `part_3_biographic`,
`part_6_interpreter_address`, `part_7_preparer_signature`. These are clean,
consistent, sensible -- **arguably better than the gold standard.**

**But it scores 0.0% because the gold `section_id` is internally inconsistent
hand-authored noise, not a convention.** The I-90 gold mixes:
- `'Part 1 - Information About You'` (title-case, spaces, " - " separator)
- `'part_1_2_addresses'` (snake_case slug)
- `'7_3_preparer_s_phone_representation_and_signature'` (leading digit, apostrophe
  flattened)

No model can match those arbitrary strings by exact comparison -- there is nothing
to learn.

**And the deterministic layer does NOT actually win this, despite the bake-off's
claim.** Measured `section_id` accuracy, every committed I-90 arm:

| arm | I-90 section_id | I-589 section_id |
|---|---:|---:|
| old-extractor-heuristic | **0.0%** (0/131) | **88.3%** (68/77) |
| gemini35flash-hybrid | 0.0% | 0.0% |
| claude-hybrid | 0.0% | 0.0% |
| (my proto arms) | 0.0% | -- |

The deterministic arm's only `section_id` win is **I-589**, where it scores 88.3%
*because the I-589 gold schema was created by editing the deterministic extractor's
output* -- its section ids match by construction. On I-90 (gold authored
differently) the same deterministic code scores 0. So "schema-conformant
`section_id`" is a **ground-truth-seeding artifact**, not a capability of the
heuristic layer. **It is not a reason to keep the heuristics.**

Practical takeaway: if section ids matter downstream, the fix is a **stable
generated convention** (which the few-shot already produces) + accepting it as the
canon, OR a scorer that grades section *grouping* (which fields share a section)
rather than the exact id string. The current metric rewards whoever seeded the
gold and should not drive the architecture decision.

### Q2 -- What structural signal does the in-repo non-USCIS W-7 actually expose? (the 10-min probe -- done FIRST)

This **refines the bead's central finding.** The bead says I-589 names are "OPAQUE,
0 dotted paths." That's wrong on the dotted-path count. Measured across all three:

| signal | I-90 | W-7 | I-589 |
|---|---:|---:|---:|
| dotted XFA paths | 100% | **100%** | **100%** |
| bracketed `[n]` | 100% | 100% | 100% |
| **/TU tooltips present** | **100%** | **0%** | **100%** |
| semantic leaf names | rich (`P1_Line3a_FamilyName`) | **none** (`f1_01`, `c1_11`) | mixed (`PtAILine1_ANumber` AND `TextField1[8]`) |

The real cross-form variance is **(1) leaf-name semantics** and **(2) tooltip
presence** -- not dotted-path presence (all three are 100% XFA).

**W-7 is the decisive proof case for the thesis.** It exposes ONLY geometry (x/y) +
widget type + on-value + a purely positional name (`f1_23`, `c1_11`). **Zero
tooltips, zero semantic leaf names.** The only way to know what `f1_23` *means* is
to read the rendered page -- exactly what a multimodal LLM does and what no
name-parsing heuristic ever could. The USCIS heuristic parser would produce
**nothing** on W-7. This is the strongest single argument for the LLM-native
approach: it degrades gracefully to "read the page" when the machine-readable
layer is barren, where the heuristic degrades to "emit garbage / nothing."

W-7 has **no ground-truth schema** in the repo, so it stays qualitative (the bead
anticipated this). The enrichment renders W-7 cleanly (37 visual-row clusters over
69 fields) -- a usable bundle for an LLM, but unscored here.

### Q3 -- Which enrichment signals help vs noise? (partial ablation)

The enrichment as a bundle clearly **helps**: vs the baseline hybrid (same model),
the enriched no-few-shot arm improved **type accuracy 85.5% -> 96.9%** and **field
F1 97.0 -> 98.5** (fewer spurious FPs: 3 vs 7). I did not isolate each signal
individually (that's the full ablation the bead lists as a deliverable -- a
follow-up). The row-cluster + tab-order signals are the most likely contributors to
the typing/consolidation gains; a per-signal ablation is the obvious next
experiment.

### Q4 -- Will the LLM faithfully COPY exact widget names, or hallucinate? **Faithful -- no rehydrate needed.**

With an explicit anti-hallucination rule ("copy `name=` character-for-character"),
**`pdf_field_name` accuracy was 100.0% (131/131)** on every proto arm. The model
did not invent or normalize a single widget name. The name-reference+rehydrate
fallback the bead floats as a contingency is **not necessary** for gemini-3.5-flash
on a form this size. (Re-test on the 460-widget I-589 before generalizing.)

### Q5 -- Table / multi-entry consolidation from the bundle? (partial)

The few-shot arm's 7 "spurious" FPs were **not hallucinations** -- they were the 5
race checkboxes + 2 statement checkboxes emitted as separate fields where the gold
**consolidates** the 5 race boxes into one multi-option `p3_race` field (the single
matching FN). Identical consolidation-granularity pattern the bake-off flagged for
claude-hybrid. The **no-few-shot** arm consolidated better (3 FPs). So the bundle
*can* drive consolidation, but granularity is inconsistent and is the real
remaining (a)-side work. I did not test the I-589 tables (where claude-hybrid beats
gemini 7/9 vs 0/9) under the enriched bundle -- a follow-up.

### Q6 -- Model / cost / context-budget shape

I-90 (195 widgets, 7 pages) on gemini-3.5-flash:

| arm | input tok | output tok | wall |
|---|---:|---:|---:|
| baseline hybrid | 20.7K | 20.1K | ~2m17s |
| proto enrich (no shot) | 28.0K | 22.1K | ~2m |
| proto enrich + few-shot | 28.8K | 21.2K | ~2m |

The enrichment grows the field-list text **~+26%** (50.8K -> 64.2K chars) and total
input **~+35%**. Cheap and well within budget for I-90.

**Chosen model: claude-opus-4-8 via the local `claude` CLI (free in-env).** Schema
extraction runs in the maintainer's environment, where Opus is on the Claude Code
subscription (not metered), so cost is a non-issue for the production path; the
Gemini token economics above matter only for the kept-as-fallback Gemini path. Opus
completed every I-90 call in ~2-4 min single-shot and, as noted above, added
`pdf_position` no other arm recovered. The CLI's reported `cost_usd_equiv`
(~$3-4/form) and ~0 `input_tokens` are accounting artifacts, not the real in-env
cost (see "Opus 4.8 results").

The big-form chunking question (I-589 at 460 widgets, where gemini-3.1-pro **timed
out** in the bake-off) is **untested** and remains the real Q6 risk -- the enriched
bundle is larger, so chunking matters more, not less, on big forms. Whether Opus
completes the single-shot 460-widget call (and a chunking design if not) is the
explicit subject of the I-589 follow-up bead (**polyglot-pdf-7a9.11**).

### Q7 -- Where (if anywhere) does the deterministic pass still beat the LLM?

On measured metrics for I-90: **nowhere that holds up.** The deterministic arm's
apparent wins are:
- `section_id` -- a seeding artifact (Q1), 0% on I-90 anyway.
- nothing else: it scores a.F1 81.9 (vs proto 98.5), type 74.0 (vs 96.9), b.cond
  ~0 (vs 21-29).

The honest residual value of determinism is the **anti-hallucination anchor**: the
exact widget names come from PyMuPDF (`acroform_dump.py`), and the LLM copies them.
That layer **stays** -- the bead already says keep it. What retires is the
**interpretation** layer (`heuristic_hierarchy_parser.py` tooltip parsing +
`extractor.py` section-id/field-semantics), which on W-7 produces nothing and on
I-90 is beaten by the generic-enrichment LLM pass.

## Reproducibility

```
VENV=backend/.venv/Scripts/python.exe   # deps live in the main repo's venv
PYTHONPATH=. $VENV scripts/bakeoff/acroform_dump.py form-kits/i-90/form.pdf \
    --json scripts/bakeoff/outputs/i90_acroform.json

# PRODUCTION PATH -- claude-opus-4-8 via the local CLI (free in-env; the default):
PYTHONPATH=. $VENV scripts/bakeoff/arm_llm_native.py --pdf form-kits/i-90/form.pdf \
    --acroform scripts/bakeoff/outputs/i90_acroform.json \
    --out scripts/bakeoff/outputs/i90_opus_noshot.json
# bundle-only ablation (no PDF, still strong): add --no-pdf
# few-shot (off by default; (b)-only lever): add --fewshot-truth example_pdfs/i-589/i589_schema.json

# FALLBACK PATH -- Gemini SDK (metered; for hired help). Pass a gemini-* model:
PYTHONPATH=. $VENV scripts/bakeoff/arm_llm_native.py --pdf form-kits/i-90/form.pdf \
    --acroform scripts/bakeoff/outputs/i90_acroform.json \
    --model gemini-3.5-flash --out scripts/bakeoff/outputs/i90_llmnative_noshot.json
# control: the current-architecture hybrid arm (no enrichment), same Gemini model:
PYTHONPATH=. $VENV scripts/bakeoff/arm_gemini.py --pdf form-kits/i-90/form.pdf \
    --mode hybrid --acroform scripts/bakeoff/outputs/i90_acroform.json \
    --model gemini-3.5-flash --out scripts/bakeoff/outputs/i90_baseline_hybrid_rerun.json

# score any arm:
PYTHONPATH=. $VENV scripts/schema_score.py --draft <arm>.json --truth form-kits/i-90/schema.json
```

The Opus path needs the `claude` CLI logged in (subscription auth); the Gemini path
needs `GEMINI_API_KEY`. The backend is auto-selected by the `--model` prefix
(`claude*`/`opus*` -> CLI, `gemini*` -> SDK). Outputs are gitignored (regenerable),
per the bake-off's existing convention. Temperature 0.0; the scorer is
deterministic.

claude-opus-4-8 as the model. The paths are now tracked under epic
**polyglot-pdf-7a9**, research-first:

1. **Adopt the generic-enrichment LLM pass as the authoring engine; retire the
   USCIS interpretation heuristics.** Keep `acroform_dump.py` (the exact-name
   anchor). Model: claude-opus-4-8 via the local CLI (free in-env); Gemini kept as
   fallback. -> **polyglot-pdf-7a9.12** (BLOCKED BY the research beads + 7a9.9;
   reconciles with the older 7a9.8 "fused pipeline" bead, which this reshapes).

   **polyglot-pdf-7a9.13** (ready now; independent of the others).
3. **Per-signal ablation** (Q3) -- drop any enrichment signal that's noise; trim
   `structural_enrich.py` to what earns its place. -> **polyglot-pdf-7a9.10**
   (research, ready now).
4. **I-589 big-form validation** (Q5/Q6) -- tables + chunking + does Opus complete

5. **The remaining real work is (b) + consolidation**, not (a): the custom

6. **When adopted, add the pass as a scored bake-off arm** (manifest + harness), per

### Decisions I made autonomously (and why they were mine)

- **Prototyped first on gemini-3.5-flash, THEN re-ran on Opus 4.8** once the
  maintainer chose the model. Holding the model = the existing `gemini35flash-hybrid`
  arm gives the clean control isolating the architecture; Opus confirms the chosen
  production model loses nothing (and gains `pdf_position`). Both kept in the doc.
- **Auto-dispatched the model backend by name prefix** (`claude*` -> local CLI,
  `gemini*` -> SDK) rather than a separate flag -- smaller surface, one `--model`
  knob, reversible. An internal-structure call.
- **Made few-shot OFF by default** -- on both models it was wash-to-negative for (a);
  recommending it only as a (b)-only lever to revisit. A noted default, reversible.
- **Used a cross-form few-shot (I-589 exemplar when scoring I-90)** -- using the test
  form's own gold would be training on the test set and would invalidate the
  section_id result. A methodology-correctness call.
- **Filed the paths forward as beads with research-before-implementation
  dependencies** and chose the split (2 research + 1 implementation + 1 product
  decision) rather than one big bead -- bead-shaping is the orchestrator's call per
  the escalation doctrine; the section_id metric is filed as a DECISION bead because
  it is a genuine product call (yours), not something I should decide.
- **Reconstructed the research framing from the bead + committed bake-off** because
  the cited proposal doc is not in the repo. Noted at the top so you can correct it.
