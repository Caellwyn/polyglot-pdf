# i-90 P0 baseline numbers (bd polyglot-pdf-h76m.1)

Recorded 2026-07-04 as part of P0.1 of the schema-v2 epic
(`polyglot-pdf-h76m`; plan: `~/.claude/plans/rustling-discovering-hearth.md`,
maintainer-machine-local).
These are the "before anything changes" reference numbers the epic's later
gates compare against -- specifically the P6.1 exit criterion "migrated i-90
lint-clean + roundtrip fill == P0 baseline".

Both commands run from the repo root against the shipped i-90 form kit at
dev commit `b7c291fa` (the P0.1 worktree base), using the backend venv
python.

## Round-trip fill (scripts/bakeoff/roundtrip_fill.py)

```
python scripts/bakeoff/roundtrip_fill.py \
  --schema form-kits/i-90/schema.json --pdf form-kits/i-90/form.pdf
```

| Metric | Baseline |
|---|---|
| CHOICE (checkbox+radio) fill success | 100.0% (28/28) |
| TEXT fill success | 100.0% (108/108) |
| CHOICE value-convention (opt.value == widget leaf) | 73.0% (54/74) |
| value-convention violations | 20 |

The 20 value-convention violations are all on three fields --
`p3_ethnicity` (2), `p3_eye_color` (9), `p3_hair_color` (9) -- and every one
is a SEMANTIC value (`hispanic_latino`, `blue`, `bald`, ...) instead of the
schema-contract widget leaf (`P3_checkbox6[0]`, ...). In other words the
hand-curated i-90 kit already uses semantic option values on those fields,
which is the direction schema v2 standardizes (P1.1 semantic slugs). Fill
still succeeds for them because pdf fill keys on `option.pdf_field_name`,
not `option.value`. Expectation: this 73.0% number is measured against the
CURRENT (v1, leaf-convention) contract; after migration the convention
itself changes, so the load-bearing invariants to hold at P6.1 are the two
100% fill-success rows, not the leaf-convention percentage.

## Schema score (scripts/schema_score.py, self-identity)

`schema_score.py` scores a draft against a ground truth, so as a baseline we
score the shipped kit against ITSELF. That pins the field inventory and
gives the trivially-perfect reference row; the useful content is the counts.

```
python scripts/schema_score.py \
  --draft form-kits/i-90/schema.json --truth form-kits/i-90/schema.json \
  --label "i-90 self-identity baseline"
```

| Inventory item | Count |
|---|---|
| fields (TP at 100% detection) | 132 |
| fields with options | 26 |
| fields with validation | 25 |
| fields with pdf_position | 128 |
| show_if conditions | 19 |
| controls_fields entries | 13 |
| conditional_fields (legacy) | 12 |
| conditional_logic entries | 16 |
| conditional_behavior entries | 16 |
| copy_to links | 4 |
| parts | 8 |
| sections | 16 |

All precision/recall/accuracy rows read 100% by construction (self-identity);
they are omitted above. After P6.1 migration, re-running schema_score with
`--draft <migrated> --truth <original>` will NOT be a like-for-like check for
the intentionally-renamed machinery (e.g. controls_fields is deleted by
design); the migration bead's own equivalence tests are the gate there. The
inventory row that must survive migration unchanged is the field count (132)
and the show_if count (19, possibly re-expressed as composite groups).

## Vector suite

The dual-evaluator semantics themselves are pinned by
`shared/conditional-vectors.json` + the two runners
(`frontend/src/schema-forms/utils/validation.vectors.test.ts`,
`schema-editor/src/utils/conditionalVisibility.vectors.test.ts`), landed in
the same PR as this note. 65 vectors; 3 pin per-evaluator DIVERGENCES that
exist today (comma-split gate keyed on `group_kind` in the runtime vs
`type=checkbox + options[]` in the editor; FieldValue unwrapping is
runtime-only). Those divergence pins are the measured starting line for the
P3.1 convergence work.

## P6.1b migration note (2026-07-06, bd c5r8)

The i-90 kit was migrated to v2 at P6.1b. The two load-bearing fill rows above
(100% CHOICE 28/28, 100% TEXT) hold on the migrated schema; the leaf-convention
row intentionally drops to 0% (v2 re-mints option values to semantic slugs, as
foretold above). ONE deliberate, maintainer-approved live-behavior change: the 3
Part-4 accommodation checkboxes (p4_checkbox1a/b/c) had a DEAD v1 show_if
(is_checked on a radio -- always false, so they never showed); the migration
rewrites it to is_not_empty, so they now show once the Part-4 Yes/No is answered
(the author's intent). Pinned by schema-editor/src/utils/i90MigrationEquivalence.test.ts.
