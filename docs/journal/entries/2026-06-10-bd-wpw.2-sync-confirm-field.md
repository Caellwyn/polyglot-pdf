## Trigger

WS-E part 2 of the voice round-trip hardening epic (`polyglot-pdf-wpw`), and the
confirm-reliability fix the live voice harness flagged as the actual demo-blocker.
`confirm_field` was **fire-and-forget**: `_handle_confirm_field_tool` sent the
frontend a `confirm_field` WS message and immediately returned `success:true`,
never learning whether the frontend actually recorded the confirmation. The
frontend already KNEW when a confirm could not take (its 0y7 loop-breaker gates on
the field value), but that signal stayed client-side. So when model 3.1 calls
`confirm_field` on a field it never filled (the documented 3.1 confirm-without-fill
skip), the backend told Gemini "confirmed" and the user's value was silently lost
-- Gemini moved on with an empty field.

Bundled with `polyglot-pdf-p84m`: the callback-error log redaction that Codex (P1)
and fresh-eyes both flagged on PR #138 -- the same except blocks whose envelope
shape wpw.2 reuses, so they ship together (disjoint surfaces; the p84m work is in
`live_ai_gemini.py`/`dev_file_logger.py`, wpw.2 in the coordinator/callback/FE).

## What shipped

**wpw.2 -- synchronous confirm round-trip.** `confirm_field` is now a coordinator
round-trip like `next_field_hint`:

- `request_coordinator.py`: new `CONFIRM_REQUEST_TIMEOUT` sentinel +
  `request_confirm_field(field_id, confirmation_method)` (sends a `confirm_field`
  message with a `request_id`, blocks 2s, keyed slot per bd bxw so it can't clobber
  the concurrent next-field request) + `handle_confirm_field_response`.
- `callback_handler.py`: `_handle_confirm_field_tool` awaits the ack and branches.
  **The frontend is the source of truth** (it owns all field state -- the
  stateless-backend invariant), so the backend relays the FE's `{recorded, reason}`
  rather than re-checking via `request_form_state`. On `recorded:true` it takes the
  existing success path (request next-field hint, log the confirmation). On
  `recorded:false` (reason `"no_value"`) OR `CONFIRM_REQUEST_TIMEOUT` it returns
  `success:false` via `_confirm_failure_response`, which carries the WS-C2
  error-envelope keys (`status`/`retryable`/`error`) so Gemini reads it as a real
  failure and re-asks IN-BAND, and does NOT request a next-field hint (no advance).
  A timeout reads as not-confirmed + keep-going (never a successful confirm) --
  same sentinel discipline as `HINT_REQUEST_TIMEOUT`. The confirmation is logged
  only when actually recorded.
- `form_filling_service.py` + `websocket_routes.py`: `handle_confirm_field_response`
  delegation + the `confirm_field_response` WS dispatch (mirrors
  `next_field_hint_response`).
- `webFormConnection.ts`: `sendConfirmFieldResponse` acks `{recorded:false,
  reason:"no_value"}` on the unconfirmable path (alongside the existing 0y7
  re-prompt/onError loop-breaker, kept as a client-side belt-and-suspenders) and
  `{recorded:true}` on the success path. `reason` is a fixed token, never the field
  value (PII-safe). A legacy fire-and-forget `confirm_field` (no `request_id`)
  no-ops the ack for backward compatibility.

**Design note (defended):** `_tool_error_envelope` is NOT imported from the adapter
-- the failure body is built inline in `_confirm_failure_response` with the same
key set. Reason: keep the services layer from depending on adapter internals (a
`_private` helper) and from pulling the heavy genai SDK module in at import time.
The key set is kept in sync with WS-C2 deliberately.

**p84m -- callback-error log redaction.** The leak was the UNCONDITIONAL terminal
write in `DevFileLogger.log_error`, which interpolated `error_message` (= `str(e)`,
and an exception string can embed the field value the callback was handling) and
ran regardless of `self.enabled` -> reaching Cloud Logging in production. Fix at the
sink: the always-on terminal line now carries only the `error_type` (a class name,
never PII); the full message + context stay in the dev-gated `_write_to_file`
entry. Additionally, the two adapter tool-callback `except` blocks gate their
verbose `traceback.print_exc()` (which prints `str(e)`) behind
`DEV_LOGGING_ENABLED`, and the model_turn.parts block drops `error=str(e)` from its
structlog line (matching the event.tool_call block) -- so production never receives
the exception text from any of the three vectors (terminal sink, traceback print,
structlog field).

**Tests (red-first).** Coordinator: `request_confirm_field` resolves recorded/
not-recorded acks, returns the sentinel on timeout, cleans its slot, and does not
clobber a concurrent next-field request. Callback: an empty-field confirm now
returns `success:false` (was `success:true` -- the gap), a timeout returns
`success:false` + "do not assume complete", and a failed confirm is not logged.
Frontend: the FE sends `recorded:false/reason:no_value` on the unconfirmable path
and `recorded:true` on success. p84m: a PII sentinel in `str(e)` never reaches the
unconditional terminal write -- proven RED against the old leaky sink, GREEN after.
265 backend + 202 frontend tests pass.

## Lessons

- **A "fire-and-forget" send that the model treats as authoritative is a silent
  data-loss bug.** The frontend had the right signal all along; the fix was to make
  the existing round-trip carry it back so the model's confabulation becomes an
  in-band, self-correcting failure instead of a lost value.
- **The PII leak had three vectors in the same except block**, not one: the
  dev-logger terminal sink, the `traceback.print_exc()`, and the structlog
  `error=str(e)`. Fixing only the sink (the bead's literal text) would have left
  two open; the bead's "str(e) in the except blocks" scope correctly covered all
  three. (Generalizes -- noted on `docs/standards/hipaa-pii-policy.md`.)
