## Trigger

Phase 1 of the spec-driven test epic (`polyglot-pdf-uov`). The highest-value
disabled frontend suite: `SchemaFormStateManager` owns ALL client form state
(the client half of the stateless-backend invariant). The test was parked as
`schemaFormState.test.ts.NEEDS_SECTION_REFACTOR` because it referenced the dead
part-based API (`currentPartId` / `completedParts` / `getCurrentPartNumber` /
`extractPartFields` / `switchToPart`); the source had been renamed to the
section vocabulary. The bead required deriving the SPEC and checking each old
assertion against it -- a rewrite, not a mechanical rename.

(Getting here also required first fixing the collision guard -- bd
polyglot-pdf-6hr -- which had frozen this bead behind an undeclared active claim.
That fix merged in PR #130; the live `_surface_collision` check for uov.4 then
returned None and the claim went through, the real end-to-end proof of 6hr.)

## What shipped

A spec-derived `frontend/src/schema-forms/state/schemaFormState.test.ts` (54
tests), re-enabled (renamed off `.NEEDS_SECTION_REFACTOR`). Derived the contract
from the source + `docs/components/schema-forms.md`, then wrote assertions to it.

Key corrections over the old part-based test (each verified against the source,
not assumed):

- **Migration direction was BACKWARDS in the old test.** `load()` migrates the
  legacy keys FORWARD: `currentPartId -> currentSectionId` and `completedParts ->
  completedSections` (source lines 117-127). The old test asserted the reverse
  (`currentSectionId -> currentPartId`). Rewrote the three migration tests to the
  real direction, including the "prefer existing currentSectionId" case (the
  migration only fills a MISSING section id).
- **Handshake payload is SECTION-scoped, not parts.** `getHandshakePayload`
  returns `section_number` = current SECTION `.order`, `section_label` = current
  SECTION `.label`, `total_sections` = `schema.sections.length`. With `init()`
  seeding the first section (section-1a, order 1, label 'Name'), the fixture now
  expects section_number=1, section_label='Name', total_sections=4 -- NOT the old
  part-derived 'Personal Information' / 3. `parts[]` is kept in the fixture only
  to prove the manager ignores it for nav + handshake.
- **Renamed methods:** `getCurrentSectionNumber`, `extractSectionFields`,
  `switchToSection`; `getPreviousSpokenNames` collects over `completedSections`.
- Kept the still-correct tests (FieldValue wrapping, JIT tracking, save/load
  round-trip, edges), updating their part-keyed fixtures to section keys.

## Findings

**None.** Every spec assertion passes against the current source -- the state
manager already conforms to its documented section-based behavior, so there was
no defect to file or `xfail`. The "rot" was entirely in the parked test, not the
code. (This is the good outcome of the spec-driven approach: deriving the spec
either finds a bug or confirms conformance; here it confirmed.)

## Decisions (defended)

- **Rewrote rather than renamed.** The migration tests had inverted semantics; a
  mechanical part->section rename would have asserted a migration the source does
  not perform. Verified the real direction in `load()` before writing.
- **Refreshed `docs/components/schema-forms.md`** (bumped `Last updated`, added
  journal pointer). It was flagged stale and I re-verified its claims against the
  code by writing this spec; its content was already accurate (section nav +
  forward migration), so this is a freshness re-stamp, not a content fix.
