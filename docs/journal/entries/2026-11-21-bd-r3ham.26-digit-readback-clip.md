## Trigger

In the 2026-11-20 `gemini-3.8-live` benchmark, a mobile number asked right
after a similar daytime number was stored as a blend of the two (`0197` for
`0297`, after `0184`). Cloud STT heard the model's VOICE read back the
daytime number while its transcript said something else -- the same
speech-head attractor that moved name spelling to the `name_spellback` clip
(bd 0rpu / 22h1f). The maintainer approved moving number read-backs to that
clip, with the condition that digits are spoken in the session language
(hypothesis 1 of bd r3ham.25).

## What shipped

- **Model instructions.** `DTI_SPELLBACK_SI_ADDENDUM` and
  `SPELLBACK_TOOL_DECLARATION` now route identifier numbers (phone, ZIP,
  A-number, SSN/tax ID, account/case/document numbers) to `name_spellback`;
  the old "numbers are unaffected, read them yourself" exemption is gone.
  Dates stay out of scope. DTI WORKFLOW step 3's number rule now yields to a
  later instruction, like its name rule already did.
- **Digit clip language gate** (`spellback_tts.resolve_spellback_voice(...,
  for_digits=True)`, chosen when the value contains a digit). The clip
  already voiced each character as its own comma-separated token; what was
  missing was the language rule. A digit clip uses the SESSION locale only:
  an unmapped language, a locale the voice listing shows no voice for, or an
  unavailable listing raises `SpellbackLanguageUnavailable`.
- **Fallback contract.** The route answers 406; the client already forwards
  any non-OK status as `tts_http_<status>`; the tool maps `tts_http_406` to a
  new `read_back_yourself` response telling the model to read the STORED
  digits itself, one at a time, in the session language, never in English.
  No frontend change.
- A failed voice listing is no longer cached for the process lifetime
  (digits fail closed on it, so a cached blip would have disabled every digit
  clip on the instance).
- TTS-only live check `scripts/spikes/check_digit_spellback_tts.py` + findings
  (`digit_spellback_tts_findings.md`): digits PASS in Spanish, Mandarin and
  Russian (10/10 separate spoken digits on the waveform, in-language STT, no
  English digit word); Urdu, Persian and an unmapped language get no digit
  clip. A requested name leg (JOSE) confirmed each frame is in the session
  language; whether Spanish says jota/ese is not decidable from STT (clip
  saved for a human listen). Spend about $0.062 TTS + STT, zero Live-model
  (the $0.05 cap was extended by ~$0.013 for the name leg, on request).

## Decisions

- **Tool keeps the name `name_spellback`.** A rename touches the sim harness,
  log analysis and several docs; this bead could not measure whether the name
  hurts compliance (no Live-model spend). Measuring it is bd r3ham.29.
- **Names keep the en-US clip for an unmapped language.** Names are stored in
  Latin characters, and the alternative (the model speaking a spelling) is
  the measured 0rpu defect. Only digits lose the English fallback.
- **No phone grouping.** A dash in a stored phone value is voiced as the
  locale's word for it, as before; group pauses were optional in the bead.
- **406, not 422,** because FastAPI emits 422 by itself for a malformed body.

## Lessons

- **A voiceless locale does not fail -- it speaks English.** `ur-PK` lists no
  voice, yet a synthesize call for it with no voice name returns audio in an
  English voice (Urdu STT heard "five zero"); `fa-IR` returns 400. So
  "unmapped language" was only half the English-fallback gap; the other half
  was the ladder's own last rung. The gate checks the voice listing. Names,
  intro and notice clips still take that rung for Urdu/Persian (bd r3ham.27).
- **STT cannot measure "separate digits".** Inverse text normalization turns a
  run of spoken digit words into one numeral and merges repeats, so the first
  verdict failed every language for a recognizer artifact. Counting voiced
  segments in the waveform answered it for free (10/10 in each language), and
  STT kept the job it can do: which language the digits were spoken in.
