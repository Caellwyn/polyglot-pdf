## Trigger

Gate 2 of the secretary research (epic jnjj), gated on Gate 1 RECALL (jnjj.26,
"feasibility promising", PR #240). The `ask_secretary` call is BLOCKING -- the
principal (live voice model) waits mid-conversation -- so the question is whether a
cached flash-lite lookup is fast enough for live conversation UX. Two parts: (a)
establish Gemini context-caching facts from authoritative sources; (b) measure the
real round-trip and record a GO/KILL.

## What shipped

`backend/scripts/probe_secretary_latency.py` (reuses the Gate-1 renderer + corpus)
and `scripts/spikes/secretary_latency_findings.md`.

**Part (a) caching facts (authoritative -- gemini-docs MCP + live pricing/caching
pages; the vendored `docs/genai_docs/` is Live-API-only and had no caching content,
so recorded from the next authoritative tier per the bead's fallback order):**
- The secretary's ~8.4k-token value-free static catalog clears both the explicit (2048) and
  implicit (~1-2k) minimums comfortably.
- flash-lite supports caching: $0.10/M input, $0.01/M cached (90% off), $0.40/M
  output, $1.00/M/hr storage. Explicit cache CREATE latency ~0.78s (a one-off direct
  `caches.create()` test, not in the committed verdict artifact -- informational,
  since explicit is deferred to jnjj.41).
- **DECISION (maintainer): implicit caching now; explicit deferred to scale (~100
  concurrent users) -> bd jnjj.41.** Implicit is free/automatic; explicit's per-hour
  storage + lifecycle is overhead the input-discount does not pay back at low
  concurrency.

**Part (b) latency -- VERDICT: CONDITIONAL GO.** Full-corpus run (n=49/arm, ALL 6
tiers, value-free static catalog ~8.4k + values tail ~1.6k, retried=0, with a
committed PER-CASE CSV): **median ~0.95s, p90 ~1.2-1.4s** -- conversational -- BUT a
**heavy unpredictable tail**: 7.2s this run, 20.2s an earlier run (retried=0, not
outage). Per the per-case CSV the tail is only PARTLY cache-related (one run's spike
was a cache miss, another's a cache hit) and not tier-tracked -- cheap-model
variance. A multi-second blocking pause is a real UX failure, so the median-fast
lookup must ship WITH a timeout + graceful filler (bd jnjj.43), not raw. Structural
findings hold: implicit caching hit **96-98%** (zero setup, on the value-free prefix
-- the prefix/tail split caches correctly) -- the cost lever works -- and uncached vs
implicit median latency is ~the same, so **implicit caching is a COST lever, not a
latency one**. (METHOD: SUPERSEDES an earlier n=12 run that sampled only the easy
tiers and hid the tail -- the Codex finding below.)

## The outage + the model-fallback resilience

At measurement time `gemini-2.5-flash-lite` (the target) was in a sustained,
widely-reported (Reddit) **503 UNAVAILABLE** outage -- intermittent, flash-lite-
generation-specific (the sibling `gemini-2.5-flash` answered ~0.67s; flash-lite
`caches.create()` worked; both confirm it was not an account/key/region issue).
Early runs were OUTAGE-CONTAMINATED (~3-6s, but a bare 1-token prompt also took
3-6s, so the slowness was the degraded model, not the ~9.5k payload) and NO verdict
was recorded off them.

This motivated a **probe-level model fallback chain** (2.5-flash-lite ->
3.1-flash-lite -> flash-lite-latest, all within the Gemini BAA), which produced the
clean verdict number on `gemini-3.1-flash-lite` (the target 2.5-flash-lite was
intermittently 503). A sound same-tier proxy for the MEDIAN (both lite models median
sub-second). The TAIL is NOT a single-model artifact: multi-second spikes reproduced
on 3.1-flash-lite (7.2s, committed run) AND on 2.5-flash-lite itself (an 8.9s call
before it 503'd out) -- a real cheap-model-tier property. Re-confirm on a fully-
healthy 2.5-flash-lite for a clean target number, but DESIGN for a heavy tail
regardless (cheap models have heavy tails; outages recur), hence the guard bd
jnjj.43. The
same model-fallback resilience for the PRODUCTION path (`TextAIGemini`) is bd
jnjj.42 (P2).

## Codex review (PR #245)

Round 1 returned 3 P1 findings -- all valid and all material to the verdict
(triaged as blockers, fixed, and the measurement RE-RUN):
1. The "static" catalog embedded per-user values (`render_secretary_context`
   emits `value=..|shown=..`), so it was NOT a stable cacheable prefix. Fixed:
   added `render_static_catalog()` (value-free) + `render_values_tail()` and split
   prefix/tail; the cached prefix is now genuinely session-invariant (cache still
   hits 96-98%).
2. Retry backoff was excluded from the timed latency. Fixed: the probe now records
   a retry-inclusive `blocked` latency alongside the clean `call` time -- the honest
   blocking-pause number for the gate.
3. `--n 12` sampled only the first (easy/aliasing) tier block, hiding the tail.
   Fixed: stratified sampling across all 6 tiers; the verdict run uses the full
   49-query corpus. **This is what surfaced the heavy tail and turned a naive GO
   into the CONDITIONAL GO above** -- the review materially improved the finding.

Round 2 returned 4 more P1 findings (Codex looked deeper at the corrected probe);
all fixed:
4. `--n` default was still 12 (a re-run could re-hide the tail). Now defaults to 0
   = FULL corpus; a small n is documented as smoke-only.
5. Unknown `--arms` (a typo) silently ran as implicit. Now validated -> fail fast.
6. The artifact only had aggregates, so the "spikes not tier/cache-correlated"
   claim was not auditable. Now persists a PER-CASE CSV (case_id, tier, call_s,
   blocked_s, cached_tokens, retried). **Looking at the rows CORRECTED the claim:**
   the tail is only PARTLY cache-related (a miss spiked one run, a hit another) --
   the review's "make it auditable" finding caught an overstatement.
7. The model resolver only fell back on 5xx; a 404/429 on a fallback ID would
   abort. Now continues on 404/429 (availability) while still failing on auth/config.

I hit the Codex loop ceiling (MAX_REVIEW_ROUNDS=2) at round 2. The round-2 findings
were all valid + quick, so they were fixed; verification of the fixes routed to the
Opus-4.8 fallback reviewer (the reviewer-of-last-resort when the Codex loop is
exhausted) rather than a 3rd Codex round.
