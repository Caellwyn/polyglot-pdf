## Trigger

WS-E part 3 of 3 (the post-demo quality slice of the voice round-trip hardening
epic `polyglot-pdf-wpw`). The client-side validation of AI-applied values had been
**disabled** in `webFormConnection.handleFormUpdated` -- a commented-out
`validateField` block with the note "Frontend validation temporarily disabled --
backend handles validation." That left the client, which OWNS all field state (the
stateless-backend invariant), applying whatever value the model sent: a non-existent
enum option, a malformed SSN/A-Number, an over-length string all landed in state
unchecked. The backend does validate in `_handle_update_form_fields_tool`, but the
client is the authoritative store of its own field values, so a client-side gate is
the correct defense-in-depth layer -- and it can refuse the apply outright, which the
backend (stateless) cannot.

FE-only and independently revertable per the finalized plan (2026-06-09).

## What shipped

**Enum validation in `validateField` (`schema-forms/utils/validation.ts`).** Added
option-membership (enum) checking: for an option-backed field (`select`/`radio`/
checkbox groups) a non-empty value must be one of `field.options[].value`. This runs
**independently of `field.validation`** -- hoisted above the early
`if (!field.validation) return null` -- because option-backed fields frequently carry
no `validation` block at all (the option set itself IS the constraint). Array values
(checkbox groups) are validated member-by-member. The error message is built from
`field.name` + the constraint phrasing, never the rejected value.

**Re-enabled client-side validation of AI-applied values
(`webFormConnection.ts`).** A new `applyAiValueWithValidation(field, value)` helper
runs `validateField` before an AI value lands: valid -> applies as `confirmed:false`
(unchanged behavior, still requires explicit `confirm_field`); invalid -> SKIPS the
apply and routes a corrective prompt to the model. Wired into all three AI-fill apply
sites: `handleFieldUpdate` (the `field_update` path -- every value is an AI fill) and
both loops of `handleFormUpdated` (the `form_updated`/JIT path -- only `isApplied`
values are validated; a state echo writes through unchanged, since re-validating an
echoed prior value would falsely re-reject it).

**Corrective feedback routed via the proven channel.** The feedback goes back to the
model through `completion_message` -> `service.send_prompt(...)` -- the same channel
the 0y7 unconfirmable loop-breaker uses, which actually reaches Gemini in-band. NOTE:
the pre-existing `dependency_error` send is a **dead channel** -- the backend does not
handle that message type (it falls through to `unknown_control_message_type` + an
`error` reply), so it never reaches the model. The corrective message carries only the
field's spoken name + the schema constraint -- NEVER the rejected value (PII-safe, the
p84m principle; `validateField`'s messages are value-free by construction).

**Per-field loop-breaker.** Mirroring the 0y7 unconfirmable breaker: count consecutive
rejects of the same field; prompt on the first reject and then once per
`VALIDATION_REJECT_LIMIT` (2), capped at `VALIDATION_REJECT_REPROMPT_CAP` (3) total --
so a model that keeps re-sending the same bad value cannot spin the session (prompts
fire at rejects #1, #2, #4, then silence). Both counters reset when a value for the
tracked field validates (a good value lands) and on (re)connect / section switch
(alongside the existing 0y7 resets).

**Tests (red-first).** `validation.test.ts`: enum accept/reject, enforced with no
`validation` block, empty-optional is not an enum error, required-vs-enum precedence,
array member-by-member, and a PII assertion (the error never echoes the value).
`webFormConnection.aivalidation.test.ts` (new, mirrors `confirmloop.test.ts`): a valid
enum value applies; a bad value does NOT apply (asserted via the `onFieldUpdate`
callback, which fires only for landed values -- the AI path holds values in in-memory
state, not sessionStorage) and prompts the model; the rejected value never appears in
ANY sent message; an unconstrained field passes through; the prompt cap holds over 50
rejects (exactly 3); a later valid value lands and resets the streak. 220 frontend
tests pass (was 202).

## Lessons

- **`dependency_error` is a dead FE->backend channel.** The frontend has sent
  `dependency_error` for locked-field rejects for a while, but the backend never
  registered a handler for it -- it logs `unknown_control_message_type` and replies
  `error`. Any "route this back to the model" work must use `completion_message`
  (-> `send_prompt`), the channel the loop-breakers already prove works. (Filed as a
  follow-up consideration -- the locked-field path may want the same fix.)
- **Client-side validation is not redundant with backend validation here.** Because
  the client is the authoritative store (stateless backend), the client gate can
  *refuse the apply* -- a strictly stronger guarantee than the backend's tool-response
  validation, which can only tell the model after the fact.
