## Trigger

WS-E part 3 of 3 (the post-demo quality slice of the voice round-trip hardening
epic `polyglot-pdf-wpw`). The client-side validation of AI-applied values had been
**disabled** in `webFormConnection.handleFormUpdated` -- a commented-out
`validateField` block with the note "Frontend validation temporarily disabled --
backend handles validation." That left the client, which OWNS all field state (the
stateless-backend invariant), applying whatever value the model sent: a non-existent
enum option, a malformed SSN/A-Number, an over-length string all landed in state
unchecked. The backend does validate in `_handle_update_form_fields_tool`, but the
client is the authoritative store of its own field values, so a client-side gate is
the correct defense-in-depth layer -- and it can refuse the apply outright, which the
backend (stateless) cannot.

FE-only and independently revertable per the finalized plan (2026-06-09).

## What shipped

**Enum validation in `validateField` (`schema-forms/utils/validation.ts`).** Added
option-membership (enum) checking: for an option-backed field (`select`/`radio`/
checkbox groups) a non-empty value must be one of `field.options[].value`. This runs
**independently of `field.validation`** -- hoisted above the early
`if (!field.validation) return null` -- because option-backed fields frequently carry
no `validation` block at all (the option set itself IS the constraint). Array values
(checkbox groups) are validated member-by-member. The error message is built from
`field.name` + the constraint phrasing, never the rejected value.

**Re-enabled client-side validation of AI-applied values
(`webFormConnection.ts`).** A new `applyAiValueWithValidation(field, value)` helper
runs `validateField` before an AI value lands: valid -> applies as `confirmed:false`
(unchanged behavior, still requires explicit `confirm_field`); invalid -> SKIPS the
apply and routes a corrective prompt to the model. Wired into all three AI-fill apply
sites: `handleFieldUpdate` (the `field_update` path) and both loops of
`handleFormUpdated` (the `form_updated`/JIT path). Every value that REACHES an apply
on these channels is an AI change (applied_fields named it, or the legacy
no-applied_fields path sent it and it differs from the current value); a pure
unchanged state-echo is `continue`d earlier by the `limitToApplied`/`shouldUpdate`
guards, so the apply validates unconditionally (Codex round-1 fix -- see below;
an earlier `isApplied`-only gate left the legacy `on_form_update` path unvalidated).

**Corrective feedback routed via the proven channel.** The feedback goes back to the
model through `completion_message` -> `service.send_prompt(...)` -- the same channel
the 0y7 unconfirmable loop-breaker uses, which actually reaches Gemini in-band. NOTE:
the pre-existing `dependency_error` send is a **dead channel** -- the backend does not
handle that message type (it falls through to `unknown_control_message_type` + an
`error` reply), so it never reaches the model. The corrective message carries only the
field's spoken name + the schema constraint -- NEVER the rejected value (PII-safe, the
p84m principle; `validateField`'s messages are value-free by construction).

**Per-field loop-breaker.** Mirroring the 0y7 unconfirmable breaker: count consecutive
rejects of the same field; prompt on the first reject and then once per
`VALIDATION_REJECT_LIMIT` (2), capped at `VALIDATION_REJECT_REPROMPT_CAP` (3) total --
so a model that keeps re-sending the same bad value cannot spin the session (prompts
fire at rejects #1, #2, #4, then silence). Both counters reset when a value for the
tracked field validates (a good value lands) and on (re)connect / section switch
(alongside the existing 0y7 resets).

**Tests (red-first).** `validation.test.ts`: enum accept/reject, enforced with no
`validation` block, empty-optional is not an enum error, required-vs-enum precedence,
array member-by-member, and a PII assertion (the error never echoes the value).
`webFormConnection.aivalidation.test.ts` (new, mirrors `confirmloop.test.ts`): a valid
enum value applies; a bad value does NOT apply (asserted via the `onFieldUpdate`
callback, which fires only for landed values -- the AI path holds values in in-memory
state, not sessionStorage) and prompts the model; the rejected value never appears in
ANY sent message; an unconstrained field passes through; the prompt cap holds over 50
rejects (exactly 3); a later valid value lands and resets the streak.

**Review-round fixes (fresh-eyes + Codex round 1, all adopted).** The round-1
review surfaced 6 genuine blockers, all fixed on-branch with added tests (229
frontend tests pass, was 202 at open):

1. **Top-level constraint fields bypassed (Codex P1).** Many generated schemas
   (e.g. form-kits/i-90 -- dozens of text fields) carry `max_length`/`min`/`max`
   at the FIELD level with no `validation` block; the early `!field.validation`
   return skipped them, so an over-length AI value still landed. Fixed by folding
   the top-level fields into an `effectiveRules` object (explicit `validation`
   wins on conflict) and running the rules-based checks whenever EITHER source has
   constraints.
2. **String-option schemas false-rejected every value (Codex P1).** Some schemas
   use plain-string options (`options: ["Agender", ...]`, e.g.
   adult_intake_demo_schema.json -- the shape the backend `List[str]` normalizer
   emits); `validateOptionMembership` read `opt.value` (undefined for strings),
   building an all-`undefined` allowed set that rejected EVERY valid value. Fixed
   with an `optionValue()` helper handling both the `{value}` object and plain
   -string shapes.
3. **Legacy `on_form_update` path unvalidated (Codex P1).** The `isApplied`-only
   gate let a value with no `applied_fields` (the legacy adapter path) write
   through unvalidated. Fixed by validating every value that reaches an apply
   (pure echoes are already `continue`d earlier), so the legacy path is covered.
   (The legacy branch is currently dead -- guarded by `if on_tool_call ... elif
   on_form_update`, and `on_tool_call` is always wired -- so this is
   defense-in-depth, not a live leak.)
4. **`onError` stranded the live session (Codex P1).** A validation reject called
   `this.callbacks.onError`, which maps the connection status to `error`; the voice
   overlays disable push-to-talk unless `connected`, so a single bad value would
   strand the user exactly when the model re-asks. Removed the `onError` call -- the
   in-band `completion_message` is the correct non-fatal channel.
5. **Cross-field prompt spin (Codex P1).** A model alternating bad values BETWEEN
   fields reset the per-field counter on every switch, so the per-field cap never
   engaged and it prompted forever. Added a SESSION-WIDE cap
   (`VALIDATION_REJECT_SESSION_CAP=6`) that is not reset on a field change (only on
   connect/section-switch/good-value), bounding the cross-field spin.
6. **Reject streak survived a section switch (fresh-eyes).** `startSection` /
   `switchToSection` (same-socket section transitions, so `handleOpen`'s reset does
   not fire) reset the 0y7 counters but not the validation-reject ones; added
   `resetValidationRejectTracking()` to both. Defense-in-depth (field ids are
   globally unique per schema, so a cross-section carry-over needs a duplicate id),
   mirroring why 0y7 resets there too -- proven by a red-first test that reuses one
   field id across the switch boundary.

**Codex round 2 (3 more P1 blockers, all adopted; 239 frontend tests pass).** The
round-1 fixes had three edge-case siblings, all genuine:

7. **Top-level date min/max not enforced.** Round-1 fix #1 folded top-level
   `min`/`max` into `effectiveRules`, but `validateDateValue` only read
   `field.min_date`/`field.max_date` -- so a date field with top-level string-date
   bounds (e.g. adult_intake `dob`: `min "1900-01-01"`, `max "2007-10-13"`, no
   `*_date`) let an out-of-range AI DOB land. Fixed: `validateDateValue` falls back
   to `rules.min`/`rules.max` via an `asDateBound()` helper that takes only strings
   (a numeric bound from a real number field is ignored, not mis-parsed).
8. **Session cap not restored after progress on a DIFFERENT field.** The
   reject-budget reset only ran when the good value matched
   `lastValidationRejectFieldId`; once the session cap was hit on A/B, a successful
   fill of C left the cap stuck, so a later bad value on a new field got no
   corrective prompt. Fixed: reset all reject tracking on ANY successful AI apply --
   the prompt budget now tracks forward progress, while the pure no-progress spin
   (Codex round 1) still hits the cap.
9. **Comma-separated checkbox values false-rejected.** The backend prompt
   (`config.py`: "Multiple checkboxes: comma-separated exact values") tells the
   model to send a checkbox group as one comma-joined string; `validateOptionMembership`
   treated the whole string as a single candidate and rejected it. Fixed: for a
   checkbox-group field (`type==="checkbox"`/`group_kind==="checkbox"`) a
   comma-containing string is split + trimmed before membership-checking. Scoped to
   checkbox groups only (a single-select option that literally contains a comma --
   e.g. "Springfield, IL" -- is still matched whole; tested).

**Codex round 3 (3 more P1 blockers, all adopted; 246 frontend tests pass).** All
three were field-type/value-shape scoping gaps in the enum gate -- the same root
class as the round-1/2 option findings (the `FieldType` -> value-shape contract is
richer than the gate first modeled):

10. **Standalone boolean checkbox rejected.** The enum gate ran for ANY field with
    `options`, but a STANDALONE checkbox (`type:"checkbox"` WITHOUT
    `group_kind:"checkbox"`) is a BOOLEAN per the backend contract ("For checkbox:
    boolean") -- its `options` array describes its single PDF widget, not an enum.
    So `String(true)` was compared against an option like `"P2_checkbox3[0]"` and
    every valid true/false fill was rejected (i-90 has many such fields). Fixed: an
    `isStringEnumField()` predicate gates the enum check to select/radio/checkbox
    GROUPS only; a standalone checkbox skips it.
11. **Bare date field never format-validated.** A date field with only a `format`
    and no validation/min/max (e.g. i-589's many `type:"date"`,
    `format:"mm/dd/yyyy"` fields) hit the empty-`effectiveRules` early return before
    `validateDateValue` ran, so a malformed AI date landed. Fixed: a non-empty date
    value always runs `validateDateValue` (parseability + bounds) regardless of
    rules, via an early `field.type === "date"` return.
12. **Empty array `[]` on a single-choice field passed.** An `[]` for a select/radio
    made the membership loop vacuously pass, landing a blank value. Fixed:
    `validateOptionMembership` rejects a NON-empty array for a single-choice field;
    `[]` is handled by the unified empty-handling in round 4 (below).

**Fresh-eyes round 4 (Codex quota-exhausted -- fresh-eyes substituted; 3 actionable
findings, all adopted; 249 frontend tests pass).** Two of these were flaws the
round-2/3 fixes themselves introduced -- the loop-breaker over-correction is the
notable one:

13. **Reset-on-any-success bypassed the session cap (the round-2 over-correction).**
    Round-2 fix #8 reset ALL reject tracking on ANY successful apply. Fresh-eyes
    showed that over-corrects: a model alternating `[bad-A, good-B]` every batch
    would clear the session cap each batch and prompt for the failing A forever --
    the exact cross-field spin the cap exists to stop. Re-scoped: a success resets
    the budget ONLY when the field that succeeds IS the one currently being rejected
    (`field.id === lastValidationRejectFieldId`) -- genuine progress on the STUCK
    field -- not on an unrelated success while a streak is active. This satisfies
    BOTH findings: round-2's "the stuck field recovering restores budget" and
    round-4's "an unrelated good value must not". (Lesson: the right progress signal
    is progress on the FAILING thing, not any field.)
14. **Empty array unified as empty.** `normalizedEmpty` now also treats `[]` as
    empty, so a REQUIRED checkbox group submitted as `[]` (no selections) is caught
    by the required check instead of slipping through, and an `[]` on an optional
    field is simply unfilled (not a vacuous landing). The matching guard was added to
    `handleConfirmFieldRequest`'s `hasUsableValue` so an empty array can never be
    confirmed as filled either (closes the confirm-gate half of round-3 #12).

**Deliberately NOT fixed (defended):** fresh-eyes round-4 Finding 2 -- the corrective
prompt names the field by `spoken_name` in the preamble and (inside the constraint
phrase) by `name`. This is a minor prompt-readability nit, not a data-safety or PII
issue (both are field identifiers, never the value), and fixing it would mean
threading `spoken_name` through every `validateField` message. Left as-is; the
constraint phrasing -- the load-bearing part -- is correct.

## Lessons

- **`dependency_error` is a dead FE->backend channel.** The frontend has sent
  `dependency_error` for locked-field rejects for a while, but the backend never
  registered a handler for it -- it logs `unknown_control_message_type` and replies
  `error`. Any "route this back to the model" work must use `completion_message`
  (-> `send_prompt`), the channel the loop-breakers already prove works. (Filed as a
  follow-up consideration -- the locked-field path may want the same fix.)
- **Client-side validation is not redundant with backend validation here.** Because
  the client is the authoritative store (stateless backend), the client gate can
  *refuse the apply* -- a strictly stronger guarantee than the backend's tool-response
  validation, which can only tell the model after the fact.
- **The schema shapes vary more than the `FormField` type admits, and any
  validation pass must handle ALL of them.** Three of the five Codex blockers were
  the same root cause: a constraint can live at the field level (`max_length`) OR
  under `validation`; an option can be a `{value}` object OR a plain string. The
  TypeScript type understates this (it types `options` as `FieldOption[]`), so the
  variety only shows up against real schemas (i-90, adult_intake_demo). A
  validation/normalization helper that reads one shape silently mis-handles the
  other -- here, false-rejecting every value or skipping the check entirely. When
  touching schema-driven code, enumerate the real schemas, not just the type.
- **A loop-breaker keyed only per-field misses the cross-field spin.** The per-field
  cap stopped a model re-sending one bad value, but a model ALTERNATING bad values
  between fields reset the counter on every switch and prompted forever. Needed a
  second, session-wide cap not reset on field change. (Generalizes to the 0y7
  unconfirmable breaker, which is also per-field -- noted as a potential sibling gap.)
