## Trigger

Sprint-6 editor-authoring epic (s4dp), bead B3, the last child (epic was 4/5).
`help.instructions` -- guidance shown to schema authors AND fed to the LLM /
subagents (validator, researcher) -- was always left blank by extraction, even
though the AcroForm `/TU` (tooltip) text was already captured in the dump and
unused. Layers on the metadata-extraction pattern B4 (s4dp.2) established: a
deterministic, no-LLM, dump-join pass inside `extract()`.

## What shipped

Two deterministic sources, both targeting per-field `help.instructions`.

**Source 1 -- /TU baseline (free, always on).**
`extract_form.py` gains `_build_name_to_tu(dump)` (widget name -> /TU, the same
join key `_backfill_positions` uses for rects) and
`_extract_instructions_from_dump(schema, dump)`, which sets each field's
`help.instructions` from its `/TU` -- joining on `pdf_field_name` (or the first
option's name, for a consolidated `options[]` field, exactly like the position
back-fill). It runs INSIDE the dump `try` (the dump is deleted in the `finally`),
and does NOT clobber an existing `help.instructions` the LLM pass may have
written -- /TU only fills a genuine blank.

**Source 2 -- optional instructions-PDF upload (enriches when provided).**
New `--instructions-pdf` CLI param + `_parse_instructions_pdf` (whole-document
PyMuPDF text pass) + a straightforward per-field text merge
(`_enrich_instructions_from_pdf`): for each field whose LABEL appears in the
instructions text, the matched paragraph is APPENDED after the /TU baseline (both
survive, blank-line separated). Absent -> /TU-only, no error. A bad/missing PDF
yields "" -> no enrichment, never a crash.

**The merge-policy decision (defended).** The bead says "a straightforward
text-merge" and explicitly puts "deep parsing / structured ingestion" OUT of
scope. A whole-PDF blob can't sensibly go into every field, so the in-scope
reading is a per-field LABEL-substring match: `_match_instruction_for_label`
finds the SHORTEST paragraph containing the field's label (tightest, most
field-specific passage), case-insensitive, skipping labels under 4 non-space
chars (match too loosely). No LLM, fully deterministic, unit-testable. This was
an implementation/structure call (decide-by-default), not a product-direction
one -- noted here for the audit surface.

**The upload thread (reuses the form-PDF flow, no new multipart path).** The
browser writes the chosen instructions PDF into the kit dir as a FIXED
`instructions.pdf` (`writeInstructionsPdf` in `formKitDirectory.ts`, mirroring
`onboardPdf`), then passes that filename to the endpoint. The host resolves it
inside `kitDir` and passes `--instructions-pdf <path>` -- reusing every existing
guard (kitDir containment, safe-filename, same-origin). A named-but-missing
instructions PDF 404s (the browser writes it before POSTing, so absence means
something went wrong) rather than silently degrading.

- `schema-editor/vite-plugins/extractEndpoint.ts`: optional
  `instructionsPdfFile` request field (string-typed, safe-*.pdf-name,
  in-kit-dir + exists checks); appended as `--instructions-pdf` to the spawn args.
- `schema-editor/src/utils/extractionClient.ts`: `instructionsPdfFile?` opt
  (flows through the existing `...opts` spread; `undefined` is dropped by
  `JSON.stringify`, so /TU-only carries no key).
- `schema-editor/src/utils/formKitDirectory.ts`: `writeInstructionsPdf`.
- `schema-editor/src/components/FormCatalogue.tsx`: a hidden file input

  on run.
- Provenance: `_bakeoff.authoring` now reports `instructions_filled` (from /TU)

## Review rounds (what the layers caught)

- **Pre-PR fresh-eyes (2 rounds):** round 1 caught a real Crit-2 bug -- the
  `_enrich_instructions_from_pdf` skip guard had an `existing in passage` arm that
  silently DROPPED richer help when the /TU baseline was a substring of the
  instructions paragraph (the common case). Fixed to skip only `passage in
  existing`. Plus 2 nits (a misleading `# pragma: no cover`; a missing
  instructionsPdfFile traversal test). Round 2: NO-GAPS.
- **Codex (PR #274), 3 P1 findings, all real -- caught what fresh-eyes missed:**
  1. **Whitespace-normalize the label match.** PyMuPDF wraps extracted text with
     newlines, so a label "Family Name (Last Name)" would NOT substring-match a
     paragraph rendered "Family Name\\n(Last Name): ...". Added `_collapse_ws`,
     applied to both the label and each paragraph before matching (returns the
     original paragraph so appended help keeps its layout).
  2. **Match on `name`, not `label`.** The backend FormField makes `name` the
     required display label and has NO `label` field at all; the LLM draft does
     emit both, but a contract-minimal field carries only `name`. The enrich loop
     keyed on `field.get("label")`, so it would have produced ZERO enrichment for
     the contract shape. Added `_field_match_label` (name, fallback label). This
     was the load-bearing miss -- the synthetic fresh-eyes test schemas all used
     `label`, hiding it; verified against the real i-90 schema (`name` =
     "Family Name (Last Name)", the concise key; `label` = a verbose "Part 1. ..."
     breadcrumb that would over-match anyway).
  3. **Validate the selected file is a PDF client-side.** The catalogue's `accept`
     filter is advisory; a user could pick a .txt, it would be stored as the fixed
     `instructions.pdf`, pass the endpoint's .pdf-name guard, and yield no text --
     a success-reported run that ignored the selection. FormCatalogue now rejects a
     non-PDF pick with an error before storing it.
  Tests added for all three (whitespace match, `_collapse_ws`/`_field_match_label`,
  name-keyed enrich, non-PDF rejection). Editor 312 green; Python instructions 26
  green; tsc clean.
