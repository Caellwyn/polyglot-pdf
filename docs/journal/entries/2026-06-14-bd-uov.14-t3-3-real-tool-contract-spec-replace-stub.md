## Trigger

Bead polyglot-pdf-uov.14 (T3.3, under the spec-driven test epic uov, Phase 3).
Original framing: replace the 0-line `test_tool_contracts.py` stub with a spec
that the 5 declared tools in `config.py` match what `callback_handler` dispatches
(names, required args, response shapes).

## What shipped

A new `backend/tests/unit/test_tool_contract_static.py` (16 pure, non-external
tests) pinning the contract between `config.py` `TOOL_DECLARATIONS` (the schema
handed to Gemini) and `CallbackHandler.on_tool_call` (the backend dispatcher).
The failure this guards: a declared tool with no dispatch branch falls through to
`on_tool_call`'s unknown-tool branch (returns `{}`), so the model emits a call the
backend silently drops -- in the demo, the assistant appears to "forget" to fill
or confirm a field.

- **Declaration integrity:** the declared names equal the supported set
  (`update_form_fields`, `get_form_status`, `switch_section`, `get_field_value`,
  `confirm_field`); each declaration is well-formed (object param schema, every
  `required` entry exists in `properties` and carries a type); and
  `confirm_field.confirmation_method`'s enum is exactly `{verbal, manual}` -- the
  values the handler branches on.
- **Declarations <-> dispatcher:** every DECLARED tool routes to a real handler
  (it must NOT hit the `{}` fallthrough), proven by invoking `on_tool_call` with
  mocked tool handlers and asserting the right one fired; the dispatcher reads
  each tool's DECLARED required arg (not some other key); tool names normalize
  case-insensitively; the `get_form_state` alias (a dispatcher-side leniency, NOT
  in the declarations) routes to `get_form_status`; and an unknown tool returns
  `{}` reaching no handler.
- **Mutation-verified:** deleting the `switch_section` route makes
  `test_every_declared_tool_is_dispatched_not_dropped[switch_section]` fail,
  proving the dispatch test catches a silently-dropped declared tool.

**Framing correction (a finding worth recording):** the bead said "replace the
0-line `test_tool_contracts.py` stub," but that file is NO LONGER a stub --
epic wpw (PRs #126/#133, bd 8k8) had already filled it with a real 280-line LIVE
tool-call SEQUENCE test (`@pytest.mark.external`, A/Bing the 2.5 vs 3.1 model's
update->confirm ordering). That is a DIFFERENT contract -- the model's runtime
behavior -- from what uov.14 specs (the static declaration<->dispatcher wiring).
So I added a NEW pure unit file rather than touching or duplicating the live one;
the two are explicit counterparts with no overlap.

342 backend tests pass; test-only, no product code changed. The bead had no
`## Exit criteria` (creation-time-norm slip); a retrospective rubric was written
at claim time.

## Lessons

A "replace the stub" bead can be stale by the time it is claimed -- another epic
may have already filled the named file with a DIFFERENT contract. The check
before rewriting: read the file's current content AND ask what contract it
actually asserts, not just whether it is non-empty. Here the live file asserts
model ORDERING (does the model fill-then-confirm?), which is orthogonal to the
static wiring (is every declared tool dispatchable?). The two coexist as labelled
counterparts; collapsing them would have lost the distinction between "the model
behaves" and "the backend is wired."
