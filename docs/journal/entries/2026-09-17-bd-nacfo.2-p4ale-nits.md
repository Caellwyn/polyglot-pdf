## Lessons

Running `closeout_prep.py` from the wrong working directory (a different
worktree bound to the same session) makes it resolve `git rev-parse
--show-toplevel` against THAT worktree, so its dirty-tree, stale-docs, and
commit-ahead-of-base checks silently report on the wrong branch entirely --
with no error, because the script has no way to know which worktree the
caller meant. The tell was the same as the git-reset-soft trap: numbers that
did not match what this branch actually touched (a stray `admin-console/`
untracked directory and `ybwjw` plan-doc commits neither introduced by this
diff). Always launch `closeout_prep.py` (and by extension any script that
resolves its own root via `git rev-parse`) via `(cd "$WT" && python
scripts/closeout_prep.py ...)`, never by passing an absolute script path
while the shell's cwd sits in a different worktree.

Separately, `bd orphans` (part of beads housekeeping) timed out at 120s under
this session's machine load (many concurrent worktrees/sessions running);
confirmed independently with a bare 30s `bd orphans` call from the main
checkout, also timing out. This matches the existing memory note that `bd`
subprocess spawns hit a process-spawn ceiling under many concurrent sessions,
not a `bd` or beads-data problem -- left as a pre-existing environment
condition, not something this bead's diff caused or can fix.
