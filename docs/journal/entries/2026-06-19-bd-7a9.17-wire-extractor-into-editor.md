## Trigger

The schema-editor onboards a dropped PDF (creates `form-kits/<id>/`) but had no
in-app way to RUN the extraction that produces its schema -- the human had to drop
to a terminal and run `scripts/authoring/extract_form.py` by hand. The maintainer
asked to make the editor a stand-alone PDF -> schema tool (drop a PDF, click a
button, get a schema), and to factor the LLM out-call so a remote/hosted or better
model can be swapped in later without a rewrite. This completes the editor<->extractor
spine of the authoring epic (polyglot-pdf-7a9) and unblocks the open child ue5s
(run a new form through the loop), which the manual step was gating.

## What shipped

Three layers, plus a worktree-runnability fix surfaced during verification:

1. **LLM provider seam** (`scripts/bakeoff/llm_providers.py`). The extractor's
   single model call was previously an inline `startswith("gemini")` branch inside
   `arm_llm_native.run()`. Factored it into a registry of `LLMProvider`
   implementations (`ClaudeCliProvider` default, `GeminiProvider` fallback) resolved
   by `resolve_provider(model)`: `EXTRACTOR_PROVIDER` env overrides (the
   hosted/remote swap knob), else the model name dispatches exactly as before. A
   typo'd `EXTRACTOR_PROVIDER` fails loud (KeyError naming the source + known
   providers), never silently picks a wrong backend. Behavior-preserving:
   `arm_llm_native.run()` is the only edited call site; `extract_form.py` and the
   chunked arm are untouched (they call `run()`). `register_provider()` lets a
   future hosted deployment inject its own backend.

2. **Dev-only extraction endpoint** (`schema-editor/vite-plugins/extractEndpoint.ts`).
   The editor is a pure browser SPA; a browser cannot spawn Python or the local
   `claude` CLI, so extraction MUST run host-side. Added a Vite plugin
   (`apply: 'serve'`) exposing `POST /api/extract` (+ a `GET` capability probe) that
   spawns `extract_form.py` for one kit. The form-kits root is a SERVER-side path
   (`FORM_KITS_ROOT`, default the repo's `form-kits/`) because the browser's
   directory handle is opaque to the host; the request carries only a kit id,
   validated as a single safe path segment + confirmed inside the root (path-traversal
   guard). Dev/local only -- a static prod build has no endpoint.

3. **React UI** (`FormCatalogue.tsx` + `extractionClient.ts`). A "Run extraction"
   button on a schemaless+pdf kit card, gated on a mount-time `GET /api/extract`
   probe so a deployed static editor degrades to an instruction hint instead of a
   broken button. Click -> POST -> spinner -> on success refresh the catalogue (the
   kit lights up openable) -> success/error notice with the validation detail.

4. **Worktree runnability** (`vite.config.ts` `server.fs.allow`). Verification
   surfaced that the editor could not run from a git worktree at all: a worktree's
   `node_modules` is a junction into the main checkout, so Vite served the pdfjs
   worker by its link-resolved (main-repo) path, which sits OUTSIDE the worktree
   root and Vite's `fs.allow` refused it ("403 Restricted" -> "Failed to Load PDF").
   Added an `fs.allow` that includes the realpath-resolved `node_modules`; a no-op
   in a normal checkout (realpath == nested path). This is what made the in-worktree
   end-to-end verification (and the maintainer's pre-merge test-drive) possible.

**Verified end-to-end:** dropped the real W-7 PDF, POSTed `/api/extract`, got a
61-field schema that validated against the backend Pydantic `FormSchema`, written
to disk, exit 0 (~2m16s). Traversal/missing-id/not-found request paths all return
the right 4xx. Production build succeeds with the endpoint correctly excluded.

**Codex outer review (round 1):** found 7 P1 findings my fresh-eyes pass missed,
all adopted (none were true nits) -- a CSRF/same-origin guard on the side-effecting
endpoint; a non-string-`id` type guard (`{"id":123}` coerced past the regex); a
`.catch` on the floating handler promise; refuse-to-overwrite an existing schema
(force opt-in) so a stale catalogue can't clobber reviewed work; write to a temp
file + atomic-promote on success so a failed/invalid run never lands a broken
`schema.json` at the real path; kill the (paid, minutes-long) child + clean the
temp when the client disconnects; and forward `EXTRACTOR_MODEL` to `--model` so a
configured provider swap actually takes effect from the button (closing a real hole
in exit criterion 2's swap contract). Verified live: cross-origin -> 403,
non-string id -> 400, existing schema -> 409, force re-extract -> validated schema
via temp-promote with no leftover temp file.

**Codex outer review (round 2):** found 7 more genuine findings (none re-litigation;
escalated past the nominal 2-round ceiling with maintainer approval since all were
real). Adopted all: a P0 build-break (the plugin uses Node builtins + `process`/
`Buffer`/`__dirname` but `@types/node` was not a dep, so `npm run build`'s `tsc`
could fail on a clean install -- added `@types/node`); the temp filename used
`process.pid` which is constant for the Vite server, racing two concurrent
extractions of the same kit (added a per-request counter); the child-kill listened
on `req.close` but the long-run abort surfaces on the RESPONSE (moved to
`res.close` + `req.aborted`); `resolvePythonExe` only probed the worktree's
`backend/.venv` which never exists (the venv lives only in the MAIN checkout), so
the button fell back to a PyMuPDF-less `python3` in exactly the worktree setup this
feature supports (now resolves the main repo via `git --git-common-dir`, plus an
`EXTRACTOR_PYTHON` override -- verified the resolution lands on main's real venv);
the Gemini-default-model gap deepened (even with `EXTRACTOR_MODEL` forwarding, a
bare `EXTRACTOR_PROVIDER=gemini` still defaulted to a Claude model name -> now
`GeminiProvider` rejects a non-gemini model loud, before any SDK call); the
filename regex rejected legitimate metadata names with SPACES ("Form W-7.pdf") that
the catalogue accepts (replaced the stem-regex with a traversal-only
`isSafeFilename`); and no automated coverage of the endpoint's security/data-safety
contracts (added 12 endpoint tests driving `handleExtract` with mock req/res over a
temp form-kits dir: same-origin, traversal, type-guard, filename-with-spaces,
bad-extension, not-found, overwrite-refusal, force). Reordered the overwrite gate
before the extractScript-exists check so the request is fully validated first.
Verified live: cross-origin->403, spaces->404 (accepted), venv resolves to main.

**Codex outer review (round 3):** 4 narrower findings (concurrency/identity edge
cases on a single-user localhost tool). Maintainer chose "fix the 2 real gaps in
the round-2 fixes, defer the 2 inherent edge cases." FIXED: (a) the abort killed
only the Python wrapper, not the `claude`/`gemini` grandchild it spawns -- now the
child is spawned in its own process group (`detached` on POSIX) and an abort kills
the whole tree (POSIX `kill(-pid)`, Windows `taskkill /T`); (b) the round-2 busy
guard was shared with the drop handler, so a concurrent drop's `finally
{setBusy(false)}` re-opened the folder controls mid-extraction -- replaced with a
DEDICATED `extractingId` in-flight guard that folder-switch and drop both refuse
against and that no other handler can clear (+ a test holding the POST open to
assert the controls stay locked). DEFERRED to **polyglot-pdf-7a9.19** (P3): the
rename-time TOCTOU (two concurrent same-kit extractions racing on promotion) and
cross-root mutation (opened folder != server FORM_KITS_ROOT) -- both inherent to
the opaque-browser-handle architecture and low-likelihood on a single-user tool.

**Codex outer review (round 4 -- final):** 4 findings, now clearly diminishing
returns (the loop had not converged in 4 rounds on a dev-only tool). Maintainer
chose "fix the 2 cheap ones, defer the rest, stop the loop." FIXED: `path.resolve`
the `EXTRACTOR_PYTHON` override against repoRoot (a relative override was checked
from the Vite cwd but spawned from repoRoot -- they could disagree); reject a
non-object JSON body (`null`/`5`/`[]` parse as valid JSON but `body.id` on a
non-object would throw). DEFERRED to **polyglot-pdf-7a9.19**: a symlink-escape of
the kit-root containment check (needs a planted symlink) and an upload-abort
promise leak in `readJsonBody` (microsecond window, tiny body). After 4 rounds
(round 1: 7 adopted incl. security/data-loss; round 2: 7 incl. a P0 build-break;
round 3: 2 real-gap fixes + 2 deferred; round 4: 2 cheap fixes + 2 deferred), the
Codex loop was stopped by the maintainer with the remaining edge cases tracked --
the feature is heavily reviewed and the open items are all narrow hardening on a
single-user localhost tool.

**Out-of-scope, filed not built:** the hosted/remote extraction path (deployed
server + secrets + cost) -- the seam is built FOR it, standing it up is its own work.
During verification, found a real extractor bug: on W-7 every field's `pdf_position`
is all-zeros, so editor click-to-jump fails (works on I-90). Root cause:
`_backfill_positions` guards with `if field.get("pdf_position"): continue`, which
skips a present-but-zero position the model emitted, so the deterministic
dump-rect back-fill never runs. Filed as **polyglot-pdf-7a9.18** (P1 bug, next).

## Lessons

- **A browser SPA that needs host-side work needs a host-side process; the File
  System Access handle cannot bridge to a filesystem path.** The directory handle
  the SPA holds is opaque by design -- it can't be handed to a server as a path. So
  the server must resolve kit ids against its OWN known root, which constrains the
  feature to "the editor's open folder is the server's form-kits root" (the normal
  local-dev case). Designed around it rather than fighting it.
- **A git worktree whose `node_modules` is a junction trips Vite's `server.fs.allow`.**
  Anything Vite serves by realpath (the pdfjs worker via `new URL(..., import.meta.url)`)
  resolves outside the worktree root and 403s. Generalizes to any worktree-run Vite
  app; added a one-liner to `docs/standards/testing.md` citing this entry.
- **The fresh-eyes model picker measures committed HEAD vs base, so it under-routes
  an uncommitted diff to Haiku.** A 1133-line uncommitted change measured as 0 lines.
  Commit before picking, or fail toward the capable model (did the latter -> Sonnet).
