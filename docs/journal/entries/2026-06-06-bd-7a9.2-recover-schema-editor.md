## What shipped

The `schema-editor/` app, recovered into the repo + this assessment. NOT wired
into the main app; it is a standalone Vite/React tool.

### Recovery

`git checkout a0bf111 -- schema-editor/` (a0bf111 = `5ea05d4^`, the commit before
the delete-to-separate-repo). 48 files committed (`node_modules`, `.vite`, and
`dist` all gitignored and absent from the commit). The app is self-contained: `public/schemas/{i-90,i-589}/` bundles the
PDFs + schema variants, and `AVAILABLE_FORMS` (`src/utils/schemaLoader.ts`) loads
from `/schemas/...`, so it does NOT depend on the also-deleted
`pdf_schema_extractor/` paths the README mentions.

### What the tool is (from README + EDITOR_GUIDE, "Production Ready, 113/113
tests" as of 2025-11-05)

A visual PDF-form-schema correction editor: renders the PDF (pdfjs-dist canvas,
multi-page, zoom 50-200%), draws **color-coded field overlays** on the page
(green=complete / yellow=review / red=error), a field-list tree with completion
status, a property editor (type, spoken_name, help, validation, `show_if`
conditional logic), real-time validation, and Cmd+S to download the edited schema.
Components: `PDFViewer`, `FieldOverlay` (the WYSIWYG overlay), `FieldEditor`,
`ValidationPanel`, `FormSelector`, `pdfCoordinates` utils.

### State assessment -- intact, needs a modest revival pass

| Check | Result |
|-------|--------|
| `npm install` | OK (280 pkgs, Node 24) |
| Vitest suite | **101/113 pass** |
| Dev server (`vite`) | boots in ~257ms, serves app + assets (200), React mounts, **zero console errors** |
| `tsc` build | FAILS -- but only on test-file type errors + 2 unused-var lints (see below) |
| Headless render screenshot | timed out (canvas/pdf-worker headless limitation; NOT a runtime error -- console clean) |

**The 12 test failures all cluster in coordinate transforms** (`pdfCoordinates`,
`FieldOverlay` positioning, auto-scroll). My first hypothesis was `pdfjs-dist`
drift (`4.0.379 -> 4.10.38` under the `^` range), so I pinned `pdfjs-dist` to
`4.0.379` exact -- **but re-running the suite at the pinned version still gives
101/113 (the pin did NOT change the count).** So the drift hypothesis was WRONG
(verified, not assumed -- see lesson below). The real cause is a **test-vs-component
mismatch in the recovered code itself**: e.g. `FieldOverlay.test.tsx:53` expects
`top: 62px` (computed `(792 - 700 - 30) * scale`, a PDF-origin-flip formula) while
the component renders `700px` (raw y); and `:172` expects a `3px` selected border
while the component uses `4px`. These read as tests encoding an OLDER coordinate
formula than the shipped component -- i.e. the suite was **already red at
`a0bf111`** when the tool was shelved (the README's "113/113" was stale/aspirational).
Pinning `pdfjs-dist` is kept anyway (correct hygiene for a recovered front-end
tool), but it is NOT the fix. Reconciling the 12 test/component coordinate
mismatches is revival work (bead `7a9.6`).

**The `tsc` build failures are NOT app-logic problems:** `toBeInTheDocument` /
`toBeDisabled` types not resolving (a `@testing-library/jest-dom` types wiring
issue under the newer toolchain) in `.test.tsx` files, plus 2 trivial
unused-symbol lints (`ValidationError` in `ValidationPanel.tsx`, `pageNum` in
`test/setup.ts`). The `vite dev` server (no `tsc`) runs fine.

### Verdict for the recommendation bead (`7a9.5`)

**Recover, do not rebuild.** The tool is structurally complete and boots. The
valuable WYSIWYG correction surface (PDF + overlay + property editor + validation)
is exactly what the maintainer wanted back, and it exists. The residual work is a
**revival** task: reconcile the 12 test/component coordinate-convention mismatches
(decide which side -- the test formula or the component -- is correct, likely by
visual inspection of where overlays actually land on the PDF), fix the jest-dom
types wiring, clear 2 lints, visually confirm render in a real browser. That is
bounded revival, NOT a rebuild. Filed as `7a9.6` (see below).

## Lessons

- **Don't assume a test-failure cause -- verify it.** I first blamed the 12
  coordinate-test failures on `pdfjs-dist` drift (`^4.0.379` floated to `4.10.38`)
  and pinned it -- but re-running at the pin showed STILL 101/113. The pin changed
  nothing; the real cause is test-vs-component coordinate-convention skew in the
  recovered code (the suite was already red at `a0bf111`; the README's "113/113"
  was stale). Fresh-eyes caught the unverified "fixed by pinning" claim; the cheap
  resolution was to actually re-run, not re-hedge. (Pinning exact versions is still
  good hygiene for recovered front-end tools -- just not THIS bug's fix.)
- **A clean `tsc` failure can be entirely test-harness types, not app logic** --
  read the errors before concluding the app is broken. Here `vite dev` ran with
  zero console errors while `tsc` "failed."
- **A recovered tool's own test suite may have been red when it was shelved** --
  "production ready, all tests passing" in a README is a claim to verify, not trust.
