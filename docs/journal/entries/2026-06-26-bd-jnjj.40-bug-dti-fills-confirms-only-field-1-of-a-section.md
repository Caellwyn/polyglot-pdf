## Trigger

In DTI mode a continuous voice session filled+confirmed only the FIRST field of a
section; fields 2-6 stalled until a section reset (new Gemini session) recovered
them. Present in every historical DTI run (sections 2-3 filled via fresh sessions,
section 1 only ever confirmed field 1). This bead was filed during the jnjj.38
investigation and deliberately gated on jnjj.39 (the `--debug` instrument) so it
could be diagnosed from real per-turn data instead of guessed.

## What shipped

The jnjj.39 `--debug` artifact (model transcript + tool args/responses) showed the
stall was not a single bug but THREE compounding causes -- and the first one was a
test artifact masquerading as a product bug:

1. **A test-fixture bug (the actual trigger).** The harness scripted a 10-DIGIT
   USCIS online account number for a field whose validation requires EXACTLY 12
   (min/max_length=12). The model was *correct* to reject it -- then got stuck. The
   "is it fixed or hiding?" scrutiny is exactly what surfaced this: the value was
   wrong, not the model. Fixed the say/wrong/expected to a valid 12-digit value.
2. **Numeric normalization (defensive, real).** Gemini's speech-to-text rendered the
   spoken digit string as `$1,234,567,890` (a `$` + commas), which fails the length
   check. `uscis_account` is now a recognized `format_preset` (added to the
   `ValidationRules` Literal + the I-90 schema field) and `normalize_value` strips
   non-digits before validation, so punctuation can never re-trigger the stall.
3. **Empty-confirm loop (production robustness).** When the model emptied a field
   and confirmed it, the `no_value` failure was marked `retryable: True`, so it
   re-confirmed the same empty field identically and wedged in a loop (its own
   transcript: "...which has me in a loop"). `no_value` is now `retryable: False`
   with explicit "fill, do NOT retry the bare confirm" guidance.

**Exit-criteria scorecard (Step 5.5.a):**
1. Root cause identified with evidence -- **PASS.** The instrument distinguished it
   from the three hypothesized causes (never-confirms / merge-broken /
   hallucinated-field-id): the real chain was invalid-value-rejection -> empty-confirm
   loop. Transcript evidence on the bead.
2. Continuous DTI session fills+confirms ALL fields of a multi-field section,
   verified on the harness -- **PASS.** 4 consecutive 9-question I-90 section-1 runs
   all 9/9 confirmed, 0 failed tool responses, 0 exceptions (was 1/6). The
   stability check (3 repeats) is what makes this "fixed", not a lucky run.
3. Validated on real audio OR flagged if audio-specific -- **PARTIAL / FLAGGED.**
   All runs use synthetic gTTS audio. The fixes are sound for production regardless
   (the fixture + the loop are audio-independent; the normalization is a safe
   defensive strip). But whether a real human saying digits would ever trigger the
   comma artifact is unknown from synthetic audio -- flagged for a future real-voice
   spot-check. Recorded in the PR + bead.

## Lessons

- **"Is it fixed or hiding?" catches fixtures masquerading as product bugs.** The
  headline "fix" was correcting a 10-vs-12-digit scripted answer the model was right
  to reject. Without the skeptical re-examination (and the input-transcript signal
  that showed exactly what the model heard), this would have been mis-filed as a
  model/DTI defect.
- **Verify the fix MECHANISM, not just the score.** 9/9 alone could be luck; the
  decisive evidence was 0 failed tool responses across 4 runs -- the cascade
  (rejection -> empty-confirm loop -> hallucinated field ids) demonstrably did not
  occur, not merely "the number went up".
- **A retryable error the model literally cannot recover by retrying is a loop
  invitation.** `confirm_field` on an empty field fails identically every time;
  marking it retryable told the model to do the one thing that can't work. The fix
  is to redirect (fill first), not retry. Generalizes: an error envelope's
  `retryable` flag should be False when the same call would fail identically.
