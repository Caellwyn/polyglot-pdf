# 3.1 rejects send_client_content text turns -- use send_realtime_input (bd polyglot-pdf-1g6)

## Symptom

With the demo on AI Studio + `gemini-3.1-flash-live-preview` (after the bd
`polyglot-pdf-jrl` switch, the Gemini-API enablement, and the API-key
restriction fix), the voice session finally CONNECTED -- the backend logged
`setupComplete` then `GEMINI SESSION READY` -- but ~3s later closed with
`1007 (invalid frame payload data) Request contains an invalid argument` and
`Events received before disconnect: 0`. In the browser this looked like the
section-switch reconnect failing.

## Root cause (verified against the live endpoint)

`setupComplete` proves the entire connect-config (modalities, tools, VAD,
system_instruction) was ACCEPTED -- so it was not a config field. The `1007`
fired on the first send AFTER setup: the disclaimer / initiating text message,
which the adapter sent via `session.send_client_content(turns=...)`.

An isolation probe (`backend/scripts/probe_3p1_1007.py`, run with the demo's AI
Studio key from Secret Manager) pinned it:

| Stage | Method | Result |
|-------|--------|--------|
| send-client-content-text | `send_client_content(turns=...)` | **1007** |
| minimal-config + client-content | same, stripped config | **1007** (rules out config) |
| send-realtime-audio | `send_realtime_input(audio=)` | OK (audio already worked) |
| **realtime-input-text** | **`send_realtime_input(text=...)`** | **OK, got_audio=True** |

So `gemini-3.1-flash-live-preview` rejects a text turn sent via
`send_client_content`, but accepts the same text via `send_realtime_input(text=)`
and responds with audio. This is a model-specific input-channel quirk, not a
config or auth problem. (Audio input via `send_realtime_input(audio=)` was never
affected.)

## Fix

Added `LiveAIGemini._send_text_turn(session, text)` and routed all three adapter
text-send sites through it (the public `send_client_content`, the `text_sender`
queue drain, and the `_pending_client_content` flush). It chooses by model
family (`config.model_family`):

- **3.1 family** -> `session.send_realtime_input(text=text)`
- **2.5 / others** -> `session.send_client_content(turns={role:user,...}, turn_complete=True)`

Kept model-conditional rather than a blanket swap: the 2.5 realtime-text path is
unverified (the 2.5 probe stage hung -- the documented `daa` native-audio
flakiness), and prod runs Vertex/2.5, so we must not regress it. When 2.5 is
re-verified the branch can collapse to a single `send_realtime_input(text=)`.

## Verification

- Probe: `send_realtime_input(text=)` on 3.1 returns audio (`got_audio=True`).
- Unit: `test_send_text_turn_uses_realtime_input_for_3p1` /
  `..._uses_client_content_for_2p5` assert the routing; full suite 112 passed.

## Decisions (defended)

- **Model-conditional, not blanket** -- maintainer chose safest; avoids any
  chance of regressing the 2.5/prod path while the 2.5 realtime-text behavior is
  unconfirmed.
- **One helper, three call sites** -- the fix lives in `_send_text_turn` so every
  text-initiation path (disclaimer, language switch, prompt, hint, recovery,
  queued) is covered consistently; no site can drift.
- **Kept the probe script** (`backend/scripts/probe_3p1_1007.py`) -- it is the
  reproduction + the evidence for this finding and a reusable diagnostic for the
  next "which argument does model X reject" question. Reads the key from env;
  prints nothing sensitive.

## Scar tissue

Live API input-channel support is MODEL-SPECIFIC and must be verified against the
endpoint, like model names and modalities before it (see
`docs/genai_docs/README.md`). `send_client_content` vs `send_realtime_input(text=)`
are NOT interchangeable across model families: 3.1 needs the latter for text.
