## Trigger

The G3 fill-correctness measurement (jnjj.7) produced data that looked alarming
-- DTI filling far worse than the full-SI baseline -- and a first pass concluded
the harness (`scripts/spikes/measure_form_session_costs.py`) was "broken": a run
that filled 24/25 fields logged tool calls for only ~6 questions. jnjj.38 was
filed to fix the harness before trusting any DTI fill number. The maintainer
stopped a long live-Gemini debugging loop with two corrections -- "test it
yourself" and "look at the past trials" -- that redirected the investigation to
the truth.

## What shipped

A small, genuinely-useful harness improvement plus a corrected understanding and
two follow-up beads. The bead's premise turned out to be partly wrong, so the
deliverable is right-sized to what is actually true.

- **`meta["tool_callback_exceptions"]`** (the one landed code change). During
  diagnosis a crashing tool callback (a `FormField`-vs-`dict` `AttributeError`,
  briefly introduced by my OWN debug probe) was INVISIBLE: the adapter logs
  tool-callback exceptions via `_log.exception` (traceback DEV-only, `str(e)`
  scrubbed for PHI), so from the harness's view the fill silently never landed and
  read as model "drift." The tool tap now records each exception
  (`{q, tool, error_type}`) into the run meta, so a handler bug can never again
  masquerade as model behavior. Cheap, always-on, PHI-safe (type name only).
- **(committed earlier under jnjj.7)** `meta["fill_accuracy"]` per-field scoring,
  the `get_field_value` recall handler, and the `I90_EXPECTED` fixture fix (radio/
  select fields store CODED values -- `TX`, `P1_checkbox6c_Unit[0]` -- not spoken
  labels; the label fixture had mis-scored correct fills, identically across arms).

**Exit-criteria scorecard (Step 5.5.a):**
1. Tool-callback-exception blind spot closed -- **PASS**
   (`meta["tool_callback_exceptions"]` in `_tool_tap`).
2. "Broken harness" symptom correctly characterized + the real DTI bug filed --
   **PASS** (characterized as an attribution display quirk; jnjj.40 filed for the

**Fresh-eyes (Sonnet, 1 round, all adopted):** (1) `get_field_value` spoken-name
map collided across I-90 parts -- a whole-schema dict comprehension let a never-
filled Part-7 field shadow the Part-1 field the plan fills, so cross-section recall
returned `(None, found=True)` for 7 field types. FIXED: scope the map to the plan's
fields and resolve to a list, preferring a field actually filled in `client.state`.
(2) `found` semantic now mirrors production (name-known) without the collision
corrupting it. (3) `_canon_value` docstring overclaimed that "Twelve B"/"12B"
collapse (only SINGLE-digit words map) -- corrected the docstring. No deferrals; no
out-of-scope beads filed. The criterion-2 "beads unverifiable" gap was a
dolt-sync artifact (the subagent can't `bd dolt pull`) -- jnjj.39 and jnjj.40
verified present.

**What this bead deliberately does NOT do.** A state-sync turn-driving rewrite
(drive the loop by observing the form write instead of a token tick) was
prototyped and **reverted**: it did not improve fill rates and replaced the
historically-working token-tick driving without justification. The deeper harness
observability -- transcripts, per-turn tool I/O, reliable attribution -- is the
right-sized "fix the harness," split to **jnjj.39** (diagnostics), which
**jnjj.40** (the DTI bug) depends on.

## The real finding (why this was worth the dig)

The "broken harness" symptom was mostly a **`per_question_tools` display/attribution
quirk** -- async tool calls stamped with a mutable question counter under-attribute
past section 1. The fills themselves were landing. Underneath it, though, was a
**real, pre-existing DTI product bug** (now jnjj.40): in a continuous DTI session,
only field 1 of a section fills+confirms; fields 2-6 stall until a SECTION RESET
(new Gemini session) recovers them. This is why every historical DTI run scored
14-20/25 -- Sections 2 and 3 filled cleanly, Section 1 only ever confirmed
`p1_line1_aliennumber`. The model is capable (fills later sections perfectly), so
it is a within-section per-field handoff bug, not model competence.

## Lessons

- **Be as suspicious of your own debug code as of the harness.** A debug line that
  did `f.get("id")` on a Pydantic `FormField` crashed every fill and sent diagnosis
  chasing a phantom "model declines to fill" for several live runs. The
  exception-recording shipped here exists so that exact trap is visible next time.
- **Check the historical run records before concluding the model/harness "can't do
  X."** Past JIT / section-reset / DTI runs filled fine; the maintainer's "look at
  the past trials" is what exposed that the alarming numbers were Section-1-specific,
  not a model or harness incapacity.
- **Build observability before diagnosing model behavior.** The investigation
  devolved into expensive guess-and-rerun precisely because the harness shows almost
  nothing about WHY the model acts -- no transcripts, no per-turn tool I/O. jnjj.39
  builds that first so jnjj.40 (and future model-behavior questions) resolve in one
  instrumented session instead of ten.
- **Right-size the fix to what is actually true.** The bead said "fix the broken
  harness"; the honest deliverable was one observability improvement plus a correct
  re-characterization, not a turn-driving rewrite of a loop that mostly worked.
