## Trigger

The first live pilot of the epic polyglot-pdf-r3ham measurement harness ran on Vertex `gemini-3.8-live` with output transcription requested. Over 8 turns, zero transcript characters reached the client, and the adapter never logged `GEMINI_TRANSCRIPT_RECEIVED`.

A bare genai Live probe localized the cause:
- **3.8 bundles `output_transcription` into the same server message as an audio chunk:** 3/3, 3/3 and 4/4 transcript events across three runs.
- **`gemini-live-2.5-flash-native-audio` never bundles:** 0/10 and 0/5.
- **`usage_metadata` arrives on its own message on both models,** so token and cost accounting were never affected.

`LiveAIGemini`'s receive loop forwarded `event.data` audio and then `continue`d, so every 3.8 output transcript was dropped. A completion flag, an interrupt, or an input transcription bundled with audio would have been dropped the same way.

## What shipped

**The fix** (`backend/adapters/live_ai_gemini.py`):
- The post-audio `continue` became an `audio_forwarded` flag, so `server_content` is now processed on every message.
- The `model_turn` parts walk is skipped once the audio was already forwarded through `event.data`. That `model_turn` IS the audio, so walking it again would double-play it.
- The per-turn audio counters reset on a transcript only when the transcript arrived on its own message (the 2.5 shape).

**Tests:** five SDK-shaped receive-loop tests, where `event.data` carries the same bytes as the `model_turn` `inline_data`:
- a bundled transcript is delivered and the audio forwarded once;
- a bundled `turn_complete` fires `processing_done`;
- a bundled input transcription signals user activity;
- plain audio is forwarded once;
- the `inline_data`-only path still forwards.

Each mutation turned tests red:
- restoring `continue`: 3 red;
- reverting to `else` (double-play): 3 red;
- dropping the counter-reset guard: 1 red.

**Live verification:** a 3-question W-7 pilot on Vertex 3.8 delivered transcripts on every turn. The greeting audio was 5980 ms after the fix versus 6180 ms before, so the audio is not doubled.

**Filed as non-blocking or pre-existing:**
- **polyglot-pdf-yc621:** a `function_call` part sharing a `model_turn` with audio is still skipped, exactly as before.
- **polyglot-pdf-tkfyz:** if 3.8 bundles input transcription with audio, `on_user_activity`'s `_set_processing(True)` can re-raise the thinking indicator after the reply audio cleared it. The effect is cosmetic, capped by `THINKING_MAX_MS`, and has not been observed.
- **polyglot-pdf-pnc4k:** the ws-protocol, voice-ai and callback docs describe a `turn_complete` / transcript flow that is already stale on dev.

**Blast radius:**
- No shipped client requests output transcription. The paths that do are the WS `send_transcript` param and the local-only `SEND_TRANSCRIPT`, both used by local dev and the measurement harness.
- On the default production path, completion flags and input transcription are processed on audio-bearing messages. These were previously dropped whenever 3.8 bundled them.
- Correction to the bead description: the `LIVE_DEV_TRANSCRIPTS` dev capture was NOT affected. It records in the `event_shape` probe, which runs before the audio block.

## Lessons

- **A model migration can change the wire shape of server messages, not only behavior.** Receive-loop code that `continue`s after handling one field of a multi-field message silently drops the rest. The evidence that settled it was a bare-SDK probe counting field co-occurrence per message, run on both models. That costs about $0.01 and should be the first move whenever a migrated model "stops sending" something.
- **Before editing a shared receive loop, ask what ELSE now runs on the messages you stop skipping.** Here that meant usage accounting, interrupts, input transcription, and per-chunk logging. All were checked, and the one new ordering hazard is filed as tkfyz.
