## Trigger

Maintainer kickoff: keep improving the Gemini round trip. The handoff named bd
`i9q8` as the remaining blocker -- "both models under-call the form tools in-app
(2.5 hears 'yes' but skips confirm_field; 3.1 skips update_form_fields) while a
short-SI direct probe gets reliable tool calls" -- with a bisect-ladder plan to
find which part of the ~3850-char system instruction (SI) suppressed the calls.

Two complications surfaced immediately:

1. **The handoff beads were unrecoverable.** `i9q8`, `4sv7`, `vmxx`, `46bu`,
   `9jv` existed only in the prior session's un-pushed dolt store -- text-mentioned
   in `.beads/interactions.jsonl` ("Follow-on voice work continues under
   4sv7/vmxx/i9q8") but never stored as beads anywhere reachable. The committed
   journal + sprint plan + probe scripts carried the substance; the tracker
   entries did not. (Scar: bead state syncs via `bd dolt push`, not git.)
2. **The SDK changed under the findings.** The `google-genai` 1.38.0 -> 2.8.0
   cutover landed earlier the same day (PR #156). The maintainer flagged that all
   pre-cutover probe verdicts must be re-measured, not assumed. (The shared venv
   was still on 1.38.0 and had to be synced to the merged pins before any
   measurement was valid -- a trap that would have silently produced old-SDK
   results.)

## What shipped

- **Root cause (re-measured fresh on 2.8.0).** The SI-bisect was a dead end and
  the historic premise was false under the new SDK. A new harness
  (`backend/scripts/probe_si_bisect_i9q8.py`) drove the fill->answer turn across
  an SI ladder (short control -> full SI) per model:

  | Model | SI | `value` type | `update_form_fields` |
  |-------|-----|-----------|------|
  | 3.1 | short | untyped (old) | 0/4 |
  | 3.1 | full | untyped (old) | 0/5 |
  | 2.5 | short | untyped (old) | 4/4 |
  | 3.1 | short | "string" (fix) | 5/5 |
  | 3.1 | full | "string" (fix) | 4/4 |
  | 2.5 | full | "string" (fix) | 4/4 |

  3.1 failed even with the *shortest* SI, and passed the *full* SI once the param
  was typed -- so SI content/length was never the variable. A raw shape-dump
  showed 3.1 was not silently skipping: it verbalized "My apologies, I encountered
  an issue when processing that value" -- the model *attempted* the call and the
  call was *rejected*. The reject came from the tool schema: `update_form_fields`
  declared its REQUIRED `value` param with **no `type`** (only a description, left
  untyped because value can be string/bool/option-value). SDK 1.38.0 tolerated it;
  2.8.0's stricter validation makes 3.1 reject it. 2.5's native-audio path stayed
  lenient -- which is exactly why the defect read as "3.1 is an unreliable
  tool-caller" (`bd polyglot-pdf-5oq`) rather than a schema bug.

- **Fix.** `backend/config.py`: declared `update_form_fields.value` `type:
  "string"`. The model already sends radio/select + checkbox values as the
  option-value STRING shown in the schema, and the frontend owns boolean coercion,
  so a string type matches real usage without information loss. Stale model-tiering
  comments (the "3.1 ~50%, confabulates trouble saving" narrative) corrected in
  `config.py`, and the `ai-models.md` / `config-deployment.md` current-state docs
  updated to "both models now reliable; the defect was the untyped param."

- **Bundled: bd `polyglot-pdf-l3a.2` (was 46bu) -- empty-env compression parse.**
  Same hazard the VAD_*_MS knobs were hardened against in PR #156:
  `CONTEXT_COMPRESSION_{TRIGGER,WINDOW}_TOKENS` used `int(os.getenv(key,
  "default"))`, which only defaults when the var is UNSET; a set-but-empty value
  (`...=` in an env file) yields `int("")` -> ValueError at import -> backend won't
  boot. Switched to `int(os.getenv(key) or "default")`. Proven: old pattern raises
  on "", new pattern boots clean.

- **Regression guards (unit, no live Gemini).** New
  `backend/tests/unit/test_config_tool_and_env.py`: asserts every REQUIRED tool
  param is typed (would have caught the original bug) and that compression settings
  survive set-but-empty env across a parametrized matrix. The live
  `test_tool_contracts.py` 3.1 case was **un-xfail'd** (it was xfail'd as a "known
  3.1 regression" -- no longer true; it is a real gate now).

## Lessons

- **An SDK bump invalidates behavioral findings, not just code.** The whole
  bisect-ladder plan was aimed at the wrong layer because its premise ("short SI
  works, full SI breaks") was a 1.38.0 artifact. Re-measuring the controls FIRST,
  on the actual installed SDK, turned a prompt-engineering hunt into a one-line
  schema fix. Always verify the installed package version before trusting a probe
  -- the venv lagged the merged pin.
- **"Model under-calls the tool" can be a schema-validation reject in disguise.**
  The tell was the transcript: the model narrated a processing error rather than
  going silent. A required param with no type is invalid under stricter SDKs;
  lenient models mask it, strict ones expose it -- which looks like a model-quality
  gap but is a contract bug.
- **Un-pushed dolt = lost beads.** The handoff's substance survived only because
  it was also in committed files (journal, sprint plan, probe scripts). The tracker
  IDs were gone. Durable handoffs belong in committed artifacts, not just dolt.
