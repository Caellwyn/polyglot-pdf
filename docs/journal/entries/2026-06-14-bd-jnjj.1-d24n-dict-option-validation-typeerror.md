## Trigger

`polyglot-pdf-jnjj.1` (F0) is the hard predecessor for the SI-reduction epic
(`polyglot-pdf-jnjj`): every behavioral-measurement gate in that epic (G1/G2/G3)
must run on a baseline free of silent tool-call failures, so d24n had to be fixed
first. The d24n bug (`polyglot-pdf-d24n`): the production `LiveAIGemini` tool
callback logged `tool_callback_error` / `error_type=TypeError` for
`update_form_fields` ~2-3 times per 20-question gemini-2.5 run (captured in the
wyhh cost-matrix `costs_2.5_*.meta.json` `errors` arrays), and 2.5's confirmed-field
rate was systematically depressed (13-15/20 vs 3.1's 18-20/20), consistent with a
swallowed callback failure losing saves.

## What shipped

**Root cause (confirmed by live capture, not the bead's hypothesis).** The bead
originally guessed an arg-parse / signature mismatch around
`live_ai_gemini.py:1716`. That was disproven: a full static trace of the
`update_form_fields` chain plus a synthetic repro harness
(`scripts/spikes/repro_d24n_update_form_fields_typeerror.py`, 14 model-realistic
arg shapes) produced ZERO TypeErrors -- the success path and arg-parsing are
robust. The real failure is value-shape-dependent and lives on the
validation-ERROR path:

- `backend/utils/field_validator.py::_validate_checkbox` passed the field's RAW
  `options` list as the `ValidationError.valid_options`. The generated form-kits
  store options as `{value, label}` DICTS, so dicts flowed through. (Its membership
  check at the same spot was also comparing selected strings against dict options,
  so dict-option checkbox validation never matched -- a second latent bug.)
- `backend/services/callback_handler.py::_build_update_fields_response` then did
  `", ".join(valid_options[:3])` -> `TypeError: sequence item 0: expected str
  instance, dict found`. The Live adapter's `event.tool_call` path caught and
  swallowed it (`tool_callback_error`, PII-redacted to the type name only), so the
  save silently failed.

It fires intermittently because it only triggers on a dict-option
checkbox/select field that receives an INVALID value (~2-3 such fields per 20q
run) -- which is why offline static reading and the synthetic harness (both on the
success path / `model_turn.parts` path) never surfaced it. `_validate_select`
already extracted string values correctly; `_validate_checkbox` did not, and a
stale comment at the formatter ("valid_options is now a list of strings") masked
the discrepancy.

**Fix (3 layers).**
1. New `_option_values()` helper extracts bare string values from `{value,label}`
   dict options; `_validate_checkbox` uses it for BOTH the membership check and
   `valid_options`; `_validate_select` refactored onto the same helper.
2. Defense-in-depth `str()` coercion at `_build_update_fields_response` so a stray
   non-str option can never crash the formatter again; corrected the stale comment.
3. Regression test `backend/tests/unit/test_d24n_dict_option_validation.py` (6
   cases) reproducing the exact dict-option-checkbox-invalid path end-to-end
   through `on_tool_call`.

**Live before/after verification.** Captured the TypeError on a live 2.5 run of
`scripts/spikes/measure_form_session_costs.py --model 2.5 --arm section-reset
--path happy` with `DEV_LOGGING` on (the dev `.env.DEV` marker enables the full
traceback that production redacts). After the fix, the SAME cell ran clean:
`errors: []` in the meta sidecar and **18/20 confirmed fields** (up from 13-15/20,
now matching 3.1). Both F0 exit criteria met.

**Exit-criteria scorecard (Step 5.5.a).**
- C1 (root cause identified + fixed; new 2.5 run shows zero TypeError events):
  **PASS** -- `field_validator._validate_checkbox` / `callback_handler:713`;
  post-fix meta `errors: []`.
- C2 (2.5 confirmed-field rate >= 18/20 with the fix): **PASS** -- live run
  reported `confirmed fields: 18/20`.

**Fresh-eyes assess (Step 5.5.b, sonnet, 2 rounds).** Round 1: `GAPS-FOUND (1)` plus
two sub-findings. The gap -- both exit criteria require a live-2.5-run result, but
no run artifact was committed (a diff-only reviewer couldn't verify them). Adopted:
added `scripts/spikes/d24n_dict_option_typeerror_findings.md` with the captured
traceback + a before/after table (2-3 TypeErrors -> 0, `errors:[]`, 18/20) as the
durable record (the raw meta.json stays reproducible/uncommitted -- the `data/` dir
holds many such artifacts). Sub-finding (adopted): the repro harness's schema had
NO dict-option checkbox, so it never actually reproduced d24n -- it only *disproved*
the arg-shape hypothesis. Added a real dict-option checkbox/select repro block (PRE-fix
raises, POST-fix clean, with a valid-selection case proving no false rejection) and
reframed the docstring honestly. Sub-finding (noted, not fixed -- low/not-a-regression):
`_option_values` silently drops a dict option with no `value` key, matching the
prior `_validate_select` behavior and unreachable given Pydantic's `value: str`.
Round 2: `NO-GAPS` (one cosmetic markdown-fence defect in the findings doc, fixed
inline). **Codex outer review: ERROR -- account code-review usage limit reached**
(quota, not a finding). Per review-flow doctrine, when Codex is unavailable the
pre-PR fresh-eyes `NO-GAPS` verdict is the review record; PR #195 was handed to the
maintainer on that basis.

## Lessons

- **An intermittent, value-shape-dependent TypeError on a swallowed path cannot be
  root-caused by static reading or a synthetic success-path harness** -- it needed
  a live run of the real measurement instrument with dev logging on to print the
  traceback production redacts. The cheap repro harness was still valuable: it
  *disproved* the bead's hypothesis and narrowed the search to the error path.
- **Two option-shape handlers drifted:** `_validate_select` handled `{value,label}`
  dicts; `_validate_checkbox` did not. When two parallel validators consume the
  same schema shape, factor the shape-handling into one helper so they cannot
  diverge. (General enough to note, but kept here -- not promoted to a standard.)
