## Trigger

Bead polyglot-pdf-uov.16 (T3.5, the final Phase-3 item of the spec-driven test
epic uov). Surfaces with existing test nets were originally judged on test DEPTH,
not spec-correctness. This bead re-audits those "green" tests against the derived
spec -- the rule being "do NOT assume green == correct; file a bug bead for any
test that passes against wrong behavior." It is an AUDIT bead: the deliverable is
the audit and the filed findings, not a code change.

## What shipped

A re-audit of five of the six named surfaces (the sixth, idle-timeout, was
already cleaned in bd polyglot-pdf-01y6 / PR #200, so it was excluded here). The
audit fanned out one reviewer per surface, each reading the surface's tests AND
its real source and judging each green test for four failure modes:
self-fulfilling/fake coverage, wrong-behavior encoding (green but wrong),
tautology, and genuine gaps.

Surfaces audited: confirm-loop breaker, FieldValue unwrap, validation/A-number,
JIT/manifest, schema-editor.

**What passed.** The A-Number FORMAT spec (the one the bead specifically flagged
to scrutinize) is correctly encoded on BOTH sides -- `validation.ts` and
`field_validator.py` agree on 7-9 bare digits with an optional A/a prefix and
separators stripped, and the genuine tests (`TestANumberNormalization`,
`test_d24n_dict_option_validation.py`) exercise the real validator. No A-Number
bug. The confirm-loop breaker, FieldValue, and manifest-generation paths mostly
run real production code; their concerns were weak-assertion / gap, not
wrong-behavior.

**Five findings filed (each verified against source before filing):**

- **polyglot-pdf-840i** (test-debt, high confidence): schema-editor
  `PDFViewer.phase4/phase5.test.tsx` are `expect(true).toBe(true)` documentation
  stubs; `phase2`'s page-clamp test makes no assertion; jsdom's zero
  `getBoundingClientRect` makes the auto-scroll/fit-width tests unable to
  distinguish right from wrong; `usePDFDocument` cleanup asserts on the test's own
  local var, never that `destroy()` was called.
- **polyglot-pdf-nx6g** (test-debt, high confidence): four classes in
  `test_field_validation_responses.py` and all of `TestCallbackHandlerJITIntegration`
  mock the unit-under-test wholesale -- they stay green even if the validator / JIT
  logic were deleted (the self-fulfilling-mock pattern, the same class as 01y6).
- **polyglot-pdf-979r** (green-but-wrong product bug, verified PDFViewer.tsx:257):
  the toolbar renders `'1 fields'` (no singular), and the test hardcodes the wrong
  plural -- so a singular/plural fix would break the test rather than the bug being
  caught.
- **polyglot-pdf-h2ii** (latent product bug, verified): `get_next_field_schema_for_jit`
  never calls `should_include_schema_in_response` (dead code at
  `manifest_service.py:141`), so a repeat confirm of the same field re-delivers the
  JIT schema -- the duplication JIT exists to avoid.
- **polyglot-pdf-6oe6** (spec drift, verified both paths): `computeNextField`
  (`value !== ''`) disagrees with `hasUsableValue` (`'' && !required`) for an
  optional field with value `''`, so navigation re-offers it to fill while the
  confirm contract treats it as confirmable; untested.

Lower-severity observations -- a loose `> 0` lower bound on a session-cap test, the
`Real-world Bug Scenarios` block that restates earlier unit tests, tautological
token-estimate assertions, and a frontend-vs-backend asymmetry in whether the
rejected value is echoed (frontend PII-safe, backend echoes to Gemini by design) --
were folded into the relevant finding descriptions rather than filed as separate
beads, to keep the tracker signal-to-noise high.

No code changed in this bead; the fixes live in the five filed beads.

## Lessons

A green-test audit produces a long tail of "weak but not wrong" observations; the
discipline is to file the few that are actually green-but-wrong or
self-fulfilling, and fold the rest into those descriptions rather than minting a
bead per nit. Two patterns recurred and are worth naming repo-wide: (1)
jsdom-bound UI tests that assert a call happened but cannot assert the COMPUTED
result (zero rects, no canvas) are a structural blind spot -- they belong to a
real-browser check, and the testing-standards doc already says so; (2) the
self-fulfilling-mock pattern (01y6's lesson) is not isolated -- it recurs wherever
a test injects a mock for the very unit it claims to cover, so "does the
unit-under-test actually run?" is the first question of any green-test audit.

## Doc freshness

No tier-1/2 doc tracks these test surfaces directly.
`docs/standards/testing.md` already carries the self-fulfilling-mock note (added
in uov.9) and the "green vitest does not prove a canvas/PDF UI" note -- both of
which this audit re-confirmed in the field, so no new doc rule is needed. The
STALE docs closeout flags track files this branch did NOT touch -- pre-existing
drift, not owed here.
