### Tests (12 -> 0 failures)

The 12 failures collapsed to a few root causes, not 12 independent bugs:

- **Coordinate convention (9 tests) -- one decision.** The producer of the schema
  rects (`scripts/bakeoff/acroform_dump.py`) emits PyMuPDF `widget.rect.y0`, which
  is **top-left origin** (PyMuPDF normalizes PDF's native bottom-left; y increases
  downward). So `pdfToScreenCoords` (which does NOT flip Y -- "just scale") was
  **correct**, and the tests (which assumed a `792 - y - height` flip) plus the
  stale `screenToPdfCoords` half (which still flipped) were **wrong**. Fixed the
  inverse function to also not flip (true inverse) and updated the 9 flip-assuming
  cases in `pdfCoordinates.test.ts` + `FieldOverlay.test.tsx` to the no-flip
  convention. The decision was grounded in the producer code, then **proven
  visually**: overlays land on the widgets; a flip would mirror them vertically.
- **Stale test value (1).** Selected-border expected `3px`; the component renders
  `4px` by design (thicker selected border + glow). Test updated to `4px`.
- **Auto-scroll (2).** The tests spied on `Element.prototype.scrollIntoView`, but
  the field-select effect centers via the scroll container's `scrollTo` (the
  `scrollIntoView` path is only the page-nav buttons). Rewired the spy to
  `scrollTo`. They also needed jsdom-canvas plumbing to reach that code: a
  `getContext` stub (jsdom has no canvas backend, so `PDFPage` bailed before
  `onPageLoad`, leaving `pageDimensions` empty) and a render-task `.cancel` mock
  (the existing mock lacked it, crashing cleanup once the render path ran).

### Render lifecycle (found by the real-browser check -- invisible to jsdom)

The visual check (the bead's headline acceptance) surfaced two genuine runtime
bugs that jsdom could never show, because jsdom does not actually render PDFs:

- **"Cannot use the same canvas during multiple render()".** `PDFPage`'s render
  effect re-ran (React 18 StrictMode double-invoke) and `getPage()/render()` are
  async, so a stale run called `render()` on a canvas a newer run was mid-render
  on. Fixed with a per-run `cancelled` flag (guard after the async hops) + nulling
  `renderTaskRef` on cleanup. Root re-render cause: `onPageLoad` was a fresh
  closure each render (a curried `handlePageLoad(pageNum)` factory) -- replaced
  with memoized per-page handlers so the effect stops thrashing.
- **Overlays never appeared (0 of 128).** The field overlays are gated on
  `pageDimensions.current.has(pageNum)`, but that Map is a **ref** populated in the
  page-load callback -- a ref write does not re-render, so overlays never mounted
  on first load. Added a `dimensionsVersion` state bumped on first-store to force
  the overlay pass. (Kept it a ref, not state, so the auto-scroll effect still
  reads it synchronously.)
- **"Worker was destroyed".** `usePDFDocument` cleanup ran on the first StrictMode
  unmount and destroyed the loading task; the second mount then used a torn-down
  worker. Also its cleanup referenced the closure's `document` (stale -- always
  null at cleanup). Fixed with a per-run `cancelled` flag + tracking the loaded
  doc in a local var for cleanup.

### Build / types / lint (tsc + vite build now clean)

- **jest-dom types.** `setup.ts` runtime-extended `expect` with the matchers (so
  tests passed) but never imported the TYPE augmentation, so `tsc` did not know
  `expect` had `toBeInTheDocument`/`toBeDisabled`/etc. Added
  `import '@testing-library/jest-dom/vitest'`. This alone cleared ~54 of 60 tsc
  errors.
- **Remaining type/lint errors** (all pre-existing, red at recovery, masked
  because no clean `tsc` had been run): removed unused `ValidationError` import;
  re-exported `FormConfig` from `schemaLoader` (FormSelector imports it there);
  updated the `phase5` mock schema to the current `FormSchema` shape
  (`source`/`form_metadata`/`parts`...); dropped unused `pageNum` params.
- **Vite build target.** `pdfjs-dist` ships top-level await, which the default
  esbuild target (`es2020`/chrome87) rejects -- this failed BOTH `npm run build`
  and the dev dep-optimizer (so the editor could not even boot in dev with the
  current pdfjs). Set `build.target` and `optimizeDeps.esbuildOptions.target` to
  `esnext`. (Folded in, not a separate bead: it is a one-line config fix and the
  README treats `npm run build` as a first-class workflow, so it is squarely in
  service of "revive to green.")

## Lessons

- **A recovered front-end tool's "boots clean" claim must be checked in a REAL
  browser, not headless/jsdom.** `7a9.2` reported the editor boots with zero
  console errors, but that was the welcome screen -- the moment a PDF actually
  rendered, three runtime bugs fired (canvas race, missing overlays, worker
  destroyed) that jsdom structurally cannot surface (no canvas backend, no real
  PDF render). The visual-confirm step is not a formality; it is where the real
  bugs live. (Generalizes -> noted in `docs/standards/testing.md`.)
- **A test/component mismatch is often ONE convention decision, not N bugs.** 9 of
  the 12 failures were the single Y-flip question; resolve it against the data
  PRODUCER (here `acroform_dump.py`'s PyMuPDF rects), not the test or a stale code
  comment, then prove it visually.
