## Trigger

During Gate 2 (jnjj.27, secretary latency) `gemini-2.5-flash-lite` was 503
UNAVAILABLE for 1hr+ (widely reported), while the sibling `gemini-3.1-flash-lite`
answered fine (~0.4s). A single cheap model can have a sustained outage; without a
fallback, the secretary/validator (which both run on the cheap text model via
`TextAIGemini`) would simply be down. This bead ports the probe-level fallback chain
(built in jnjj.27's latency probe) to the PRODUCTION `TextAIGemini` adapter.

## What shipped

`backend/adapters/text_ai_gemini.py` -- a model-fallback chain inside the one
chokepoint both `validate()` and the future secretary `ask()` route through
(`_generate()`):
- Constructor builds an ordered, de-duplicated `_model_chain`: the configured model
  first, then `DEFAULT_FALLBACK_MODELS` (`gemini-3.1-flash-lite`,
  `gemini-flash-lite-latest`). Overridable via a new `fallback_models` param.
- `_generate()` walks the chain. On a transient AVAILABILITY error it tries the
  next model; otherwise it re-raises. The transient set (`_is_transient_availability`):
  **5xx ServerError** (overload/outage) and **404/429 ClientError**
  (model-not-found / rate-quota). **400/401/403** (bad-request / auth / config) are
  NOT transient -- they fail fast and are never masked, since every model would fail
  the same way.
- Logs which model served each call (`model=`, `is_fallback=`) so a prolonged
  fallback period is visible in telemetry. PII discipline unchanged (ids/counts/
  tokens only, never values).
- `validate()`'s fail-open is preserved -- the fallback REDUCES how often fail-open
  fires (a sibling answers instead), it does not replace it. The future secretary
  `ask()` inherits the chain for free via the shared `_generate()`.

All chain members are Gemini, so the "BAA covers Gemini only" constraint holds (no
new vendor). NOTE for the maintainer: confirm `gemini-3.1-flash-lite` specifically
is in-scope for the signed BAA before this serves real PHI (version-level check; the
policy doc enumerates the vendor, not model versions).

Tests: `backend/tests/test_text_ai_fallback.py` (12, all passing) -- 503/404/429
fall back; 403/400 fail fast (chain not walked); all-models-down re-raises AND
`validate()` fail-opens; custom `fallback_models` override; chain de-dup; and (added
in the pre-PR assess) structlog `capture_logs` assertions that a fallback call logs
`is_fallback=True` and a primary call logs `is_fallback=False`.

Pre-PR fresh-eyes assess: 1 round, GAPS-FOUND(1) then NO-GAPS. The gap: exit
criterion 2 literally requires verifying the `is_fallback=true` LOG, which the
initial tests asserted behavior for but not the log line -- added the two
`capture_logs` tests above. Also adopted a clarity fix it flagged: dropped a dead
`or getattr(exc, "status_code")` branch in `_is_transient_availability` (the SDK
always sets `.code`).
