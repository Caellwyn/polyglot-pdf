## Trigger

Sprint-6 epic `polyglot-pdf-s4dp` (editor authoring power, plan
`docs/sprint_6_editor-authoring-power_plan.md`) is the demand-gated fix for four
walls a real W-7 touch-up (`ue5s`) hit in the schema editor. B1 is the
highest-friction wall and the blocker for the other three children: the editor
could VIEW a consolidated `options[]` field but could not CREATE one. A real
form's "check one box" radio group (e.g. W-7 `reason_a..e`) arrives from
extraction as N separate radio/checkbox fields, forcing the author into
hand-edited JSON to consolidate them. This is the field merge/split work the
closed Track-A editor epic (`hid`) intentionally deferred until a real touch-up
proved the need; that gate fired on the W-7 pass.

## What shipped

A pure merge/split util plus the editor wiring to drive it. The backend model +
runtime already consume the consolidated shape (`FieldOption.pdf_field_name`,
`consolidated_widgets[]`) -- this is purely an editor-side mutation.

- **`schema-editor/src/utils/fieldGrouping.ts`** (new): pure `mergeFields`,
  `ungroupField`, `canUngroup`, `isGroupableField`. Merge collapses N separate
  radio/checkbox fields into ONE field with an `options[]` array, each option
  carrying its source widget's `pdf_field_name`, plus `consolidated_widgets[]`
  mirroring the option values -- byte-for-byte the runtime's real consolidated
  shape (verified against `schemas/i-90/i-90_schema.json`'s `p1_checkbox4`).
- **`types/schema.ts`**: `FieldOption` gained `pdf_field_name` (the editor's type
  was missing it, though backend/runtime have it) plus `spoken_label` /
  `label_translations`, so a load -> edit -> save round-trip does not strip
  backend option metadata.
- **`App.tsx`**: `groupSelection` state + `handleMergeFields` /
  `handleUnmergeField`, reset on every form switch / kit open / kit clear.
- **`FieldList.tsx`**: a per-field merge checkbox (only on groupable
  radio/checkbox fields) + a merge action bar that appears once 2+ are ticked.
- **`FieldEditor.tsx`**: an "Ungroup" button on consolidated fields
  (`canUngroup`).
- **`test/setup.ts`**: stubbed `Element.scrollIntoView` -- a jsdom gap that
  surfaced (as an uncaught post-test `TypeError`) when a selection-driven test
  triggers FieldList's auto-scroll effect. Shared fix, not specific to this
  feature.

**Decisions (mine -- implementation/internal structure, decide-by-default):**

- **Merge primary = first-selected field.** Its id, section_id, spoken_name,
  help, validation survive; keeping the primary's id means existing `show_if` /
  `controls_fields` references to it stay valid, and the field-list position
  barely shifts. The plan explicitly left "which field's id/section/spoken_name
  wins" to me.
- **Un-merge reconstructs from option data (no stash key).** Rather than stashing
  each original `FormField` on the option to guarantee byte-perfect reversal, the
  un-merge rebuilds one separate field per option from `value` (-> id),
  `pdf_field_name`, and `label`. This keeps the saved schema clean (no private
  keys polluting the JSON; matches the real i-90 consolidated shape exactly) at
  the cost of not restoring rich per-source metadata that simple radio/checkbox
  widgets rarely carry. The exit criterion is "un-group restores the separate
  per-widget fields," which reconstruction satisfies.
- Un-merge de-dupes a reconstructed id against surviving + already-rebuilt ids so
  a collision can't silently merge two fields back together.

**Exit-criteria scorecard:** crit 1 (merge 5 -> one field, 5 options each with
pdf_field_name) PASS; crit 2 (un-merge restores separate fields, reversible)
PASS. Verified by `fieldGrouping.test.ts` (27 tests, W-7 `reason_a..e` scenarios
+ the fresh-eyes + Codex-fix cases) and `App.grouping.test.tsx` (4 tests, full UI
wiring incl. the cross-section disable). Full editor suite green (246 tests);
`tsc --noEmit` clean.

**Fresh-eyes assess (2 rounds, Sonnet, pre-PR).** Round 1 found 3 correctness
gaps (dangling refs, type loss, empty-array contract); all fixed. Round 2
`NO-GAPS`.

**Codex review (PR #256) drove a deeper redesign.** Codex cross-referenced the
actual runtime consumers (`shouldShowField`, `pdf_fill_routes`) and real schemas
and surfaced 8 P1 findings the fresh-eyes pass missed -- all real, all fixed:
1. A merged-away widget's `show_if: {operator: is_checked}` rewritten to the
   primary kept `is_checked`, which never fires against a radio. Now rewritten
   with correct semantics -> `{operator: equals, value: <option value>}`.
2. Non-primary sources' own `controls_fields` were dropped by the `{...primary}`
   spread. Now carried onto the merged radio, re-keyed to fire on their option
   value.
3. A global selection let fields be merged ACROSS sections (silently moving a
   field in the Form > Parts > Sections hierarchy). Now rejected
   (`mergeBlockReason: 'cross-section'`) + the UI disables Merge with a reason.
4. Un-merge rebuilt from a whitelist, dropping `help`/`validation`/`show_if`/
   `controls_fields`/etc -- destructive for hand-authored I-90 groups. **Core
   redesign:** merge now STASHES each source field's complete original object +
   the dependent-conditional rewrites under a private `_ungroup` key; un-merge
   restores them verbatim (lossless inverse). The whitelist rebuild is now only
   the FALLBACK for a hand-authored consolidated field that has no stash.
5. The Ungroup button was nested under the select/radio-only Options block, so
   consolidated CHECKBOX groups (I-90 `p3_race`) could not be split. Moved to its
   own block keyed on `canUngroup(field)`.
6. Merge allowed a source without a `pdf_field_name` (unfillable + non-reversible
   option). `isGroupableField` now requires one; UI explains the block.
7. Un-merge did not revert dependent conditionals -- now restored from the stash.
8. (paired with 1/7) the same conditional-semantics gap on the reverse path.

This reversed the earlier "reconstructive, no-stash" decision (kept for the
no-stash fallback only): Codex correctly showed reconstruction is lossy for real
hand-authored groups carrying conditional logic.

## Lessons

The schema editor (`schema-editor/`) and the voice-app frontend runtime
(`frontend/src/schema-forms/`) maintain SEPARATE TypeScript copies of the schema
types. The editor's `FieldOption` had drifted behind the backend model (missing
`pdf_field_name`) -- a VIEW path tolerated the gap, but a CREATE path could not.
When adding editor authoring for a shape the runtime already consumes, check the
editor's type against `backend/models/form_models.py` (the source of truth for
shape), not just the editor's own types. This echoes the `controls_fields`
drift caught earlier (the editor's type was a stale single-object vs the
canonical list).
