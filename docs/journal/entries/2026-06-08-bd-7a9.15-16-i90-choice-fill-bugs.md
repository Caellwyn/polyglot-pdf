## Trigger

`bd polyglot-pdf-7a9.15` + `bd polyglot-pdf-7a9.16` -- two live I-90 /fill-pdf
correctness bugs surfaced by the 7a9.14 round-trip harness. Bundled into one PR
(both are I-90 choice-field fill fixes in the same file/schema, individually too
small for separate cycles).

## What shipped

Two production fixes + regression tests that drive the REAL /fill-pdf route.

**7a9.16 -- read-only unlock never fired.** `apply_field_flag_changes`
(backend/routes/pdf_fill_routes.py) read `pdf_field_flag_change` from
`conditional_behavior`, but every I-90 gold field stores it under
`conditional_logic` (`conditional_behavior` carries only `unlock_method`). So the
descriptor was never found and 16 read-only fields stayed locked: previous-name
(shown when name changed), apt/suite/floor numbers, accommodation text, interpreter
language, representative name, etc. Fix: the helper now reads the descriptor from
`conditional_logic` first, then `conditional_behavior` as a fallback; it takes the
whole `field_obj` and the 4 call sites pass it. PyMuPDF writes `field_value` even on
a read-only widget, so the observable effect of the unlock is the read-only FLAG
being cleared in the output PDF (a viewer then renders the field editable, not
locked) -- that is what the test asserts.

**7a9.15 -- p3_race (Race "select all") would not fill.** Its 5 option
`pdf_field_name`s dropped the `[0]` widget index (`P3_checkbox7_White` vs the real
`...White[0]`), so the filler's exact-then-endswith `find_widget` never matched and
Race silently did not fill; it also used semantic `option.value`s
(`"white"`/`"asian"`) off the I-90 widget-leaf convention. Fix: brought p3_race onto
the same convention every other I-90 choice field uses (full-path `pdf_field_name` +
widget-leaf `value`). Safe because the frontend is generic (`CheckboxField` sends
back whatever `option.value` the schema defines) and no code hardcodes the old
semantic strings (verified by grep). The other demographic dropdowns
(`p3_ethnicity`/`p3_eye_color`/`p3_hair_color`) still use semantic values -- that
vocabulary is the open product call in `bd polyglot-pdf-7a9.13`, deliberately out of
scope here.

Verification: the 7a9.14 round-trip harness now scores the I-90 gold **28/28 choice
fill (was 23/28)**; both new tests were confirmed to FAIL on the pre-fix code and
PASS after. Full backend suite: **219 passed**.

Decisions made autonomously:
- Read the unlock descriptor from EITHER key (logic-first, behavior-fallback)
  rather than only switching to conditional_logic -- tolerant of both the gold's
  current shape and whatever future extractors emit; reversible.
- Brought p3_race fully onto the widget-leaf convention (fixing both its missing
  [0] and its semantic values at once) rather than only appending [0] -- it matches
  every other I-90 choice field and the 7a9.14 contract, and is safe given the
  generic frontend. The broader demographic-value vocabulary stays for 7a9.13.
- Folded a tiny ASCII cleanup (2 pre-existing non-ASCII arrows in the file's
  docstring/Field) into this PR since I was already editing the file -- removes a
  cp1252 crash hazard (scar #6); trivial, in-file, noted here.
- Bundled both beads into one PR (same surface, small).

## Lessons

- **PyMuPDF writes field_value even on a read-only widget.** The read-only bit does
  NOT gate the programmatic write -- it gates viewer editability. So a "did the
  value land?" check does not prove an unlock fired; assert the read-only FLAG in
  the output instead. (Generalizes to any read-only-unlock verification.)
- **A schema can pass the name-match scorer yet not fill** (p3_race: names off by a
  `[0]` suffix the exact-then-endswith match can't bridge). The round-trip harness
  is what catches this class -- both bugs here were invisible to the old proxy.
