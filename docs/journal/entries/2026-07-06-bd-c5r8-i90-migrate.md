## What the equivalence harness caught (and drove)

The harness surfaced defects that lint + model_validate MISSED -- exactly its job:
1. **Standalone-unwrap dangling ref.** When a 1-option checkbox unwraps to a
   standalone boolean, its option value vanishes, so a dependent's `equals <that
   value>` can never fire on the now-boolean trigger -- silently turning "show
   when checked" into "always hidden" (3 `p4_line1*` fields). Fixed in the script:
   such an `equals` is rewritten to `is_checked` (the standalone idiom);
   `not_equals` -- which has no clean v2 idiom -- is REPORTED, not mis-rewritten
   (i-90 has none). The controls-mirror check got the matching fixup so a genuinely
   mirrored edge on a standalone checkbox still drops cleanly.
2. **Harness value-modeling bugs** (in the test, not the migration): a v1
   1-option-or-multi-option checkbox is a GROUP (array value), not a boolean --
   fixed the trigger-value model, which removed 3 false divergences.

## The 3 intended divergences (maintainer-approved)

`p4_checkbox1a/b/c` (Part-4 disability-accommodation checkboxes) had a v1 show_if
using `is_checked` on a RADIO trigger -- ALWAYS FALSE in both v1 evaluators (a
dead condition; the fields never showed). The migration rewrites `is_checked` ->
`is_not_empty`, so they now show once the Part-4 Yes/No is answered -- the
author's clear intent. The maintainer chose "fix to intent" (2026-07-06) over
preserving the dead condition. This is a deliberate, DOCUMENTED live-behavior
change: the equivalence harness allowlists these 3 fields and POSITIVELY pins the
new behavior (v1-hidden -> v2-shown), so a future regression re-forces the
decision.
