## Trigger

bead polyglot-pdf-jnjj.43, picked up right after the secretary went live (jnjj.45
closed). Gate 2 (jnjj.27) measured the blocking ask_secretary lookup at median
~1s but with a heavy, unpredictable tail -- 2 of 98 calls spiked to 8.5s and
20.2s (not retries, not correlated with cache state). The interim guard shipped
with jnjj.45 was a single 8s blocking timeout that fail-opened to an apology: the
principal could sit silent for up to 8s, then apologize. A 20s silent gap
mid-conversation is a real UX failure. This bead replaces that with a short
deadline + asynchronous delivery of a slow answer.

## What shipped

The synchronous ask_secretary tool call now waits only **SECRETARY_DEADLINE_S**
(~2.5s). The median (~1s) lookup still resolves on the fast path
(`status: ok` -> the principal voices the answer). Past the deadline the tool
returns `status: pending` -- the principal's turn is freed (told to wait, NOT to
answer or re-ask) -- and the still-running lookup is **detached** to deliver its
answer on a follow-up turn via `send_client_content` when it lands.
**SECRETARY_TIMEOUT_S** stays the hard cap on the model call itself (both the sync
wait and the detached lookup are bounded by it).

**Design decisions (maintainer, 2026-06-29), two of which reversed an in-progress
draft:**
1. **No spoken live-model filler.** The first draft had the principal voice "let
   me check that for you" on the deadline. The maintainer flagged that a live-model
   turn is expensive (audio-out tokens + a round-trip) just to stall -- a cost
   lever. The "I'm working" signal is instead the **cheap, gap-based wpw.5 thinking
   indicator**, which spans user-turn-end -> first-response-audio and so covers a
   slow secretary lookup *for free* (a slow lookup just delays the first audio).
   So jnjj.43 spends NO filler turn.
2. **The visual indicator is wpw.5, not built here.** wpw.5's own spec (maintainer,
   2026-06-26) already designed the indicator to be pure-frontend and to cover the
   secretary case with no tool-call wiring. Building a secretary-specific (or
   "shared") indicator in jnjj.43 would duplicate it. So jnjj.43 is purely the
   backend latency guard + async-deliver; the spinner ships with wpw.5.
3. **On the deadline, async-DELIVER the late answer** (vs. proceed-and-drop). The
   user gets the answer moments later as a follow-up turn rather than having to
   re-ask. The deliver instruction anchors it ("as a follow-up to what they asked a
   moment ago"); the wpw.5 indicator showing "thinking..." the whole time is what
   tells the user an answer is still coming, which mitigates the inherent
   non-sequitur risk of a delayed turn.

**Contract change:** `handle_ask_secretary` now returns
`{status: ok|pending|failed, answer}` (was a bare `str`); the callback dispatch
maps `ok`->answer, `pending`->a wait instruction (available=True, no apology),
`failed`->the existing apology. Handler + dispatch tests updated to the dict
contract; +5 tests for the deadline/pending/async-deliver/drop-when-inactive/
drop-empty/end-session-cancel paths.

**Lifecycle (the subtle part):** detached lookups are tracked as `(deliver,
lookup)` pairs. `end_session` cancels BOTH, cancelling + draining the *lookup*
directly from a context that has no pending cancellation of its own -- cancelling a
task that is itself awaiting another does not reliably drain the inner `wait_for`,
which otherwise leaks "Task was destroyed but it is pending." A late answer is
dropped (no push) if the lookup errors/times out/returns empty or the live session
is no longer active.

**Exit criteria:** both PASS. (1) the sync wait is bounded and the turn is freed on
deadline -- verified by injecting a stalled secretary response
(`test_handle_ask_secretary_deadline_returns_pending_then_delivers_async`). (2) the
post-timeout behavior (async-deliver, per the product decision) is implemented and
exercised end-to-end in unit tests (deliver / drop-inactive / drop-empty / cancel).

**Verification scope:** criterion 1 says "verified by injecting a slow/stalled
secretary response" -- the unit tests inject exactly that (`_slow` stub), so unlike
p68s (whose criterion named the voice-harness) a live run was not required here; a
real tail-spike is also nondeterministic to force live. Noted as a deliberate call.

## Lessons

- **A live-model turn is never free -- don't spend one as a stall.** The reflex to
  have the assistant "say something" while waiting costs an expensive audio turn; a
  cheap client-side indicator (gap-based, already specced in wpw.5) is the right
  layer for "I'm working." Recorded so the next "show progress" instinct checks the
  cost.
- **Cancelling a task that awaits another does not drain the inner task.** The
  `end_session` cancel must cancel + await the inner `lookup` from a clean context,
  not rely on the cancelled deliver task to unwind it -- else asyncio leaks a
  pending `wait_for`. General trap for any detached-task cleanup in this codebase.
