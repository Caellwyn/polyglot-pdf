## Trigger

An audit of "empty audio frames" cost/error risk (maintainer concern: noisy
waiting rooms, users walking away with the mic open). The audit re-framed the
real exposure, surfaced a genuine idle-timeout gap, and -- following the thread
into reconnect behavior -- forced a decision on the already-approved session
resumption bead (l3a.3). This entry records the resumption DECISION (declined);
the idle-timeout FIX ships under l3a.4.

## Audit findings (the cost picture)

- **Literal empty frames are a non-issue.** In MANUAL VAD mode the frontend
  explicitly drops all-zero chunks ("CRITICAL: Never send all-zero chunks",
  `audioManager.ts`). In NATIVE mode (the default) that skip is deliberately
  bypassed and continuous audio incl. silence is streamed -- by design, Gemini's
  VAD needs the stream. The only literally-empty artifact is ONE ~2-byte frame
  per session at mic-arm (a worklet render-quantum edge); harmless, no errors.
- **Audio input IS billed, but for real audio, not empty frames.** Across 32
  logged sessions audio-input was 68.5% of input cost (~\$0.67 total). The
  dominant multiplier in ACTIVE sessions is the Live API's per-turn re-billing of
  accumulated context -- not silence.
- **The walk-away gap is real.** Native mode streams continuous silence; the WS
  idle watchdog resets `last_rx` on EVERY received message, INCLUDING those
  silence frames (`websocket_routes.py:256-273`). So an abandoned open mic never
  trips the 120s idle timeout. Cost is linear and non-compounding (no user turns
  -> no responses -> no context re-bill): ~\$0.0045/min (~25 tok/s x \$3/1M).
- **Gemini's 15-min audio SESSION cap is the current backstop**, bounding a
  single walk-away to ~7 cents. `CONTEXT_COMPRESSION_ENABLED` defaults false and
  compression is ruled out (see epic l3a), so the 15-min cap STAYS -- it is a
  real, permanent backstop, not something a future compression flip removes.

## The two-timer fact that drove the resumption decision

The Live API has two distinct limits (Google session-management docs, confirmed
against `docs/genai_docs/live-api-best-practices.md`):

- **Connection lifetime ~10 min** -- the server periodically resets the
  WebSocket. Session resumption exists to span THIS: reconnect with a handle and
  continue the SAME session seamlessly.
- **Session lifetime 15 min (audio)** -- the total cap. Resumption does NOT
  extend past it; once the session clock expires you get a genuinely new session,
  handle or not. Resumption tokens are valid 2h after the last session ends.

So resumption's only job is invisibly surviving the ~10-min connection
reset / GoAway / network blip MID-session.

## Decision: session resumption DECLINED (l3a.3 -> wont-do)

l3a.3 was a fully-designed, "wnt"-approved bead to add resumption on the
unintentional-reconnect path. The maintainer REVERSED that approval on
2026-06-15: the benefit does not warrant the complexity.

- **PII was NOT the blocker.** Gemini retains the conversation server-side for
  its own retention window whether or not we hold a handle; a handle is a pointer
  to context Gemini keeps anyway. It changes neither WHAT is stored nor for HOW
  LONG. The client-owns-state invariant is therefore not a privacy argument
  against resumption -- that mental model was corrected here.
- **Why declined anyway:** reconnect ALREADY rebuilds Gemini context from the
  client-owns-state handshake (field values + section state replayed from
  `sessionStorage`). The ONLY thing resumption adds is the non-deterministic
  in-session residue the handshake does not capture -- recent conversational
  flow, an in-flight turn, prosodic/audio context (e.g. "user just asked to
  repeat the question in Spanish mid-clarification"). That is a marginal UX
  smoothing on involuntary drops, set against real cost: adapter capture of
  `SessionResumptionUpdate.new_handle`, a handle-plumbing decision across the
  STATELESS backend boundary (handle is per-Gemini-session state; a reconnect is
  a new WebSocket), frontend storage + handshake carry, a fresh-vs-stale
  source-of-truth rule, and live-only (`external`) testing on native-audio models
  where type-existence != endpoint-availability.

Net: the cost/complexity is concrete; the benefit is speculative residue. Declined.

## What ships instead: l3a.4 (idle-timeout cost defense)

The walk-away cost is addressed directly and cheaply, server-side only, WITHOUT
client-side VAD and WITHOUT resumption (resumption would PRESERVE an abandoned
session -- the opposite of what is wanted):

- Reset the idle watchdog on Gemini NATIVE-VAD user-turn signals
  (`input_transcription` -> `on_transcript`, which fires ONLY on a real detected
  utterance -- noise/silence do not produce it), NOT on raw mic bytes. So a noisy
  waiting room or a walk-away (audio frames, no detected turn) trips the existing
  120s timeout and routes into the existing `ConnectionTimeoutModal` path.
- Orthogonal to resumption by design: idle-timeout INTENTIONALLY kills an
  abandoned session (fire on no-user-turns); resumption would have PRESERVED an
  active one across an involuntary drop (fire on connection reset). Different
  problems; the declined feature would not have helped this one.

See bd `polyglot-pdf-l3a.4` for the implementation + exit criteria.
