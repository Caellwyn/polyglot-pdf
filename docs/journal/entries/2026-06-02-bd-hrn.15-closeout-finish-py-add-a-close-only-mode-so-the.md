This PR bundles two harness items: the hrn.15 telemetry-dedup fix and a
permission-allowlist tuning (maintainer-directed, surfaced mid-session).

## Trigger

**hrn.15** was filed while dogfooding hrn.13 on PR #58: the two-call review-worthy
closeout pattern (call 1 opens the PR + writes the telemetry row; call 2 closes the
bead after Copilot CLEAN) could append a **duplicate** ledger row if call 2 used
`--close-beads`, because `closeout_finish.py` runs its telemetry step
unconditionally. The maintainer flagged this as a priority — duplicate rows
contaminate the A/B experiment metrics the whole harness-tuning sprint depends on —
and bumped it to P1.

**The allowlist** came from a separate maintainer report: driving the session from
mobile, every action prompted for approval despite "auto" mode. The fix is harness
config, not anything I control at runtime, so it goes in `.claude/settings.json`.

## What shipped

**hrn.15 — `--close-only` mode.** A new flag on `closeout_finish.py` that closes
the bead(s) and does **nothing else** — no commit, rebase, push, PR, or telemetry.
It is the clean second call of the two-call pattern: the first call already wrote
the telemetry row, so `--close-only` writes none, eliminating the duplicate. To let
it omit the PR-opening args, `--branch`/`--pr-title`/`--pr-body-file` and the
review gate moved from argparse-`required` to **`main()`-enforced only for a
PR-opening run** (a `--close-only` call needs just `--bead`). `--close-only`
implies `--close-beads`, skips the branch guard (no push happens), and reports
`RESULT: CLOSED-ONLY`. The SKILL two-call guidance now says **use `--close-only`,
NOT `--close-beads`, for call 2**, with the double-count reason spelled out.

**Permission allowlist** (`.claude/settings.json`). Per maintainer direction —
"`git push` and `bd` are routine; gate merging and deploying" — added broad allows
for the workhorses (bd dolt push / create / update / close / dep; git add / commit
/ push / fetch / pull / checkout; gh pr create / comment; the backend venv
interpreter running each harness script + pytest) and a new **`deny`** block for
the dangerous ones (`git push --force`/`-f`/`--force-with-lease`, `gh pr merge`,
`firebase`/`npx firebase`, `bd dolt push --force`). Deny outranks allow, so
force-push stays gated even under `git push:*`. Per-script entries (not a blanket
`python:*`) keep arbitrary code execution off the allowlist.

**Decisions noted:** chose a dedicated `--close-only` mode over a bare
`--no-telemetry` flag (the second call needs to skip commit/rebase/push/PR too, not
just telemetry); added a `deny` block (the `/fewer-permission-prompts` skill says
don't touch deny, but the maintainer's explicit "gate dangerous" instruction
overrides it — confirmed with them). Two follow-up beads filed: **hrn.16**
(closeout_prep.py cp1252 crash, found during this closeout's prep) — a pre-existing
robustness gap, not introduced here.

## Lessons

- **A telemetry double-count is silent and corrosive** — it doesn't error, it just
  quietly inflates the cost numbers the experiment reads. Worth a dedicated,
  hard-to-misuse mode (`--close-only`) rather than relying on the operator
  remembering not to pass `--close-beads` twice.
- **Allowlist tuning is a real lever for mobile/remote driving**, but the safe
  shape is "allow routine reads+writes, deny the irreversible few" — and the
  compound-shell commands (the closeout prep one-liner) can't be allowlisted at
  all, so they remain the residual prompt. Fixing those is a command-style change
  on my side, not a config change.
