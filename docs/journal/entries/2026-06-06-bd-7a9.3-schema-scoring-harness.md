## Trigger

`bd polyglot-pdf-7a9.3`, the metrics backbone of the PDF->JSON authoring epic
`7a9`. The extractor bake-off (`7a9.4`) needs a way to measure a draft (extractor
output) FormSchema against the hand-authored ground truth, scoring the two halves
of the problem SEPARATELY so the recommendation can say "tool X solved field
extraction but not the conditional logic" -- the central (a)/(b) split.

## What shipped

`scripts/schema_score.py` -- a standalone, throwaway scoring harness (reuses the
backend venv; no app imports; ASCII-only/cp1252-safe).

```
python scripts/schema_score.py --draft DRAFT.json --truth TRUTH.json [--json OUT.json]
```

It prints two tables per form and optionally writes the full result JSON:

- **(a) FIELD EXTRACTION** -- detection precision/recall/F1 (TP/FN/FP) plus
  per-attribute accuracy over matched fields: `type`, `pdf_field_name`, `options`,
  `validation`, `section_id`, `pdf_position`.
- **(b) RELATIONSHIP / LOGIC** -- recall per conditional type (`show_if`,
  `controls_fields`, `conditional_fields`, `conditional_logic`,
  `conditional_behavior`, `copy_to`, `overflow_to_supplement`) and structural
  counts (parts, sections, supplements, tables/multi_entry).

### The crux: extractor-id-agnostic field matching

A draft field's `id` is whatever the extractor invented, so the harness NEVER
matches on `id`. It matches on `pdf_field_name` -- the AcroForm widget name, the
one key both schemas derive from the same PDF -- normalized to its dotted leaf and
lowercased, so an XFA full path (`form1[0].#subform[0].P1_checkbox4[0]`) and a
short AcroForm name (`P1_checkbox4[0]`) compare equal. This mirrors the
exact-then-`endswith` logic the production filler uses
(`backend/routes/pdf_fill_routes.py:171`). For radio/checkbox fields whose name
lives on their options (17/132 in I-90), it matches on the set of option-level
pdf_field_names. Fields with no PDF name at all fall back to a fuzzy
`(section, name)` key at >=0.85 similarity.

`pdf_position` and any relationship absent from a form are scored `n/a`, not 0 --
e.g. I-589 has no coordinates and no `controls_fields`, so those rows correctly
read `n/a` rather than dragging the score down.

### Validation -- it scores AND discriminates

Two checks, both required (a harness that always returns 100% is useless):

1. **Self-test (truth vs itself => 100%):** both I-90 and I-589 score 100% on
   every applicable attribute and conditional, 0 FN / 0 FP. Confirms the matcher
   pairs every field and the comparators agree with themselves.
2. **Degraded-draft test (must DROP proportionally):** a synthetic draft of I-90
   with 20% of fields dropped, 5 junk fields added, `pdf_field_name` stripped from
   half, `type` corrupted on a third, and all `show_if`/`controls_fields`/`copy_to`
   removed. Result, exactly as designed: detection recall 80.3% (the drop),
   precision 95.5% (the 5 junk FPs), `pdf_field_name` 50.0%, `type` 86.8%,
   `show_if`/`controls_fields`/`copy_to` 0.0%, untouched attributes 100%. Every
   degradation surfaces in the right cell.

## Lessons

- **Validate a scorer twice: that it scores AND that it discriminates.** A 100%
  self-test only proves the happy path; the degraded-draft test is what proves the
  numbers actually move when quality drops. Without the second test a broken
  always-100% scorer would look "passing."
- **Reuse the production matching rule, do not reinvent it.** Field<->widget
  matching already exists in `pdf_fill_routes.py` (exact-then-endswith); copying
  its normalization keeps the harness honest about how the real system pairs
  fields.
