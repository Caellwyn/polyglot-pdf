## Trigger

The principal-side implementation of bd jnjj.22 (per the approved plan
`~/.claude/plans/we-are-going-to-transient-wall.md`). On Gemini 2.5 the per-turn
system instruction (SI) is 95-98% of cost (the measured invariant in
`docs/standards/logging-and-cost.md`). DTI makes the voice model (the
"principal") carry only a static behavioral backbone + the CURRENT field's
guidance, so the per-turn SI is tiny and ~constant regardless of section size.
This replaces the broken JIT next-field schema-drip (the original jnjj.22 bug)
rather than fixing it.

## What shipped

Tier 1 of DTI, env-gated behind `USE_DTI` (default false), fully reversible:

- **`USE_DTI` + `DTI_SYSTEM_INSTRUCTION`** (`config.py`): the thin template keeps
  the static backbone (LANGUAGE/WORKFLOW/TOOLS/MATCHING/CONSTRAINTS/ADDRESS-
  CONSISTENCY/CONFIRMATION) and has ONE dynamic slot, `{current_field_guidance}`
  (field 1). No whole-form `{fields_json}`, no JIT `{manifest_text}`.
- **Single-source field-guidance renderer:** `manifest_service.get_field_guidance`
  reads the canonical NESTED help block (`help.instructions`/`help.format_hint` --
  the real form-kit/I-90 shape) with flat fallbacks; `ai_context.render_field_guidance`
  turns it into the text block. The SAME renderer feeds field 1 (in the SI) and
  fields 2..N (in the confirm response), so the model sees identical guidance
  whichever path delivers it.
- **Client-supplied guidance (the key correction -- see Lessons):** when DTI is on,
  the frontend sends the next field's FULL schema on `next_field_hint_response`
  (`webFormConnection.ts`, `getFieldSchema`); the backend stashes it on the
  RequestCoordinator and renders it into `response["next_field_guidance"]` in the
  confirm_field handler. No backend schema source -- the client owns the schema.
- **A/B rollout:** `websocket_routes` echoes `jit_mode_enabled |= USE_DTI` (shared
  manifest-first handshake) + a distinct `dti_mode_enabled`. Precedence in
  `build_form_context`: DTI > JIT > legacy (getattr-guarded for stub settings).
- Section switch is UNCHANGED (still close+restart with a smaller SI) -- it stays
  the A/B baseline. Tier 2 (soft section advance) is deferred per the plan, gated
  on the eviction measurement.

Verified (build + unit only): backend 381 pass (10 new DTI tests), frontend 400
pass + tsc clean; on the real I-90 the DTI SI is ~constant and ~28% smaller than
full-SI on the first section, render identity holds, and `help.instructions`
flows through. The LIVE voice-harness behavioral run (R1: the model advances on
`next_field_guidance`) is DEFERRED to the jnjj.25 measurement on the real I-90
(gated on jnjj.24's harness port); R1 is de-risked because DTI reuses the exact
confirm-response mechanism JIT already uses in production.

## Lessons

- **The "bug" was an inverted data-ownership, and the fix had to follow the data.**
  jnjj.22 looked like "make get_next_field_schema read the manifest." But the
  backend genuinely never has field N's schema in JIT/DTI mode -- the CLIENT owns
  it (stateless invariant). So no backend-side fix could work; the guidance had to
  come FROM the client (on the existing next-field-hint round-trip). When a
  cross-tier "drip" returns nothing, check which tier owns the data before trying
  to make the wrong tier produce it.
- **DTI diverged from the external (Gemini) proposal for a good reason.** Gemini
  suggested injecting guidance as a `client_content` text turn; exploration showed
  that ALWAYS forces a spoken model turn on 2.5 (no silent/system-role inject in
  the SDK). The confirm_field tool response is the silent vehicle (the model
  consumes it and advances), so DTI rides there instead. External suggestions get
  verified against the actual SDK surface, same as our own.
- **A unit assertion must encode the property that's actually invariant.** My first
  "DTI SI < full SI" test failed on a 3-field section -- DTI is LARGER there (the
  static backbone dominates; the win is on big sections). The real invariant is
  "DTI SI is independent of section field count"; the test now asserts that.
