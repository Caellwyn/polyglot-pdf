## Trigger

After the i9q8 fix landed (PR #157: typed `update_form_fields.value`, both models
now tool-call reliably), the maintainer asked whether the live demo defaults to
2.5 and what the Cloud Run env actually sets. It does: `deploy-demo.sh` pins
`USE_PREMIUM_MODEL=false` (confirmed live on the service), and the pin's comment
still justified it with the OLD rationale -- "3.1 emits the tool call only ~50% /
confabulates a trouble-saving message" -- which was the untyped-param bug, now
fixed. The maintainer chose to keep 2.5 but fix the stale rationale.

## What shipped

- **A/B measured 2.5 vs 3.1 on the deployed VAD mode** (`native-hi`, genai 2.8.0,
  real audio fixtures, real TOOL_DECLARATIONS, 8 turns/model) via
  `scripts/spikes/diag_turn_reliability_4sv7.py`. Result: a reliability TIE --
  both 8/8 turn registration, 4/4 short-"yes" confirms, zero 1011s, both emitting
  `update_form_fields` + `confirm_field` every turn. The one real difference is
  LATENCY: 2.5 ~0.01s/turn vs 3.1 ~1.75s/turn (~170x). The live fill->confirm
  contract test passed for both models. So 2.5 stays the demo default -- now for
  latency, not for tool-calling.
- **Corrected the stale rationale** (NOT the pin -- `USE_PREMIUM_MODEL=false`
  stands) in the current-state surfaces that still blamed 3.1's tool-calling:
  `deploy-demo.sh` (the `USE_PREMIUM_MODEL` comment), `docs/standards/voice-and-vad.md`,
  `docs/technical_guide.md`, and a `backend/tests/unit/test_model_selection.py`
  docstring (the test itself unchanged; 5 pass). Each now states current state
  plus a pointer to `ai-models.md`, with no history narrative inline.
- The `daa` concern (2.5 ~80% 1011 report) did not reproduce: zero 1011s in this
  run, consistent with the prior 30/30-clean read.
- Fresh-eyes assess: [recorded in the merge ping].

## Lessons

- **Code comments + docstrings are current-state only.** First drafts of this
  change packed the "4p0 set 3.1, 5oq reversed it, i9q8 root-caused it" lineage
  into a comment and a docstring; the maintainer corrected it twice. That history
  belongs in the journal (tier 3); a comment carries current state plus at most a
  one-line bead/journal pointer. Same rule the doc-freshness gate enforces for
  tier-1/2 docs, applied to code.
- **A stale rationale outlives the bug it described.** The "3.1 ~50%" comment was
  copied across four surfaces and survived the fix that invalidated it. When a fix
  changes WHY a config is set the way it is, grep the rationale, not just the code.
