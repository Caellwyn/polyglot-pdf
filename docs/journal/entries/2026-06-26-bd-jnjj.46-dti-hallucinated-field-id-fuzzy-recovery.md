## Trigger

The residual jnjj.40 split off: in DTI mode (one field per turn) the model
intermittently calls `update_form_fields` with a HALLUCINATED field_id -- it keeps
the semantic tail right but mangles the positional head (`p1_line1_familyname` for
the real `p1_line3a_familyname`). The backend rejected these as `unknown_fields`, so
the field never filled. Measured at ~2/10 DTI runs before this bead.

## What shipped

A fuzzy recovery for hallucinated field_ids in
`backend/utils/fuzzy_field_matcher.py` (the one production consumer is
`validation_handler._match_fields`, the existing exact-then-fuzzy fallback for
`update_form_fields`). The matcher previously indexed only `spoken_name` /
`spoken_aliases` / `name` -- never the id -- so a garbled *id* had nothing to match.

The headline finding is that the obvious fix is a TRAP. Indexing the raw id is worse
than the bug:

1. **Raw-id matching SILENTLY MIS-FILLS.** The raw id carries the positional prefix
   (`p1_line1`), so a hallucinated id resolves to whatever PRESENT field shares that
   prefix and APPLIES the value there. A live `--debug` run caught exactly this:
   `p1_line1_familyname` (value "Vasquez") matched `p1_line1_aliennumber`, then
   "Vasquez" failed the A-number pattern. A wrong-filled field is strictly worse than
   a rejected one.
2. **DTI merge-timing widens the trap.** The validation set holds only field 1 plus
   fields merged on each prior `confirm_field`, so the correct target is often not
   yet present when the model calls `update_form_fields`. With raw-id matching a
   hallucination then resolves to a present NEIGHBOR.

The shipped fix is built around "recover the recoverable, REJECT anything that would
corrupt data":

- **Strip the positional prefix** (`strip_positional_prefix`, regex
  `^(?:p\d+_)?(?:line\d+[a-z]?_|part\d+_)+`) before indexing/matching the id, so the
  match keys on the SEMANTIC tail (`familyname`) the model gets right, not the
  positional head it mangles. Conservative: a non-positional id is left untouched,
  and a degenerate all-prefix id falls back to the original (never empty).
- **A strict threshold for id-derived matches** (`ID_MATCH_THRESHOLD = 0.88` vs the
  0.52 spoken-name bar). Legitimate suffix-variant recoveries score >= 0.95; spurious
  id-fragment collisions (`givenname` vs `aliennumber`) sit ~0.60 and are rejected.
  Index entries are flagged `is_id` so only id wins get the strict bar.
- **Dedup candidates by field.id** before the ambiguity check. A field is now indexed
  under several texts (spoken name + stripped id); without dedup a clean single-field
  win read as "ambiguous" because the field's own second entry sat within
  `AMBIGUITY_DELTA` of its best.

**Exit-criteria scorecard:**
1. Root cause identified with --debug evidence -- **PASS.** The model receives the
   exact id in `next_field_guidance` but mangles the positional head; the backend's
   fuzzy fallback never indexed the id. A live `--debug` artifact captured the real
   hallucinations (`p1_line1_familyname`, `p1_line1_givenname`, `p1_line1_uscisnumber`).
2. A mitigation that raises the DTI confirm-rate above ~8/10 -- **PASS.** 12 live DTI
   I-90 (9-field) happy runs with the fix: **10/12 perfect (9/9), 1/12 7/9, 1/12 6/9,
   NO catastrophic 0/6** (vs the jnjj.40 baseline of 8/10 + a 0/6). CAUSAL evidence:
   replaying the REAL captured hallucinations through the fix recovers
   `p1_line1_familyname` -> `p1_line3a_familyname` and `p1_line1_givenname` ->
   `p1_line3b_givenname`; `p1_line1_uscisnumber` (a semantically-different token)
   correctly does NOT force-match. Honesty note: in this particular 12-run batch the
   model sent exact ids 105/106 times, so the fuzzy path did not fire live -- the
   live batch proves NO REGRESSION (no mis-fills, no new failures, catastrophe gone),
   and the unit tests + the replay prove the recovery mechanism on real hallucinations.
3. Re-measured rate over >= 10 runs recorded -- **PASS.** 12 runs, recorded on the
   bead and above.

**Out-of-scope residuals found during re-measurement, filed as new beads (NOT this
fix):** the two imperfect runs are DISTINCT modes -- `8vy3` (the model sends a
WRONG-but-REAL id: off-by-one field-sequence drift, all exact-id-OK) and `fsoa` (the
model sends the CORRECT id but it is rejected unknown: a DTI merge-timing gap where
even fuzzy recovery cannot help because the right field is not in the candidate set).

## Lessons

- **A "did you mean" fuzzy match on an IDENTIFIER is not the same as on a label.**
  Ids share incidental letters and structural prefixes that clear a label-tuned
  threshold and route a value to the wrong field. The safe form keys on the semantic
  part only and demands a near-exact match before acting.
- **Recovering an error must never be able to CAUSE a worse one.** The bar for an
  auto-recovery that WRITES (mis-fill) is far higher than for one that READS. When in
  doubt, reject -- a rejected field is recoverable; a silently mis-filled one is not.
- **Verify the recovery MECHANISM separately from the live score.** The live batch
  happened not to trigger a hallucination, so the rate alone could not attribute the
  improvement to the fix. Replaying real captured hallucinations through the new code
  gave the causal link the aggregate score could not.
