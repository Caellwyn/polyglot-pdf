## Trigger

`bd polyglot-pdf-hi2.1`, the first gate of the re-shaped graph-representation
spike (see the plan in
[`2026-06-05-bd-hi2-graph-form-representation-spike-plan.md`](2026-06-05-bd-hi2-graph-form-representation-spike-plan.md),
since superseded by the three-gate structure). The spike asks whether a graph is
the right representation for polyglot-pdf forms; **Gate 1 is the cheapest possible
kill-point: is the data even graph-shaped, or a tree wearing a graph costume?**

A form is mostly a tree -- Form > Parts > Sections > Fields -- and JSON nesting
expresses a tree natively; you do not need graph machinery for hierarchy. A graph
only earns its keep on edges that **break the tree**: conditional dependencies
that point ACROSS section boundaries. So the gate measures, on a real form, what
fraction of relationships are tree (JSON wins) vs. genuinely cross-cutting (graph
might win).

## What shipped

A throwaway structural analysis of **I-90** (`form-kits/i-90/schema.json`: 132
fields, 16 sections, 8 parts, 0 supplements). No artifact wired into the app.

**Result -- decisive STOP at Gate 1.** Of the field-to-field conditional edges in
I-90, **effectively zero genuinely cross the section boundary.**

| Edge type | count | cross-section (raw) | cross-section (real) |
|-----------|-------|---------------------|----------------------|
| `show_if` | 19 | 0 | 0 |
| `hide_if` | 0 | -- | -- |
| `controls_fields` (shows/hides/unlocks/locks/required) | 21 | 1 | 0 |
| `conditional_fields` | 22 | 6 | 0 |
| **field->field conditional edges** | **62** | **7 (11%)** | **0 (0%)** |
| `copy_to` | 4 | (4) | 0 (self-duplicate) |
| `overflow_to_supplement` | 0 | -- | -- |
| `conditional_behavior` (PDF bit-flip attr, not an edge) | 16 | n/a | n/a |

The 7 raw "cross-section" hits were **false positives**: every one targets an
**array-index variant** of a field whose base ID lives in the same section
(`p2_checkbox3[4]`, `p7_checkbox7extend[1]`, ...). Stripping the `[n]` suffix
resolves all 7 back to the controller's own section. True cross-section count:
**0 of 62.**

The 4 `copy_to` edges are a field copying to **its own `[1]` duplicate** (the same
A-number / name repeated on a later page) -- "mirror this value to its twin," a
flat key->key map, not a cross-field dependency or a traversal.

**Attribute catalog (the ~40-attribute discovery the plan asked for).** Of the
attributes actually present on I-90 fields, the breakdown by whether they are
graph-edge-shaped:

- **Structural edges (graph-relevant):** `section_id` (containment -- tree),
  `show_if`/`controls_fields`/`conditional_fields` (conditional -- but all
  intra-section), `copy_to`/`copy_from` (self-duplicate mirror).
- **NOT edges -- per-field scalar/behavioral attributes** (graph adds nothing):
  `id`, `name`, `type`, `spoken_name`, `help`, `question_number`,
  `consolidated_widgets`, `pdf_position`, `pdf_field_name`, `label`, `max_length`,
  `options`, `read_only`, `validation`, `multiline`, `is_comb`,
  `conditional_logic`, and `conditional_behavior` (the raw-PDF-bit-flip imperative
  attribute -- the messiest non-graph item, present 16x).

**Verdict:** I-90 is overwhelmingly a **tree with purely intra-section conditional
logic.** Within a section, `show_if`/`controls_fields` are local sibling
references that JSON already expresses trivially and that the existing renderer +
backend already consume. There is no cross-cutting edge structure for a graph to
model. **Gate 1 KILLS the graph hypothesis for I-90** -- the effort does not
proceed to Gate 2 (Neo4j-vs-dict efficiency) or Gate 3 (cost/approach) on the
strength of this form.

**Caveat / generalizability (honest scope).** This is ONE form. I-90 is a
relatively flat single-applicant form. The result is strong evidence, not proof
for all USCIS forms -- I-589 (asylum, with cross-referencing narratives,
supplements, and repeating groups spanning parts) is the most likely place a real
cross-section edge would appear. The recommendation (below) accounts for this: the
gate is failed *for I-90*, and the cheap next check before fully abandoning the
runtime-graph idea is to re-run this same intra-vs-cross analysis on I-589, which
costs an hour and no Docker.

## Lessons

- **"Already ~70-80% graph-native" (the prior plan's framing) conflated
  tree-shaped with graph-shaped.** The schema IS an edge list in form_models.py
  -- but the edges are containment (tree) and intra-section siblings, which JSON
  nesting handles natively. Being expressible AS a graph is not the same as
  NEEDING one. The discriminating question is cross-cutting edges, and I-90 has
  none.
- **Section-local conditional logic is why the connection-reset-per-section
  pattern works at all.** If conditionals routinely spanned sections, dropping the
  Gemini connection at section boundaries would lose dependency context -- the fact
  that it doesn't is corroborated by this 0%-cross-section finding.
- This generalizes (recorded via `bd remember`, the repo-discoverable home for
  scar tissue): evaluate "should this be a graph?" by the cross-cutting-edge
  ratio, not by whether the data has *any* references. No `docs/standards/*` doc
  is a natural home for a data-structure-evaluation heuristic (they are all
  operational concerns), so it lives in the journal + bead memory, not a forced
  standards edit.
