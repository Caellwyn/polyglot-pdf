## Trigger

Capstone of Pillar B (SI-reduction epic, `polyglot-pdf-jnjj`). B3 (jnjj.15) built the
validator SERVICE; B4 (jnjj.16) made the client emit `section_complete` /
`form_complete` boundary events that the backend received + acked (log-only). B5
wires the verdict into action: run the validator at each boundary, push the result
to the client, and -- on a conflict -- steer the live voice model back to verify,
while preserving the user's override and bounding re-steers so a re-confirmed value
can't trap the user in a loop.

## What shipped

**Backend (`form_filling_service.py` + `websocket_routes.py`):**
- `handle_validation_boundary(fields)` -- constructs `ValidatorService` from
  `self._text_ai`, validates the contract-2 `fields`, and on a SURVIVING conflict
  injects a steer into the Live session. Returns the SURVIVING (post-suppression)
  verdict: a suppressed conflict is omitted so it reads as clean to the client and
  the section switch is not held (see the fresh-eyes fix below -- returning the full
  list trapped a user who used the override hatch).
- `_compose_validator_steer(conflicts, fields)` -- builds the in-band instruction:
  names the field(s) by their human `name` (criterion 1) and carries the legacy
  user-override escape hatch verbatim ("Accept the user's answer if they confirm ...
  do not insist", criterion 2) so B is never stricter than the in-SI ADDRESS
  CONSISTENCY prose it supplements (which STAYS -- config.py:469/533 untouched).
- `_suppress_already_steered(conflicts, fields)` -- PER-FIELD max-resteer bound
  (criterion 3): drops any conflict referencing an already-`steered:true` field
  (read from the incoming payload -- the marker is client-owned, the backend is
  stateless). `_inject_validator_steer` only delivers into a LIVE session (mirrors
  the secretary async-deliver guard) via `LiveAIGemini.send_client_content`.
- The two WS arms now call `handle_validation_boundary` and push a
  `validation_result` envelope (`{type, conflicts}`) to the client for EVERY
  boundary incl. clean (`conflicts:[]`) -- the FE's deterministic clean->resume
  signal. PII-safe: counts only logged; the `reason` rides the in-band steer (not a
  log sink), never a `_log` kwarg (contract 6).

**Frontend (`webFormConnection.ts` + state):**
- `validation_result` dispatch case -> `handleValidationResult`: clean resumes the
  paused switch; a conflict marks the named fields `steered:true` in sessionStorage
  (`SchemaFormStateManager.markFieldsSteered`, new) and HOLDS in-section (the live
  model, already handed the steer, voices it). The marker survives the switch /
  reconnect and rides the NEXT contract-2 payload -- the client half of the
  max-resteer bound.
- `proceedSectionSwitch` is now a validator GATE (contract 4 ordering): it parks the
  switch and awaits one of -- clean verdict (`resolvePendingSectionSwitch` ->
  switch), conflict (`cancelPendingSectionSwitch` -> stay, `sectionSwitchCancelled`),
  or a fail-OPEN timeout (`VALIDATOR_GATE_TIMEOUT_MS = 6000` -> advance unchecked, so
  a validator/socket outage never strands the user).
- `buildValidatorFields` reads the real `steered` marker (B4 hardcoded `false`);
  `FieldValue` gains the client-owned `steered?: boolean`.
- The B4 duplicate-confirm guard now also checks `pendingSectionSwitch` -- B5's gate
  introduced a window where `switchInFlight` is not yet set (the switch is parked at
  the validator), through which a duplicate confirm could emit a second
  `section_complete`; guarding on both states keeps it to exactly one per boundary.
- `disconnect` releases a parked gate (resolves the promise + sets cancelled) so its
  fail-OPEN timer can't later fire a switch into a torn-down connection -- and so the
  awaiting `proceedSectionSwitch` never hangs.

**Fresh-eyes adversarial assess (pre-PR, Sonnet):** round 1 found a SERIOUS
user-stranding bug (criteria 1+2 FAIL). `handle_validation_boundary` returned the
FULL pre-suppression conflict list, not just the surviving conflicts. So once a user
overrode a conflict (both fields steered:true), a later boundary correctly suppressed
the STEER but still returned the conflict to the client -- which gated the section
switch on it and HELD the section forever, with no steer voiced. The user who used
the override escape hatch was trapped. Fix: return `{"conflicts": surviving}` -- a
suppressed conflict reads as CLEAN to the client (the fields are already marked
steered, so nothing is lost), and the switch resumes. Added a regression test
(`test_override_does_not_trap_the_user_switch_gate`) + updated the suppression tests
to assert the clean return. Fresh-eyes also flagged a test-coverage gap (form_complete
didn't assert validation_result -- added) and a low-confidence latent gate bug (a
stale-gate eviction could fire two switches); I hardened the gate by moving the
`cancelled` flag ONTO the per-invocation gate object (was a shared instance flag), so
a stale gate can never make a newer switch fire. Round 2 returned NO-GAPS. Adopt 3 /
reject 0 / defer 0; no out-of-scope beads filed.

**Codex outer review (PR #275):** round 1 returned SIX P1 findings -- all real,
several sharing the "return a conflict the client can't resolve -> permanent trap"
root cause that the fresh-eyes fix only partially closed. All adopted:
1. **markFieldsSteered missed the `[]` alias.** The verdict echoes the schema id but
   the value can live under `id[]`; the marker landed nowhere -> next payload
   steered:false -> infinite re-steer. Fixed: mirror buildValidatorFields' bracket
   fallback.
2. **The validator await blocked the WS receive loop.** A hang past the 6s FE gate
   kept the loop busy so the client's own fail-OPEN manual_section_switch couldn't be
   processed. Fixed: backend-side asyncio.wait_for (VALIDATOR_TIMEOUT_SEC=4.0, under
   the FE gate) -> fail-OPEN clean on timeout.
3. **Inactive-session path returned conflicts but no steer.** A dropped steer (dead
   session) still returned the conflict -> FE held the section with nothing voiced.
   Fixed (the structural fix): _inject_validator_steer now RETURNS the conflicts that
   ACTUALLY DELIVERED, and handle_validation_boundary returns only those -- a
   dropped/failed steer reads as clean (the model never got it, so don't trap).
4. **steered marker lost on field edit.** updateField replaced the FieldValue without
   carrying steered forward -> editing an adjudicated field re-steered it. Fixed:
   updateField preserves prior steered unless the incoming value sets its own.
5. **Conflicts on unknown fields survived.** A hallucinated/misspelled field_id the
   client can't mark steered -> permanent trap. Fixed: _suppress_already_steered now
   also drops any conflict referencing a field not in the payload (and malformed
   empty-id conflicts).
6. **Duplicate confirm reset the gate timer.** A duplicate confirm re-parked the gate
   (resetting the 6s fail-OPEN timer, no new validator request) -> repeated duplicates
   delayed the advance forever. Fixed: a duplicate while a gate is parked is a no-op
   (the original gate owns the boundary).
   Each fix has a regression test.

**Codex round 2 unavailable -> Opus-4.8 fallback reviewer (PR #275, Step 7.5):**
Codex returned a quota ERROR on the re-review, so per the closeout doctrine the
review routed to the Opus-4.8 fallback. It found FOUR more gaps, the top two real
and serious -- both interactions the prior rounds did not trace:
1. **Mic-off deadlock on a conflict-hold (the worst one).** The confirm handler ran
   the audio teardown (clear queue, STOP mic capture) BEFORE the gate resolved. In B4
   a switch always followed (restarting the mic); in B5 a CONFLICT verdict HOLDS the
   section so the model can voice "verify which is correct" -- but the mic was already
   off, so the user could not answer. Fix: the audio teardown MOVED into
   doSectionSwitch, which runs ONLY when the switch actually proceeds (clean /
   fail-OPEN), never on a conflict-hold. The mic now stays live while the steer plays.
2. **Steer delivery over-reported.** _inject_validator_steer relied on
   send_client_content RAISING on failure, but the adapter SWALLOWS its own send
   exceptions and returns normally -- so a steer that never reached Gemini was reported
   "delivered" and held the section with nothing voiced. Fix: send_client_content now
   returns a bool (True=delivered; False=queued/no-session/send-error), and
   _inject_validator_steer holds the section only on a True delivery. Back-compat: no
   existing caller used the return value.
3. **Duplicate confirm re-ran the audio teardown** -- fixed by the same teardown move
   (it is no longer in the per-confirm path).
4. **(Left, with rationale) form_complete fires onFormComplete even on a conflict.**
   The last boundary has no switch to gate; the form genuinely IS complete (all fields
   confirmed) and the validator is an advisory second-pass net ("flag, don't block").
   Signaling complete while an advisory conflict is voiced is a minor UX inconsistency,
   not a deadlock -- decided to leave it rather than gate the form-complete UI on the
   verdict (a larger change inconsistent with the advisory framing).
   Opus fallback re-review (round 2): NO-GAPS -- both fixes verified correct +
   complete, finding #4's leave-decision confirmed acceptable. It flagged one
   low-confidence out-of-scope edge (the updateField steered carry-forward reads the
   exact key while markFieldsSteered may write under the []-alias; a value migrating
   between alias variants could drop the marker -- bounded to one extra re-steer, not
   a loop). Filed as polyglot-pdf-5k52 (P3) rather than expanding this PR.

**Defended decision (new config knob):** added `VALIDATOR_TIMEOUT_SEC` (4.0s) to
Settings for fix 2. This is a local fail-OPEN timeout constant, reversible, directly
in service of the bead's contract-4 fail-OPEN requirement -- not a new operational
dependency, so decide-by-default, not an escalation.

## Lessons

- B4's "exactly one section_complete per boundary" guard relied on `switchInFlight`
  being set SYNCHRONOUSLY by `switchToSection`. B5's gate makes the switch async
  (parked at the validator), opening a window where `switchInFlight` is still false
  -- so the duplicate-confirm guard had to also check the new `pendingSectionSwitch`
  state. A B4 regression test caught this immediately (the gate broke it until the
  guard was widened).
- A gate that `await`s a promise resolved only by an external event MUST be released
  on teardown, or the awaiter hangs forever. `disconnect` resolves the parked gate
  (with the cancel flag) rather than just clearing it.
- `switchToSection` uses a backend-side reconnect on the SAME socket -- it does NOT
  call `ws.close` or open a new socket in the mock. The observable "switch proceeded"
  signal in tests is `conn.getStatus() === 'switching_section'`, not a new
  MockWebSocket instance (an initial wrong assumption that two tests failed on).
