## What shipped

The JIT path read `schema["fields"]` -- which in JIT mode is only the synthesized
first-field schema -- for several independent system-instruction pieces, and the JIT
handshake under-sent three fields. Net effect: the "reduced SI" carried ONE field
per section, no cross-section recall, a wrong "x/1" progress count, the literal title
"Form", and a possibly-already-filled next field; and the schema de-dup gate was dead
code that re-sent schemas on retry/reconnect. All fixed:

- **Backend `ai_context.build_form_context` JIT branch:** consume
  `schema["manifest"].current_section.fields` (the real section the client sends) for
  `{manifest_text}` instead of regenerating from the one-field schema (gaps A/B);
  populate `previous_parts` from `manifest.previous_sections` for cross-section recall
  (C); recompute `filled_count`/`total_fields` from the real section set (N); render
  the field schema the client now sends (the first-unfilled field) (D).
- **Backend `websocket_routes` JIT handshake parse:** carry `form_title` through
  `schema["form_metadata"]` so `{form_title}` is the real form (O); fix the
  `manifest_field_count` log that read a non-existent `manifest.fields` and always
  logged 0 (E).
- **Backend `form_filling_service`:** actually gate `get_next_field_schema_for_jit`
  on `should_include_schema_in_response` (was imported but never called -- dead code)
  so a repeat confirm / reconnect does not re-deliver a known schema (G/L, h2ii); seed
  `_loaded_field_ids` from the handshake's `loaded_field_ids` at session start so the
  de-dup survives reconnects (L).
- **Frontend `schemaFormState.getJITHandshakePayload`:** select the first-UNFILLED
  field's schema (`computeNextField`) for `first_field_schema`, not `fields[0]` (D);
  send `form_title`, `previous_spoken_names`, `initial_field_hint` -- the three the
  JIT handshake under-sent (O/M/D-hint). `navigation.ts` back-references
  `SchemaFormState` as a type-only import, so the new value import is no runtime cycle.

## Lessons

- **In JIT mode the backend holds only the current field's full schema** -- it cannot
  render any other field's schema, so the "first-unfilled" selection (gap D) MUST
  happen on the frontend (which has all field schemas + values) and ride the
  handshake; the backend renders whatever single schema it is handed. Pushing that
  selection backend-side would have needed schemas the backend deliberately does not
  have. The fix respects the JIT design rather than fighting it.
- **A type-only back-reference does not block a value import the other direction.**
  `navigation.ts` imports `SchemaFormState` as `import type`, erased at compile time,
  so `schemaFormState.ts` can value-import navigation's functions with no runtime cycle.
