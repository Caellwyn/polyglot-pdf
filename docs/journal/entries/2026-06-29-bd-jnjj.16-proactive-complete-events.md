## Trigger

Pillar B of the SI-reduction epic (`polyglot-pdf-jnjj`). B3 (jnjj.15) built the
cross-field contradiction validator SERVICE; B4 (this bead) builds the boundary
TRIGGERS that feed it. Completion detection was reactive-only: the backend learned
a section/form was done indirectly (a post-confirm next-field-hint request, or the
`confirm_field_response.section_complete` sub-field). The validator needs an
explicit, proactive signal at the exact moment a section or the whole form
completes, carrying the current field state to check. B4 makes the client emit two
new WS events -- `section_complete` and `form_complete` -- and the backend receive
them.

## What shipped

**Frontend (`webFormConnection.ts`):**
- `buildValidatorFields(sectionFields)` -- projects the client's current field
  state into the minimal validator payload (validation-delegation.md contract 2):
  `{field_id, name, value, steered}`, non-empty values only, with the `[]`-bracket
  value fallback used elsewhere. `name` = `spoken_name || name || id`. `steered` is
  always `false` in B4 -- the per-field "already steered once" marker is owned by B5.
- `section_complete` emit -- in the confirm handler, the moment the last field of
  the current section is confirmed AND a next section exists (reusing the existing
  `sectionComplete` boolean). Carries `section_id` + the section-scoped projection.
- `form_complete` emit (`maybeEmitFormComplete`) -- when `isFormComplete(state)` is
  true, guarded on the COMPLETED STATE + a dirty-since-last-emit snapshot
  (`serializeFormValues`, confirmed values only), NOT a fire-once latch (contract
  4). This closes the edit-after-complete bypass (a user editing a value after the
  full-form pass and submitting it unchecked) while keeping the no-pester property
  (a static complete form never re-fires). Called from BOTH the confirm handler's
  form-complete branch AND the manual-edit path (`sendManualFieldUpdate`), since a
  manual edit does not re-enter the confirm handler. The snapshot resets on
  (re)connect (`handleOpen`) so reconnecting into a complete form re-validates once.
- `proceedSectionSwitch(sectionId)` -- the section auto-switch was extracted from
  the inline `await this.switchToSection(...)` into a single interceptable seam. In
  B4 it runs immediately (behavior identical). This is B4's concrete contribution to
  contract 4's ordering rule: B5 gates this one call on the validator round-trip so
  a verdict can't land after Gemini has restarted into the next section -- without
  B4 reaching into B5's wire types.

**Backend (`websocket_routes.py`):** two new dispatch arms (`section_complete`,
`form_complete`) that RECEIVE and ack (`section_complete_ack` / `form_complete_ack`)
only. PII-safe: they log `field_count` (+ `section_id`) only, never the `fields`/
values (contract 6). Feeding the payload to `ValidatorService` and the verdict/steer
is explicitly B5 (jnjj.17) -- the arms leave a clean seam (log + ack), and the tests
assert no validator/steer side effect fires in B4.

**The async wait-UX (criterion 3):** the events are fire-and-forget -- no spinner,
no silence. The user keeps talking to the current section's model; if a problem is
found, B5 surfaces it later via the steer. A clean verdict produces no interruption.
In B4-only state the auto-switch is NOT actually paused (it proceeds immediately via
the pass-through seam); the pause activates when B5 lands the `validation_result`
round-trip. This is the contract-consistent intermediate state -- contract 4 owns
the ordering jointly across B4 + B5.

**Exit-criteria scorecard (Assess, Step 5.5.a):**
1. Backend receives section_complete (section_id + payload) + once-only
   form_complete -- PASS (BE `test_section_complete_is_acked` /
   `test_form_complete_is_acked`; FE single-emit + once-only/dirty tests).
2. No double-fire vs the reactive path -- PASS (the legacy `section_completed` arm
   has no live FE sender; the new top-level event + the confirm-ack sub-field are
   distinct and each fire once: FE `...both fire exactly once, and are distinct`, BE
   `...does_not_collide_with_legacy_section_completed`).
3. Async wait-UX, no user wait -- PASS (fire-and-forget emit; the switch seam runs
   pass-through; no blocking spinner).

**Fresh-eyes adversarial assess (pre-PR, Sonnet):** round 1 found a real
GAP-FOUND (1) -- a correctness bug in B4's own deliverable. The manual-edit path
(`connection.ts onManualEdit`) applies the edit to a SEPARATE state object and saves
it to sessionStorage but does NOT mutate `WebFormConnection.this.state`, so
`maybeEmitFormComplete()` read the PRE-edit values, the dirty snapshot matched, and
the re-emit was suppressed -- leaving the edit-after-complete bypass OPEN through the
exact path the bead claimed to close. The existing test only exercised the
edit-after-complete case via the CONFIRM handler (which does update this.state), so
it passed despite the bug. Fix: `sendManualFieldUpdate` now refreshes `this.state`
from the persisted snapshot (the source-of-truth sessionStorage the edit handler just
wrote) before the dirty check. Added a test that drives the REAL `sendManualFieldUpdate`
path and verified it FAILS without the fix. Fresh-eyes also flagged a misleading test
name (a "skips empty fields" test that only checked "no event when incomplete") --
rewrote it to actually assert empty-field EXCLUSION from a fired payload. Round 2
returned NO-GAPS. Adopt 2 / reject 0 / defer 0; no out-of-scope beads filed.

**Codex outer review (post-PR, PR #271):** round 1 returned COMMENTS with FOUR
P1 findings, all real correctness gaps that fresh-eyes and I both missed -- adopted
all four (ambiguous=blocker, but none were ambiguous; all were genuine):
1. **Required-complete-with-empty-optional skipped form_complete on the voice path.**
   isFormComplete keys off required fields, but computeNextField(skipConfirmed)
   returns the unconfirmed optional, so the confirm handler never reached the
   form-complete branch and the AI/voice completion bypassed B5 entirely. Fix:
   call maybeEmitFormComplete() UNCONDITIONALLY after every confirm (it is
   internally guarded), not only in the !nextField branch.
2. **Hidden conditional fields leaked stale values into the validator payload.**
   buildValidatorFields iterated every schema field and only checked non-empty,
   ignoring show_if; a field hidden by a flipped trigger kept its old sessionStorage
   value and rode into section_complete/form_complete with no `shown` flag. Fix:
   apply shouldShowField (the same predicate navigation uses) and skip hidden fields.
3. **Duplicate confirm at a boundary re-emitted section_complete.** A second
   confirm_field for the same last field, arriving while the first auto-switch was
   in flight, re-ran the emit block before switchToSection rejected on switchInFlight
   -- a second event for one boundary (violating the once-per-boundary contract) AND
   an unhandled switch-rejection. Fix: guard both the section_complete emit and the
   switch-attempt on !this.switchInFlight, so a duplicate boundary confirm is a clean
   no-op.
4. **Reconnect into a dirty complete form never emitted form_complete.** A field
   edited while the socket was closed (idle timeout) takes sendManualFieldUpdate's
   WS-not-open early return, so no emit at edit time; handleOpen then cleared the
   snapshot on reconnect but nothing re-fired -> the dirty completed form bypassed
   B5. Fix: handleSessionReady (socket OPEN) refreshes this.state from the persisted
   snapshot and calls maybeEmitFormComplete(), re-emitting once on reconnect into a
   complete form.
   Each fix has a regression test verified to FAIL without it (FE connection suite:
   87 tests, +4 this round).

**Codex round 2 (PR #271):** one more P1 -- buildValidatorFields' non-empty filter
dropped undefined/null/'' but NOT empty arrays, so an explicitly-blank optional
checkbox group (stored as []) would ride to the validator as value: []. Fix: also
drop [] (and an array of only blanks). Regression test verified to fail without it
(FE connection suite: 88 tests, +1). This is Codex round 2 -- the MAX_REVIEW_ROUNDS
ceiling. The findings converged (4 -> 1, each round a DIFFERENT real bug, not
re-litigation); the round-3-vs-merge call was escalated to the maintainer per the
ceiling rule.

## Lessons

- The legacy `section_completed` frontend->backend message has NO live sender --
  the FE drives section completion entirely through the confirm handler. The backend
  arm is retained for back-compat but is effectively dead; this made the
  no-double-fire requirement (criterion 2) a local-variable concern in one handler,
  not a cross-path race. Recorded in ws-protocol.md.
- A section-switch in the vitest MockWebSocket cannot complete (its
  `section_switched` ack never arrives), so a test that drives a confirm THROUGH a
  section boundary trips the in-progress switch guard. Test the "final section"
  branch with a single-section schema (completing it has no next section -> the
  form_complete path) instead of driving a real cross-section switch; track the
  connection and `disconnect()` in `afterEach` to clear the ~15s switch watchdog.
- `sendConfirmFieldResponse` skips the ack entirely when no `request_id` is present
  (legacy-shape guard), so a test asserting the confirm-ack `section_complete`
  sub-field must pass a `request_id`.
- `structlog.testing.capture_logs()` is UNRELIABLE in the full backend suite: a PII
  log test that passed in isolation FAILED under full collection because a prior test
  left structlog reconfigured, so `capture_logs`'s `LogCapture` was bypassed and it
  returned `[]` (the get-settings-singleton test-ordering trap, structlog edition --
  passes alone, fails full-suite). Fix: patch the module logger's `.info` with
  `monkeypatch.setattr(wr._log, "info", recorder)` and assert on the recorded call
  args -- deterministic regardless of the global structlog processor chain. Caught by
  closeout's full-suite run, NOT the targeted run.
