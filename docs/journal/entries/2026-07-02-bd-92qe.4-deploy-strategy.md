## Trigger

The deployment-strategy half of the 2026-07-01 goal, and plan Bead 4 of epic
92qe: the hosted editor had NO deploy path (the Firebase config served only the
voice app), no documented way to provision the access-code secrets, and a real
round-trip gap -- a kit that existed only in the bucket (contractor-authored)
would silently DROP from the served manifest on the next deploy, because the
deploy regenerates index.json from the LOCAL form-kits/ tree.

## What shipped

**Two named Hosting targets** (firebase.json `hosting` is now an array): `app`
(the voice app, byte-identical behavior incl. its /api rewrite) and `editor`
(schema-editor/dist, SPA catch-all, deliberately NO /api rewrite -- the editor
calls Cloud Run directly because the Hosting rewrite's 60s cap would kill
minutes-long extraction; CORS covers it). `.firebaserc` maps `app` on both
projects and `editor` -> `polyglot-editor-demo` on the demo project.
CONSEQUENCE HANDLED: with named targets a bare `firebase deploy --only
hosting` deploys BOTH sites, so deploy-all.sh's frontend stage now pins
`--only hosting:app` -- a voice deploy can never push a stale editor build.

**deploy-editor.sh**: builds the hosted editor (`npm run build:hosted`) and
deploys ONLY the editor target. Its header is the one-time setup runbook:
create the site, map the targets, create the two token secrets + attach them
to the Cloud Run service once (`gcloud run services update --set-secrets` --
the same attach-once-preserve-on-deploy pattern GEMINI_API_KEY already uses),
and grant the runtime service account `roles/storage.objectAdmin` on the
form-kits bucket (reads work today; the editor's saves 403 until granted).

**deploy-demo.sh** exports the editor-facing backend env for the demo channel
via the existing BACKEND_EXTRA_ENV seam: `CORS_EXTRA_ORIGINS` (the editor
site's two origins) and `EXTRACTOR_MODEL`.

**scripts/pull-form-kits.sh** closes the round-trip gap: `gcloud storage
rsync --recursive --exclude="^index\\.json$"` from the bucket INTO the local
form-kits/ tree (never deletes local-only kits; index.json is deploy-generated
output, not a source file). Contractor work becomes git-reviewable locally,
then the NORMAL deploy republishes -- the maintainer stays the publish
authority. Fails with a clear message when the bucket is absent/unauthed.
(`--exclude` verified against the installed gcloud's rsync flags.)

**Docs**: config-deployment.md gained the hosted-editor deploy section (both
targets, the pinned hosting:app, the secrets pattern, the pull script);
EDITOR_GUIDE's maintainer notes gained the contractor-sharing runbook (URL +
which code per tier + rotation).

Pre-PR assess: exit-criteria rubric all PASS; fresh-eyes round 1 returned
GAPS-FOUND (1) + two notes, all adopted: (1) the REAL gap -- the pre-existing
frontend/package.json deploy shortcuts were not re-pinned, so under named
targets the unscoped prod `npm run deploy` would THROW (prod maps no editor
target) and `npm run deploy:demo`'s bare `--only hosting` would silently ship
a stale editor build (the reviewer traced firebase-tools' filterOnly/
resolveTargets source to prove both); both shortcuts are now pinned
(prod: `--only firestore:rules,hosting:app`, preserving the unscoped deploy's
rules coverage; demo: `--only hosting:app`) -- the exact lesson this entry's
own Lessons section states, applied to the instance the diff missed; (2) the
IAM runbook now includes the cold-start lookup for the Cloud Run runtime
service account (describe + the default-compute-SA note); (3) the
config-deployment warning now names the npm shortcuts explicitly. Round 2
verified the fixes (outcome in the merge ping).

## Lessons

Converting a singleton Firebase `hosting` config to named targets silently
changes what `--only hosting` means (ALL targets) -- every existing deploy
invocation must be re-pinned to its target in the same change, or the old
command starts shipping a second site's stale build as a side effect.

A shared writable store plus a local-tree-driven publish step NEEDS an explicit
pull direction. Push-only tooling looks complete until the first remote-only
artifact appears; the pull script is what makes the maintainer's git history
the review surface for contractor work.
