## The split, and why

The bead as filed bundles the mechanical cutover with the flag flip. On
inspection those cannot be separated the way I first proposed to the
maintainer: **deleting `read_disclaimer` is not independent of the flip.**
With both flags off, removing the model-read path would leave users with NO
disclaimer audio at all -- the model would not read it (deleted) and the clip
would not play (flag off). The dead path is not dead until the flag is on.

So this PR lands the genuinely independent parts and stops:

- `script_version` in the acceptance record (pure addition, improves the
  audit trail TODAY on the legacy path too -- it logs `None` there, which is
  itself the honest record).
- The five e2e drivers, fixed to work under BOTH flag states.
- The docs that were already wrong.

Left for the flip PR: the wire-type deletion, the three set-pinned tests that
fail together with it, and the flags themselves. Recorded on the bead.

## What shipped

- **`script_version` on `POST /api/disclaimer-acceptance`** -- the hash of the
  exact per-language script the user saw and heard. This is what turns the
  epic's determinism into EVIDENCE: without it the record proves someone
  clicked Agree but not what they were told.
- **The backend RETURNS the hash** (`X-Intro-Script-Version` on the intro
  route) rather than the browser recomputing it. A second implementation of
  "sha256 of paragraphs + newline + label, truncated to 16" in TypeScript
  would be a drift surface where the recorded version could name text the
  backend never synthesized. The client echoes; the backend owns.
- **CORS `expose_headers` gained the new header** alongside `ETag` -- the same
  omission the `s1iex.3` review caught, which would have made the header
  invisible to the client on the cross-origin dev stack.
- **The PII allowlist test updated deliberately** (its own comment demands
  that), plus two new tests: the VALUE survives the route (an allowlist entry
  that always logged `None` would satisfy the key-set check while recording
  nothing), and an older client omitting the field still logs rather than 422s.
- **Five e2e drivers made flag-AGNOSTIC.**

## Lessons

- **The plan said "swap the wait and the click"; swapping would have broken
  the drivers TODAY.** The flag is off, so the app still connects before
  Agree and the injection hook still appears first. A swap fixes the
  flag-on path by breaking the flag-off one. The right shape was a
  `clickIfPresent` helper -- dismiss the modal if it is already up, then wait
  for the hook -- which is correct under both. A plan written before the
  implementation describes the end state, not the intermediate one you
  actually ship through.
- **Fixing the ordering forced a second edit I did not anticipate.** Three of
  the five drivers clicked Agree again later; the existing `clickButton`
  helper waits 20s and THROWS when the button is gone, so my earlier click
  would have made those throw. Enumerating the later clicks was part of the
  same change, not a follow-up.
- **Reading a new response header unguarded was a REAL bug, not a test gap.**
  Adding the `X-Intro-Script-Version` read reddened 7 tests in the player's own
  suite, because the harness's fake `Response` has no `headers`. The instinct
  is "fix the fake" -- but the same shape is reachable in production (an older
  backend, any response variant without headers), and an unguarded read there
  would THROW and kill playback. The version is SUPPLEMENTARY to the clip:
  losing it costs an audit detail, throwing costs the user their audio. So the
  read is optional-chained AND the harness now supplies headers, with two
  tests: the version is captured (mutation-verified), and a headerless
  response still plays. Caught by running the FULL suite, not the targeted
  subset.
- **The knowledge needed to avoid a bug was already IN the file I edited.**
  My `clickIfPresent` pre-click matched `/I Agree/` only -- but the agree
  button is TRANSLATED, so the two Russian drivers show "Prinimayu" and would
  have matched nothing, hanging the flag-ON path. Those very files carry a
  comment saying the English literal "timed out at 20s and crashed the first
  run", and define a `RU_AGREE` constant for exactly this. I added a helper
  above that comment without reading it. Fixed bilingually; the RUNBOOK now
  states the rule for any future non-English driver.
  Fresh-eyes filed this out-of-scope (it only bites once the flag flips); I
  fixed it here anyway, because THIS PR wrote the RUNBOOK claim that all five
  drivers handle both states -- shipping a knowingly-false doc to correct
  later is worse than the fix.
- **`scriptVersion()` was a single last-write variable.** Replaying a cached
  clip after fetching a different language would have reported the WRONG
  version -- naming, in a legal audit record, text the user never heard.
  Unreachable through today's UI because language is pinned per mount, but
  that is a property of the UI, not of the accessor, and this record is
  exactly the thing that must not quietly lie. Now keyed per (language, form),
  pinned by a test that drives the three-step fetch/fetch/replay sequence.
- **Scar #7 twice in ONE bead, on the same set.** Making the drivers
  flag-agnostic meant removing their now-unreachable later Agree click. I did
  that for the three non-RU drivers and not the two RU ones -- so the RU pair
  clicked Agree TWICE, and the second call (a 60s blocking wait on a button my
  pre-click had just removed) would throw. Worse than the fresh-eyes finding:
  that one only bit when the flag flips, this one breaks the drivers with the
  flag OFF, which is what ships here. Both halves of this bead's driver work
  were the SAME set of five files, and I enumerated it correctly for one edit
  and by memory for the other. The cross-surface reviewer filed it as
  out-of-scope (harness runs are deferred); that routing was wrong -- the
  breakage is in today's shipped state and was introduced by this PR, so it
  is fixed here.
- **THREE times on one set, in one bead.** The same double-click defect
  appeared in three places: the 3 non-RU drivers (caught by me), the 2 RU
  drivers (caught by cross-surface round 1), and the RUNBOOK's manual
  procedure (caught by round 2 -- step 3 said click Agree, step 5 said click
  it again, with the English-only selector step 3 itself warns against). The
  set was never "the five drivers": it was "every place that clicks Agree",
  and the RUNBOOK is the manual form of exactly what the drivers automate.
  Scar #7's own wording is that the tell is a new finding differing only in
  LOCATION -- that happened twice here and I still re-enumerated only the
  code, not the doc. Fixing the RUNBOOK also exposed that my step-3 edit had
  described the click in prose without providing the runnable snippet; the
  only executable Agree command in the file was the duplicate I was deleting.
  After the third round I finally did what scar #7 says to do FIRST: a
  mechanical repo-wide grep for every place that clicks Agree. It found a
  FOURTH -- `.claude/skills/voice-harness/SKILL.md`, the skill that drives
  this harness, carrying the same stale wait-then-click order and deferring to
  the RUNBOOK for detail. No reviewer had reached it. The complete set is:
  5 drivers + RUNBOOK + SKILL.md, all now clicking Agree exactly once,
  bilingually, before the hook wait.
- **Half of a planned change was already done.** The plan says to add
  `script_version` AND `language`; `language` has been in the acceptance
  record since the route was written. Only one field was missing.
