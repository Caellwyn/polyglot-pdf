## Trigger

WS-C part 2 of the voice round-trip hardening epic (`polyglot-pdf-wpw`), the
second of the two "failure is invisible to the model" families. When a tool
callback RAISED, both adapter receive paths sent Gemini a bare `{}`
FunctionResponse. An empty body reads to the model as "the tool succeeded with
no data," so it confabulates success and moves on -- the user's value is
silently lost and they never learn the fill failed. Sequenced after `0c1`
because it wraps the same adapter `except` blocks that `0c1` edited (avoiding a
rebase).

## What shipped

- `backend/adapters/live_ai_gemini.py`: new `_tool_error_envelope()` helper near
  `_build_function_response` returns `{"status":"error","retryable":true,
  "error":...,"message":...}`. Both callback-exception handlers (model_turn.parts
  and event.tool_call) now set `response_payload` to that envelope instead of
  letting it fall through to the `{}` coercion. The body nests the failure under
  an `error` key -- the exact shape the official Live API docs use for a tool
  failure (`response={"error": ...}`; see `docs/genai_docs`). The Live API
  `FunctionResponse` carries only a free-form `response` dict (google-genai 1.38
  has no dedicated output/error channel field -- verified against the installed
  type), so an `error` key inside `response` is THE documented way to make the
  model read the call as FAILED. The `status`/`retryable`/`message` fields ride
  alongside (richer signal + backward-compatible reads). This `error`-key
  alignment was Codex's round-2 finding (PR #138); Codex's stated rationale (a
  top-level output/error contract) does not apply to this SDK type, but adopting
  the documented `error` key is strictly safer and is the literal WS-C2 goal.
- **Invariant preserved:** a callback that legitimately RETURNS None still gets
  the `{}` coercion (the tks every-named-call-gets-a-response rule); only a RAISE
  produces the error envelope. The 0ux call_id echo is preserved (the envelope
  flows through `_build_function_response` unchanged).
- **PII-free:** the message is a fixed, caller-controlled string -- NEVER the
  exception text (which can embed the field value the callback was handling).
  A test asserts the exception's value substring does not appear in the response.

Tests (red-first): callback-raise -> structured-error body on BOTH receive paths,
call_id still echoed, no PII leak; None-return -> `{}` unchanged; the existing
tks "exception still responds" guard updated from `== {}` to the envelope
contract. 250 backend tests pass.

Fresh-eyes triage: recorded in the merge ping (this entry predates the review).

## Lessons

- **An empty success-shaped response is worse than no response.** The model
  treats `{}` as "done, nothing to report" and advances; a `{"status":"error"}`
  is the difference between a silent data-loss and a re-ask. Whenever a backend
  failure produces a model-facing payload, make the failure legible in the body,
  not just the logs.
- **Distinguish raise from return-None at the coercion point.** The fix had to
  preserve the tks invariant (None -> `{}`) while diverting only the raise path;
  setting `response_payload` inside the `except` (before the `is None` coercion)
  is the clean seam.
