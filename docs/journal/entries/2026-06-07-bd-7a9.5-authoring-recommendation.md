## The recommendation

### 1. Which extractor, per half

**Build a FUSED pipeline, not "pick one arm."** The bake-off's clearest result is
that no single arm wins both halves, and the two halves want different engines:

- **(a) field extraction -> deterministic PyMuPDF skeleton (the old extractor's
  heuristic + tooltip-hierarchy pass), NOT an LLM.** The AcroForm layer is
  decisive: hybrid arms that feed PyMuPDF widget names to an LLM score field-
  detection F1 96-98% on I-90, while every pixels-only multimodal arm collapses to
  2-17% because invented `pdf_field_name`s never join -- and that widget name is
  the round-trip PDF-fill key. Beyond raw detection, the deterministic pass
  uniquely owns two attributes the LLMs get wrong: schema-conformant `section_id`
  (old extractor I-589 88.3% vs every LLM arm 0% -- they invent reasonable-but-
  non-matching slugs) and exact `pdf_position`. So (a)'s structure layer is a
  solved, deterministic problem; the LLM's job on (a) is consolidation/typing on
  top of exact names, not detection.

- **(b) relationships/logic -> a strong LLM fed that skeleton.** Pure-deterministic
  recovers essentially none of (b). The two top hybrids are close and effectively
  co-lead: `claude-hybrid` (Opus 4.8) won I-90 conditionals (show_if 78.9%,
  controls_fields 92.3%, copy_to 100%) and I-589 tables (7/9); `gemini-3.5-flash-
  hybrid` won I-589 conditional recall (show_if 54.7%, b.cond 44.6%, edging claude
  41.5%) and -- the operational tiebreaker -- COMPLETED the heavy I-589 fusion call
  (334 fields, ~49K output tokens, ~1 min) that gemini-3.1-pro could not finish in
  20 min (3.1-pro timed out on that 460-widget call at both 8- and 20-min deadlines).

  **Recommended (b) engine: claude-hybrid (Opus 4.8) as the default, with
  gemini-3.5-flash-hybrid as the cheaper/faster alternate.** Rationale: they tie on
  conditionals within a few points, but claude recovers tables (7/9 vs 0/9), and
  the residual hours (below) are dominated by table/multi-entry consolidation, so
  the table win matters more to the labor goal. Where cost/latency dominate (batch
  re-runs, the heaviest forms), 3.5-flash is the defensible swap -- the pipeline
  should keep `--model` pluggable, which the bake-off harness already proved out.
  Document AI is NOT an arm in either half (see decision 1 below).

The recommended pipeline (unchanged in shape from the bake-off writeup):

```
form.pdf
  -> PyMuPDF deterministic pass  ==> skeleton: EXACT widget names, types, flags,
     (old-extractor heuristic +      /TU tooltips, rects (pdf_position), AND
      tooltip-hierarchy parse)       schema-conformant section_ids/ordering
  -> feed skeleton + PDF to a strong LLM (Claude Opus 4.8 default; gemini-3.5-flash
     alternate) for the (b) reasoning: consolidate widget groups, synthesize
     show_if/controls_fields/copy_to/overflow from printed conditional text,
     detect tables.
  -> schema.json (draft)
  -> HUMAN CORRECTION in the schema-editor WYSIWYG (decision 2)
```

This beats every single arm: the deterministic pass nails the attributes LLMs
guess wrong (section_id, position, exact validation, widget-leaf option values),
and the LLM nails the relationships the deterministic pass cannot see.

### 2. How much human correction realistically remains

**(a) is largely solved; the residual labor is concentrated in (b), and it is
real.** Concretely, after the best fused pass a human still has to:

- **Author the two bespoke conditional keys NO arm populated correctly**
  (`conditional_logic`, `conditional_behavior`). These are custom schema
  encodings; every arm either left them empty or mis-split conditionals across the
  wrong keys.
- **Fix table / multi-entry consolidation granularity.** claude-hybrid over-emits
  on I-589 (precision 20.6%) by enumerating un-collapsed table rows; the truth is
  heavily consolidated. gemini-3.5-flash under-recovers tables (0/9). Either way,
  table grouping is a human pass.
- **Patch the long tail of (b) recall.** Even the best arm recovers ~45-55% of
  show_if and ~40-45% of overall conditional logic -- so roughly half the
  relationships are still hand-authored or hand-verified, plus supplement-overflow
  wiring.
- **(a) residue is small** once the deterministic skeleton supplies exact names +
  section_ids + positions: spot-checking consolidation/typing, not boundary
  detection.

Honest read: the fused pipeline removes most of the **(a)** hours (the bake-off's
central win) but leaves a meaningful **(b)** correction pass. That is exactly why
the correction UI is not optional -- the pipeline produces a strong DRAFT, and the
human-in-the-loop surface is where the remaining (b) hours are spent efficiently.
The epic's original "roughly equal (a)/(b)" split should shift markedly toward (b)
after this pipeline lands.

### 3. Revive the schema-editor vs rebuild

**Revive the recovered `schema-editor/` in-repo; do NOT rebuild.** 7a9.2 recovered
it from git `a0bf111`: it is structurally complete (PDF render + color-coded field
overlays + property editor with show_if logic + real-time validation + Cmd+S
export), `npm install` clean, dev server boots in ~257ms with ZERO console errors,
101/113 tests pass. The residual is bounded revival, already scoped as `7a9.6`:
reconcile 12 test-vs-component coordinate-convention mismatches (the suite was
likely already red when shelved -- NOT pdfjs drift, verified), fix the jest-dom
types wiring, clear 2 lints, visually confirm the render. That is a far cheaper
path than rebuilding a WYSIWYG PDF-overlay editor from scratch, and it is precisely
the surface the residual-(b) correction labor (section 2) needs.

## Decisions escalated to the maintainer (with numbers)

The bead asks me to put the two standing-dependency decisions in front of the
maintainer here. Both were in fact already decided by the maintainer during the
bake-off; I am recording their resolved state, not re-opening them -- and flagging
the one residual sub-decision that is genuinely live.

1. **Document AI as a paid dependency -> ALREADY DROPPED (maintainer decision,
   2026-06-06), and this recommendation concurs.** After cost research the
   maintainer dropped it: too expensive for negligible benefit over a raw strong-
   LLM pass. The bake-off structure agrees -- Document AI Form Parser only supplies
   the (a) OCR label<->box layer, which the PyMuPDF AcroForm dump already gives
   more precisely and for free (exact widget names, not OCR guesses), and it
   contributes nothing to (b). `arm_documentai.py` was written + SDK-validated and
   is kept for reference; no billable Form Parser processor was ever created, so
   there is no standing cost. **No new paid dependency is introduced by the
   recommended pipeline.** (The only paid dependency the pipeline DOES use is the
   LLM API call already in the product's budget -- Gemini/Claude tokens -- which
   per the epic is dominated by the live-session cost, not authoring.)

2. **Revive-vs-rebuild the correction UI -> recommendation is REVIVE; the live
   maintainer call is whether to greenlight investing in `7a9.6` now.** The
   technical verdict (revive, ~bounded) is clear and low-cost, so I am deciding the
   technical direction and filing accordingly. The product-owner call I am
   surfacing -- not deciding -- is sequencing/investment: greenlight 7a9.6 (revive
   the editor to green) and the new pipeline-build bead now, or hold. My
   recommendation is to greenlight both, because the pipeline's draft output and
   the correction UI only deliver the labor win together. I have filed the build
   beads as OPEN (not started); the maintainer gates whether/when they proceed.
