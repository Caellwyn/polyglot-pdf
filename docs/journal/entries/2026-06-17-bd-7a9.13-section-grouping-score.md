## Trigger

`bd polyglot-pdf-7a9.13`, a DECISION/product-call bead under epic 7a9, surfaced by
the 7a9.9 extractor research. The schema scorer (`scripts/schema_score.py`) graded
`section_id` by EXACT STRING MATCH, and that metric was proven broken: on I-90
every arm (incl. the deterministic extractor) scored 0% because the gold
section_ids are inconsistent hand-authored noise (prose like "Part 1 - Information
About You" mixed with slugs like "part_1_2_addresses", even "With"/"with"
duplicates), so nothing can match them; the one high score (I-589 88.3%) was an
artifact of that gold being authored by editing the extractor's own output.
Meanwhile the LLM produces clean, consistent ids -- arguably better than gold. The
bead reserved the call for the maintainer; this session the maintainer delegated
it ("whatever you think is best").

## What shipped

**The decision: option (b) -- score section GROUPING, not the id string.** Chosen
over (a) adopt-LLM-convention-as-canon-and-relabel-gold and (c) drop-the-signal.
Rationale, with the deciding fact verified in code: **no backend code depends on
section_id STRING values** (`grep section_id backend/**.py` -> only the field
matcher and models, no string contract), so sections are an internal grouping, not
a wire contract. That makes (b) correct: it measures what actually matters for the
UX (are related fields grouped together?), is naming-agnostic so it never breaks
again on a new id convention, and is the least-churn option (a scorer change vs.
relabeling every gold file). (a)'s weakness: even after relabeling, exact-matching
strings means any future arm with equally-good-but-different ids scores 0 again --
back here. (c) discards a real quality signal for free.

**The implementation.** `_section_grouping_agreement(pairs)` computes the Rand
index of the draft vs. gold partitions over matched fields: for every unordered
pair of matched fields whose GOLD side is sectioned, draft and gold AGREE iff they
either both put the two fields in the same section or both in different sections.
The old per-field exact `section_id` attribute is removed; a `section_grouping`
attribute is computed post-loop from this. The fuzzy field-matcher's `(section,
name)` fallback key is unchanged (a separate concern -- it matches fields, it
doesn't score them). On the i-90 draft-vs-gold pair this now reads
`section_grouping 88.9%` (was `0.0%` under exact match) -- a real, discriminating
signal. No code consumed the old `attributes.section_id` (the scorer is a research
script), and the "headline exclusion" was a process note, not a code gate, so
nothing else needed changing.

**Exit-criteria scorecard** (the bead's DELIVERABLE was "a decision, then the
scorer and/or gold updated to match it"; treated as the rubric):

1. A decision is made + recorded. PASS -- option (b), recorded here + in the
   commit, with the no-backend-dependency fact that drove it.
2. The scorer is updated to match the decision. PASS -- `schema_score.py` now
   scores grouping (partition agreement), not the exact id string; 7 unit tests
   in `tests/test_schema_score_section_grouping.py`; full root suite green
   (472 passed).

**Fresh-eyes assess (Sonnet, arm B picker, 2 rounds to NO-GAPS):** round 1 scored
both criteria PASS but caught a real subtle gap: a draft field with NO section_id
was normalized to "" and `"" == ""` made two unsectioned draft fields count as
"same section" -- so an extractor that emits NO sections scored 100% on a
single-section gold, defeating the metric's whole purpose (discrimination). Fixed:
an empty draft section is now a SINGLETON (`_same_section` returns false for an
empty side), so an unsectioned draft correctly scores ~0% where the gold groups
fields. Added 3 regression tests pinning this. Also tightened the docstring's
"symmetric" to "naming-symmetric". Round 2 returned NO-GAPS. (The i-90 headline is
unchanged at 88.9% -- the real i-90 draft has sections, so the fix only affects
the unsectioned-draft edge case.)

## Lessons

- **When a metric scores 0% for everyone, suspect the metric, not the extractors.**
  Exact-string section_id matching made every arm look equally bad and made one
  self-referential gold look great -- the classic signature of measuring an
  artifact, not quality. The fix was to measure the invariant the metric actually
  cares about (the partition) rather than an incidental representation (the id
  string). Generalizes to any "did you reproduce my exact label" scorer.
